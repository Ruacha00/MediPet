## 如何接取工作

1. 阅读根 AGENTS.md、总计划和[依赖与并行安排](DEPENDENCIES.md)，选择直接依赖已完成的 issue。
2. 阅读该 issue 所属 spec，再读 issue 的输入、输出、写入范围和验收。代码路径是计划路径，导入后以实际源码复核。
3. 在 issue 中把 `status` 改为 `in_progress` 并记录负责人；确认相同文件和同一测试环境没有其他写入者。允许多个执行者在当前重构工作树中处理互不相交的范围。
4. 按 AGENTS.md 对当前工作树做必要的影响/重命名分析，完成该 issue 的实现及验收。缺少必须输入时标为 `blocked` 并写清缺口，不把替身测试当成真实存储或模型证据。
5. 在“完成记录”填入实现位置、验证方法、结果和证据，全部验收满足后设为 `done`。下游消费已完成产物，集成时保留其他任务改动。

issue 头部的 `depends_on` 是直接前置的唯一依据；`touches` 是预计写入范围；`milestone` 表示主要验收归属，不是额外开工屏障。状态只维护在 issue 中。调整依赖后同步依赖表与批次视图，并检查环和文件重叠。遇到契约变更，先由 H01 的负责人同步样例和受影响消费者，再继续并行。

“原子”指一个可独立交付与验证的结果，连同必要代码、测试和说明；它不等于单文件或单次命令。使用假服务完成组件验收时，真实 API、存储和浏览器接通仍由后续 issue 验收。

## 阶段与当前可开始项

P1 是场景实现的共同前置，B04 完成后再开展 H01。P2—P5 的独立能力按 issue 依赖并行，不要求所有 P2 文件完成后才能准备 P3 内容，也不把晚期前端验收作为早期后端编写的隐式前置。阶段验收仍按 P1→P2→P3→P4→P5→P6 汇总，阶段通过需要对应能力与集成证据齐全；提前完成局部 issue 不等于该阶段通过。

当前进度以各 issue 和[执行检查点](EXECUTION.md)为准。后续可并行批次和共享文件规则见[调度文档](DEPENDENCIES.md)，恢复执行时先核对文件所有权，避免重复派发。
