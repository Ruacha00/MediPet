## 1. 哪些重点仍然相同

| 模块 | 保留的机制 | MediPet 中需要重新对应的内容 |
| --- | --- | --- |
| 技术栈 | Python/FastAPI、Anthropic SDK、Redis、Chroma、Vue/Vite、Nginx、Compose | 使用 DeepSeek 兼容 Messages；前端只保留 Python 后端，Prometheus为可选服务 |
| 三路意图 | LLM、向量模板、关键词融合；正常权重0.7/0.2/0.1；关闭向量0.85/0.15；阈值及失败降级 | 客服意图换为医院、医生、号源、预约、流程等；日期、实体及急症规则适配 |
| 领域与主辅路由 | 意图、关键词、实体打分；明确复合领域信号；主角色和辅助角色 | Technical→Guidance，Billing→Appointment；通用与升级角色继续存在，医院实体加分有调整 |
| 同类实例选择 | 成功率、延迟和监控惩罚构成 `routing_score`，同类型取最大值 | 与“应该由哪种角色处理”分开；默认每类一个实例，两版均没有默认多实例竞争 |
| 并行与整合 | `asyncio.gather`；成功回答进入 `ResponseComposer`；部分失败与整合失败降级 | 从“技术问题+账单问题”换为“查号源+说明材料”；卡片与工具事实独立于文字整合 |
| Agent工具循环 | `AgentToolSpec`、`make_tool`、工具声明、参数检查、工具结果回送模型 | 每个角色实际工具更换；身份由服务端注入，模型不能直接确认预约 |
| RAG | 查询改写、并行召回、去重、重排、缓存、超时与熔断 | 知识换成医院静态资料；动态库存与预约直连服务，检索失败和来源记录更明确 |
| 三层记忆 | Redis工作窗口；Chroma情景与画像；达到15条压缩，保留最近5条；24小时工作窗口TTL | 从用户/会话扩为参与者/患者/事项；新增完整历史与失效恢复，画像限制为患者资料和表达偏好 |
| Skills | 文件加载、角色与关键词匹配、system prompt注入、显式reload | 三类客服规范换成四组就诊规范与服务边界；重载不等于训练模型 |
| 监控 | 成功率、延迟、工具失败、Prometheus、惩罚反馈 | `monitor/performance_monitor.py` 与原固定源码字节一致；指标含义仍需按实际调用解释 |
| 评测 | Accuracy、Macro-F1、四维LLM Judge、回归比较 | 增加真实业务断言、隔离存储和时钟、失败分类、Judge实际背景、人工接受基线 |

核心源码入口：[意图](../../../core/intent_recognizer.py)、[编排](../../../agents/agent_orchestrator.py)、[工具](../../../agents/tools.py)、[记忆](../../../memory/conversation_memory.py)、[RAG](../../../mcp/tool_manager.py)、[Skills](../../../core/skill_loader.py)、[监控](../../../monitor/performance_monitor.py)、[评测](../../../evaluation/evaluator.py)。

“保留”不等于逐文件不改：`_vote`、本地向量和同类实例评分等核心函数经AST对照一致；医院实体与领域规则、请求局部工具结果、可靠性和业务断言有实质修改。Skills核心算法在去除文档字符串、归一品牌后模块AST一致。

RAG也不是整个模块不变：ToolManager有16个方法AST一致，5个方法因真实失败状态、片段去重、改写/召回/重排错误和重排索引校验而改变；KnowledgeBase有6个方法一致、4个方法调整初始化/来源/文档与检索。切片与调用框架保留，但片段身份和失败语义需要按当前源码理解。

## 2. 业务流程怎样变化

原固定源码的普通请求：

```text
消息 → 用户/会话记忆 → 意图 → 领域路由 → 单角色或主辅并行
     → 角色Skills及工具循环（需要时检索）→ 文字整合 → 写工作记忆 → 后台画像
```

MediPet普通请求延续这条链，在入口和结果两侧增加业务职责：

```text
绑定参与者/患者/事项 → 固定急症检查 → 记忆和当前选择 → 意图与主辅路由
→ 工具循环（业务服务或静态检索）→ 文字 + 实际卡片 + trace
→ 完整历史 → 工作窗口 → 普通请求后台更新画像
```

MediPet另有明确的状态修改入口：

```text
真实号源列表 → 准备pending方案 → 用户点击确认 → 服务端重新校验
→ Redis事务更新库存/预约/原始回执 → 写完整历史 → 失效工作窗口
```

原账单工具主要检查字段、计算金额差、提供处理建议，明确没有接入订单/支付/退款系统。当前新增的是演示医院内真实持久化的预约状态，不是简单把“退款”一词替换成“预约”。它仍不连接真实医院。

入口对照：原 `api/main.py:273` 对应现 [chat](../../../api/main.py:380)；新增 [confirm_appointment](../../../api/main.py:466) 调用 [confirm_proposal](../../../hospital/service.py:166)。原异步画像使用 `asyncio.create_task`，现在普通HTTP请求使用FastAPI `BackgroundTasks`；急症不运行普通模型、压缩或画像。

## 3. 必须新增掌握的五项

1. **准备与确认分离。** 模型只能生成待确认方案，准备不扣库存；按钮进入固定确认接口。理解 `pending/executed/expired/superseded`、当前方案、快照校验及15分钟有效期。
2. **事务和幂等。** Redis `WATCH/MULTI/EXEC` 如何避免末号超卖；同一方案重复确认如何返回原回执；取消如何只恢复一次库存。事务成功后历史失败，通过同一回执重试补齐，不能称为Redis与Chroma分布式事务。
3. **身份和作用域。** 参与者、患者、事项含义不同；已有事项绑定患者不可被请求覆盖。工具、Redis键、Chroma过滤都使用一致身份，孩子的方案不能被本人消费。
4. **业务事实和模型上下文分离。** 完整历史用于查看和恢复，工作窗口用于有限上下文。结构化卡片取自真实工具输出，文字说“成功”不改变状态；号源与预约始终查询业务服务。
5. **业务正确性与回答质量分开验证。** 预约数、库存、归属、回执及协作由确定性断言检查；Judge评价文字质量。有效质量分不能覆盖业务失败，固定样本结果不能称通用准确率。

对应阅读：[预约闭环](../../appointments.md)、[VisitStore](../../../memory/visit_store.py)、[业务模型](../../../hospital/models.py)、[记忆与Skills](../../memory-skills.md)、[评测工厂](../../../api/evaluation_runtime.py)、[实际证据](evidence/acceptance.md)。

## 4. 原资料需要纠正的说法

| 常见表述 | 应掌握的准确版本 |
| --- | --- |
| 每次按意图先RAG，再进入Agent | 原《业务流程说明》及《学习文档》仍这样描述，但固定源码的 `chat` 已不调用 `_build_knowledge_context`。两版均由Agent在工具循环中决定是否调用共享检索；辅助函数存在不代表进入主链路。 |
| 向量分支默认是远程深度语义模型 | 两版都在客户端支持 `embeddings.create` 时才尝试远端；当前实际使用256维字符1/2/3-gram哈希向量。它与Chroma知识检索的默认向量模型是两条不同链路。 |
| 三次循环就是整次聊天最多三个工具或三次模型请求 | 上限是每次角色 `_call_llm` 的模型请求次数。一次响应可以含多个工具，分类、多个协作角色、回退、RAG、Composer、记忆还会有各自调用。 |
| 所有低置信度都统一回OTHER | `_vote` 在正常投票末尾检查阈值；LLM失败分支先直接采用非零向量，再考虑关键词，提前返回。需讲清分支，不能把注释概括当精确算法。 |
| 意图缓存是严格LRU | 两版命中都不移动访问顺序；达到容量批量移除较早插入项，不是严格最近最少使用淘汰。 |
| `mcp/`目录等于部署了MCP协议服务器 | 当前和固定源码均为进程内工具注册/调用管理，应能解释接口、校验、缓存、超时、熔断及回退；没有独立MCP协议服务。 |
| 动态路由等于自动训练、自学习或默认多实例调度 | 这里是运行统计构成的规则评分；默认每角色一个实例，不涉及模型权重训练。 |
| 有三层记忆就永远记得完整对话 | 摘要和检索会遗漏；MediPet额外保存完整历史，关键业务状态仍由业务服务校验。 |
| Chroma HTTP模式由服务端计算向量，客户端不用模型 | 两版collection都使用Chroma客户端默认embedding；当前为 `all-MiniLM-L6-v2`。原记忆模块“Anthropic embedding、无本地模型”及知识库“服务端计算”的说明不符合这份固定源码。 |
| 记忆已经按重要性与时效性综合排序 | 两版实际是分区取数、向量检索和固定拼接，没有对应的融合排序器；不能从模块概述推导额外算法。 |
| HALF_OPEN保证并发时只放行一个探测 | 两版 `CircuitBreaker.allow()` 都没有并发单探测门闩。可以讲三态熔断与冷却，但不能保证这一并发性质。 |
| 简历模板里的准确率、速度和提升可以沿用 | 只能引用本项目实际报告；同条件对照之前不宣称提升。两份现有模型候选之间代码和Judge背景有变化，不能作严格前后性能比较。 |

另有实现修正需要知道：原意图函数构造了示例文本却没有放入提示词，当前实际注入；工具结果改为请求局部 `AgentTurn`，按 `tool_scope` 执行白名单，保留真实卡片、成功来源和失败轨迹。这些不是新的Agent架构，而是现有扩展点的具体修正。

记忆压缩修正了原版重新插入消息造成的顺序反转；画像只接纳能匹配用户原话的资料，患者事实与参与者表达偏好分开。阈值15是“消息条数”，不是15轮对话。

原评测器遇到Judge错误或缺字段会填默认0.5，且运行后自动写基线；当前将无效评分和调用异常单列，运行只保存candidate，经人工接受才写baseline。四维评分、0.75通过阈值、5%回归比较机制延续，但输入、失败记账和基线生命周期不同，不能称评测行为完全没变。

原《简历包装》的Java/Spring/BM25分支不适用于当前Python/Chroma实现；当前前端已移除Java后端切换。指定核心材料没有直接宣称通用DAG引擎，当前也没有此实现，不应自行扩写成图工作流平台。

原《EchoMind定位与技术亮点》已经解释了本地哈希向量，并非所有原材料都在这一点上写错。资料之间版本和准确程度不一，应逐条核对。原加强版简历模板中的约500条、91.3%、F1 0.89、RAG 88.7%及提升数字，本次没有找到并核验其对应原始报告，均不能用于MediPet成果描述。

## 5. 学习和面试时的阅读顺序

原《学习文档》§4、§5、§7的模块组织仍然适用。用原文理解动机，用下列当前文档和源码回答实现细节：

1. [架构](../../architecture.md)与[API入口](../../../api/main.py)：能画出聊天链路和确认链路，说明急症位置。
2. [意图与路由](../../intent-routing.md)：讲清三路融合、领域分工、同类实例选择三个不同步骤。
3. [工具与RAG](../../tools-rag.md)：解释工具循环、白名单、失败回退，以及静态知识与动态业务的区别。
4. [预约](../../appointments.md)：补齐原材料没有的状态机、事务、幂等、并发和回执。
5. [记忆与Skills](../../memory-skills.md)：解释三层记忆、完整历史、患者过滤、摘要限制与主动重载。
6. [评测](../../evaluation.md)：区分意图、Judge、业务断言以及替身/真实组件/真实模型证据。
7. [面试说明](../../interview-notes.md)与[演示脚本](../../demo-script.md)：使用当前业务例子逐条对应实际入口。

掌握的标准是能回答这些问题，并定位到代码：

- “查明天儿科号源，并说明首次就诊材料”如何触发两个角色？只有“准备预约”为什么不应多派指引角色？
- 三路意图融合和同类实例评分分别解决什么问题？LLM分类失败时实际走哪个分支？
- 为什么不能把每次聊天说成固定三次模型调用？哪些环节可能额外调用模型？
- 为什么模型不能直接确认预约？两个人同时抢最后一个号、用户双击按钮分别怎样处理？
- 为什么同一参与者操作本人和孩子时，记忆、选择列表和预约都要带患者范围？
- 为什么压缩工作窗口不会删除完整历史？业务执行成功后历史暂未保存如何恢复？
- 为什么静态文档允许缓存，而号源余量不能依赖公共RAG缓存？
- 为什么Skill热重载不能代替工具权限？为什么画像提取不等于模型训练？
- 为什么模型回答看起来合理，还要检查库存、回执和患者归属？
- 当前到底验证了什么，有哪些已知限制，哪些数字没有测量依据？
