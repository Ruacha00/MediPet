# I04 — 确定性 API 闭环正反例验收

## 目标

用接口级业务状态断言证明预约闭环和患者历史行为，补足原评测器只直接调用编排器的覆盖缺口。

## 实施范围

- 使用 FastAPI 测试入口、固定时钟和假模型/确定性工具输出，验证 I01—I03 实际接入。
- 在 `test_chat_api.py` 汇总身份、事项、急症和错误边界；在 `test_demo_workflow.py` 编排完整固定业务流程。
- 复用上游数据夹具和错误契约，断言响应、历史、业务记录之间的关联，不用 LLM Judge 代替状态断言。
- 本 issue 只补验收用例；发现实现缺陷回到对应责任 issue 修复后再验收。

## 输入与输出

- 输入：I03 完整入口和回执样例、上游固定时钟/存储替身、H01 契约和演示数据。
- 输出：可重复执行的 API 用例，交给 V03 真实存储、V04 浏览器及 V06 模型演示复用的流程与断言。
- 结果明确标记为确定性接口测试；Redis 事务/Chroma 过滤的真实组件结论由 V03 给出。

## 验收

- [x] 孩子新事项 → 复合查号与材料 → 选择 → pending → 确认 → 查询记录 → 准备取消 → 确认取消完整通过。
- [x] 未确认/文字确认不写预约；重复确认仅一条预约；过期、旧方案、目标不可用不改变业务状态。
- [x] 切换本人/家属后消息、事项、号源选择与预约互不串用；篡改患者/事项的请求被拒绝。
- [x] 重命名、归档、恢复、重新读取完整消息不丢失 artifacts；归档事项不能直接继续发送。
- [x] 模拟工作记忆压缩/过期后仍恢复完整历史并理解当前事项的选择上下文。
- [x] 模型不可用时急症固定响应通过，否定/一般咨询反例不误触发；普通失败保留可核对信息。
- [x] 确认回执未伪造模型 trace；聊天成功及失败 trace 与本轮结果对应。
- [x] 重复运行同一固定场景结果稳定，所有必需业务断言通过且失败用例未静默跳过。
