# I01 — 患者与事项接口及服务器身份加载

## 目标

将预置患者、事项管理和完整消息读取暴露为薄 API，并建立后续聊天、确认共用的服务器身份加载入口。

## 实施范围

- 新增 `GET /patients`、`GET/POST /visits`、`GET /visits/{conv_id}/messages`、`PATCH /visits/{conv_id}`。
- 沿用演示 `user_id` 或既有请求上下文；调用 M02 交付的事项/消息存储能力。
- 身份解析验证参与关系、事项归属和固定患者；已有事项不允许换绑患者。
- 更新只承接标题和归档状态，恢复使用 `archived=false`；不新增删除历史接口。
- 在既有生命周期注入事项存储，保持 `/health` 和现有管理接口可用。

## 输入与输出

- 输入：H01 字段、状态码/错误类别及 API 示例；M02 的患者/事项/历史存储接口与测试夹具。
- 输出：可被 I02/I03 复用的身份加载入口，以及 U03 可消费的真实患者、事项和历史 JSON。
- 列表筛选、空列表、未知事项和归属冲突均遵循 H01；API 层不拼 Redis 键或复制存储逻辑。

## 验收

- [x] 同一参与者可查看本人/家属预置患者；不可选择不属于该参与者的患者。
- [x] 创建事项绑定指定患者；患者筛选和归档筛选返回对应集合，另一患者事项不混入。
- [x] 修改标题后重新读取可见；归档后默认列表隐藏，恢复后重新出现。
- [x] 归档及恢复前后的完整消息和 artifacts 相同；未知事项返回明确错误。
- [x] 篡改参与者或患者不能读取、更新别人的事项；已有事项不能换绑患者。
- [x] `/health` 及既有管理接口的必要回归通过，执行结果记录为接口/存储替身测试或实际存储测试。
