# I03 — 创建与取消统一确认接口和历史回执

## 目标

让明确的页面确认事件直接执行服务保存的创建/取消方案，返回同一份业务回执并进入完整历史。

## 实施范围

- 实现 `POST /appointment-proposals/{proposal_id}/confirm`，复用 I01 身份加载与 H06 确认事务。
- 确认请求按 H01 携带参与者/事项上下文；患者由服务器加载，方案类型由服务记录确定。
- 映射已保存结果、过期、被新方案替代、患者/事项冲突、目标不可用及并发可重试结果。
- 返回业务回执和 artifacts，追加确认事件与结果消息；使用明确的业务操作类型标记。
- 重复确认返回 H06 保存的同一执行结果，历史中不得出现第二条独立预约成功事实。
- 确认不经过模型决策，不生成意图、主辅角色或工具模型 trace；不在 API 重新实现事务。

## 输入与输出

- 输入：H06 的创建/取消确认方法与稳定错误、I02 的身份/历史接入、H01 的确认请求/响应契约。
- 输出：U04 可调用的统一确认入口、成功/失效/重复/冲突样例，以及消息接口可读取的业务回执。
- 展示内容引用服务原快照；页面显示资料和实际执行目标能够按方案 ID 对照。

## 验收

- [x] 创建 pending 方案后无预约；确认后得到 active 预约，记录与回执及 artifacts 一致。
- [x] 准备取消方案不改变预约；确认后状态为 cancelled，历史可读到取消回执。
- [x] 同一方案重复确认返回同一结果和预约 ID；预约总数及号源占用不重复变化。
- [x] 过期、改选后的旧方案、患者不符、事项不符均返回明确失败，业务状态不变。
- [x] 并发冲突按 H06 约定返回可重试结果；测试不把异常转换为伪成功。
- [x] 确认路径将模型客户端替换为会抛错对象仍可成功；返回历史如实标记业务操作。

## 依赖与并行

- 等待 I02 和 H06 完成，接口确认依赖服务事务验证，不靠 UI 禁用按钮保证幂等。
- 串行接手 `api/main.py` 和接口测试文件；完成后由 I04 做综合接口验收，U04 接入真实确认。
- U02 可先验证纯卡片事件；只有本 issue 交付后才验收端到端点击行为。

## 完成记录

- 实施：主 agent。POST /appointment-proposals/{proposal_id}/confirm 从服务器事项加载身份，直接调用 H06 confirm_proposal；不进入模型。按 H01 返回明确 HTTP 业务错误及 ConfirmResponse，回执快照来自原执行结果。
- 历史：稳定 confirm:<receipt_id>/result:<receipt_id> 消息由 VisitStore 原子去重；服务执行后历史写入失败返回可重试错误，重试只重放原回执。历史成功后经 MemoryManager.invalidate_working_memory 清除当前窗口，下一普通聊天恢复真实回执；窗口失效失败也明确503可重试。
- 验证：I02/I03 接口专组15 passed，证据 `.scratch/I02-I03-tests.xml`。确认创建/取消及重复回放、原创建回执取消后不变、身份冲突/额外字段/旧方案/到期、历史失败后重试及记录不重复通过；确认零模型调用，后续上下文能恢复实际卡片。并发事务真实语义由 H06/V03 已通过，I04补接口错误映射用例。
- 下游：U04 可接入现有 U01 confirmAppointmentProposal；直接展示 receipt/artifacts，并重新读取服务器完整历史；不把确认再发给模型。模型/存储替身证据与 V03 的真实组件证据分开。
