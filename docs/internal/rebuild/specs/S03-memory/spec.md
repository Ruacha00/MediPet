## 边界

新增 `memory/visit_store.py` 保存预置患者、参与关系、事项及完整消息；沿用 `memory/conversation_memory.py` 的 Redis 工作记忆、压缩和 Chroma 情景/画像算法，只补患者隔离及完整历史恢复。

身份核验与登录系统不在范围内。患者来自预置关系和服务器加载的事项，模型不得覆盖患者。API 和页面操作分别由 S06、S07 交付。

## 行为约束

- `conv_id` 即事项 ID；创建后患者固定。患者切换进入其事项，恢复旧事项还原原患者。
- 归档只从默认列表隐藏事项，保留消息和预约；恢复后方可继续对话。
- 完整消息及业务卡片按原顺序持久化，不随工作记忆压缩或 TTL 删除；业务记录不用 24 小时工作记忆期限。
- 最近选择列表及当前方案引用按事项保存，使“第一个”“还是下午吧”等指向实际结果；方案状态由医院服务负责。
- 工作记忆按参与者、患者、事项隔离；情景召回先当前事项，再同一患者其他事项，禁止跨患者回退。
- 画像只保存明确提供的信息，将当前患者信息与参与者表达偏好分开；不将推断病情存成事实。
- 工作记忆过期后由当前事项完整历史恢复最近窗口，超窗内容仍沿用摘要与情景召回；历史中的号源或预约不是实时事实。

## 依赖与并行

消费 S02 的身份与内容契约；M01—M02 可与 H03—H04 并行。M02 完成后 H05 消费选择与方案引用接口，M03—M04 可以沿记忆模块独立推进。API 接入消费者负责将已加载身份传入记忆，不由存储层自由猜测患者。

`memory/visit_store.py` 与 `tests/test_visit_memory.py` 由本 spec 串行修改；医院服务、API 通过其接口消费。`memory/conversation_memory.py` 在 M03→M04 内串行，避免过滤和恢复逻辑同时改写。
