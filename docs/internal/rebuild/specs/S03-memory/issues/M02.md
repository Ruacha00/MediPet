# M02 持久化完整消息业务卡片和事项选择上下文

## 目标

交付独立于工作记忆的完整历史及事项选择存储，使刷新和后续承接可以恢复原业务资料。

## 实施范围

- 按 H01 消息契约保存用户消息、助手文字、业务卡片及确认事件/结果，保持次序与稳定标识。
- 提供按事项读取完整历史的方法，保留结构化业务 data，不从正文反推卡片。
- 按事项保存最近实际号源结果列表、选择所需信息与当前方案引用。
- 为 H05 暴露读取/更新当前选择与方案引用的方法，使改选后引用能一致切换。
- 对追加及读取执行 M01 的身份范围与归档状态规则；恢复读取不得串用其他患者。
- 消息和选择记录不绑定工作记忆压缩/TTL，重复确认回执保留业务幂等标识供 API 使用。

## 输入与输出

输入：M01 已验证身份/事项、H01 消息与 artifact 契约。输出：完整历史与事项状态存储接口、序列化恢复测试；聊天/确认调用接入由 S06 实现。

## 验收

- [x] 完整读回的文字、卡片、确认回执与追加内容及顺序一致。
- [x] 多患者多事项消息、最近列表和当前方案引用完全隔离。
- [x] 归档与恢复不删除历史；已归档事项的新消息写入按约定拒绝。
- [x] 模拟工作记忆过期或压缩，完整消息和卡片仍可读取。
- [x] 最新选择列表可还原位置与真实号源 ID，空列表和越界可明确处理。
- [x] 幂等事件标识可供确认接口避免重复追加同一执行结果，重复展示不形成新执行事实。

## 依赖与并行

依赖 M01 的身份/事项检查。完成后同时解锁 H05 方案准备、M03 记忆隔离及 I02 历史接入。与 M01 共享文件须串行；下游通过本模块方法消费，避免各自写 Redis 键。

## 完成记录

负责人：主 agent。GitNexus VisitStore 上游 LOW，仅当前测试导入；源码检索确认尚无运行调用方。按稳定契约新增历史与选择接口，医院事务通过公开键及事务方法消费。

- `append_messages(user_id,conv_id,messages)` 使用 WATCH/事务原子追加并按 message_id 去重，返回新增数；`get_messages` 全量按原顺序恢复。完整消息没有 TTL，不受工作窗口删除影响。
- `get_selection`、`save_selection(SelectionState)`、`resolve_selection(...,index)` 保存实际查询及一基序号；空结果/失败清空列表。save_selection 保留已经存储的当前方案引用，不能由调用方覆盖。
- H05/H06 共享 `redis/prefix`、`selection_key`、`decode_selection(identity,raw)` 和 `queue_selection(pipe,state)`，最后者仅将写入加入调用方现有事务，避免独立提交引用造成竞争。
- 定向测试 17 通过，含 15 项替身/算法检查、2 项真实 Redis DB15 独立前缀核验；真实核验覆盖重建实例后历史/选择恢复、去重、无 TTL，只清理自身测试键。证据 `.scratch/M02-tests.xml`；API/工作记忆接通由后继任务负责。
