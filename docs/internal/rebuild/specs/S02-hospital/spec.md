## 边界

在 `hospital/` 内建立具体医院业务模型、静态内容、查询服务和 Redis 记录。复用现有 Redis 依赖；接口、Agent 工具及页面分别由 S06、S04、S07 接入。

仅使用明和虚构医院、预置患者、固定排班与有限文字指引。实际执行仅由确认接口调用服务；模型只能查询或准备方案。真实医院、支付、诊疗建议、自动推荐科室和路线计算均在范围外。

## 行为约束

- 医院目录、医生、费用、地点与固定排班以 `hospital/demo_data.json` 为一致来源；按 `Asia/Shanghai` 和可注入时钟生成未来七天号源。
- 服务身份来自服务器加载的参与者、患者、事项关系；一个事项固定一名患者。
- 查询返回真实可用数据、稳定排序及明确失败类别；准备清单和指引含来源，动态号源及个人预约每次查询业务存储。
- 创建与取消均先生成 `pending` 方案；同事项最多一个当前待确认方案，改选使旧方案成为 `superseded`。默认有效期 15 分钟，可配置。
- 方案快照同时用于展示和执行。确认校验事项、患者、状态、期限及目标可用性，通过 Redis 事务更新方案、号源和预约；重复确认返回原执行回执。
- 初始化只补缺失记录；业务记录不用工作记忆 TTL。开发重置限定 MediPet 前缀及专用集合。
- 结构化结果由业务服务生成，正文不能创建预约事实；状态、错误和 artifact 字段由 H01 固定后供下游消费。

## 依赖与并行

H01 是 API、Agent、记忆和 UI 的共同契约入口；下游按契约实现，不各自定义身份与卡片字段。H02 后，H03—H06 沿医院服务串行推进，M01—M02 沿事项存储并行推进；H05 汇合两支。

`hospital/service.py`、`hospital/store.py`、医院业务测试由本 spec 负责，跨 issue 依赖用于避免同时修改同一实现。H01 后模型变更由 H01 契约责任人统一协调；下游提出所需变更再同步消费者。
