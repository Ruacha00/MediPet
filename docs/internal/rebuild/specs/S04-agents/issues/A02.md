# A02 · 四角色路由协作及请求上下文适配

## 目标

建立 General、Guidance、Appointment、Escalation 四角色及真实主辅协作。
消除 API 已分类输入与编排器自行分类时的实体差异。

## 实施范围

- 使用 GitNexus 重命名分析，将 TechnicalAgent/BillingAgent 及其后端枚举、配置、池初始化改为目标角色。
- 同步 `_INTENT_ROUTING`、`_domain_scores`、`_collaboration_targets` 和角色提示词，检查直接调用方引用。
- 所有消费者切换后，删除 A01 为保持中间状态可导入而暂留的旧业务枚举及其临时兼容测试；此处对分类器/意图测试的写入仅限过渡定义清理。
- 保留 `_route_decision`、同类实例 `routing_score()`、`asyncio.gather` 与 ResponseComposer。
- Request 按 H01 接收参与者、患者、事项和已有上下文；不接受模型覆盖已绑定身份。
- `AgentOrchestrator.run` 自行识别时同步 entities，预分类输入也使用同一字段含义。
- 前端角色标签留给 U 组，Skill 元数据留给 K03；不增加第五类 Agent 或改写并行框架。

## 输入与输出

输入：A01 意图/实体、H01 Request 字段，以及假模型可控制的各角色答复。
输出：主角色、辅助角色、路由理由、实体完整的角色请求和整合文字。
代表输入为“查一下明天儿科的号，顺便告诉我要带什么”，应产生预约与指引两项角色任务。

## 验收

- [x] 医院信息、号源、准备事项、人工导诊各选中正确角色；通用模糊请求可澄清。
- [x] 复合请求的两任务确实并发执行，记录各自结果，不只断言返回两个角色名称。
- [x] 相同输入分别采用预分类 Request 和自行识别，所得科室/日期/时段等实体一致。
- [x] 主辅选择仍包含领域、关键词、实体因素；同类实例选择仍使用原评分。
- [x] 一个辅助角色或整合器失败时保留有效结果，不把失败子任务描述为已完成。
- [x] 后端相关引用无残留旧角色符号；患者上下文在同一 Request 内保持一致。

## 依赖与并行

依赖 A01；A03、K03 和 API 适配使用此处稳定的角色与 Request。
本 issue 对编排器和其主测试文件独占写入，A03 必须在其完成后接续。
可与 K01/K02 以及医院服务实现并行；配置修改应先确认 B 组导入已结束。
