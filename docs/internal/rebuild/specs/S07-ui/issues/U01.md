# U01 — 前端 API 请求适配与契约样例

## 目标

在基准请求封装内承接患者、事项、完整历史、chat 和统一确认契约，使界面组件可按稳定响应样例并行开发。

## 实施范围

- 使用 H01 冻结的请求/响应和错误格式，为患者、事项创建/列表/修改、历史及方案确认增加具体请求方法。
- chat 请求携带 `user_id`、`conv_id` 及新事项所需 `patient_id`；保留原路由字段，读取患者/事项及 artifacts。
- 沿用 B04 的 Python-only 入口和 `/api/python` 前缀，保留既有知识、Skills、监控、评测请求方法。
- 统一把后端业务错误交给调用方展示，保留稳定错误类别，不把 HTTP/业务失败变成空成功结果。
- 为 U02/U03 提供少量成功、空结果、过期/旧方案、患者冲突的契约响应样例。

## 输入与输出

- 输入：H01 契约及模型字段、已导入的基准请求代码；H01 的上游基线依赖覆盖 B04。
- 输出：U04/U05 使用的请求方法、U02/U03 使用的 JSON 样例与方法参数说明。
- 样例只存演示数据，结构与 H01 一致；不另行定义前端预约状态或生成模型正文解析器。

### 下游请求与错误约定

所有方法保留 `(type, settings, ...)` 的现有调用方式，`type` 传 `python`；`settings.userId` 为参与者，`settings.conversationId` 为当前事项，chat 另读取 `settings.patientId`。业务对象、列表与历史采用 H01 的原字段；仅已有聊天归一化层继续提供 camelCase 字段。

| 导出方法 | 后续参数 | 返回 |
| --- | --- | --- |
| `requestPatients` | 无 | `{items:Patient[]}` |
| `requestVisits` | `patientId, archived=false` | `{items:Visit[]}` |
| `createVisit` | `patientId, title?` | `Visit` |
| `updateVisit` | `conversationId, {title?, archived?}` | `Visit`，仅发送这两个可修改字段 |
| `requestVisitMessages` | `conversationId` | `{visit,items:VisitMessage[]}` |
| `confirmAppointmentProposal` | `proposalId, conversationId=settings.conversationId` | 原 `ConfirmResponse`，完整保留 `receipt/artifacts`，不添加模型字段 |

HTTP 错误是普通 `Error`，带 `kind`（business/validation/http）、`status`、原 `detail` 和完整 `data`；业务对象另带原 `code/retryable`。422 数组保持数组，旧字符串保持字符串。网络错误为 `kind=network` 并保留 `cause`；页面原有 `error.message` 仍可用。2xx 空列表、204 和普通管理响应按原值返回；工具失败留在成功聊天原响应中，不被误判为 HTTP 失败。U02 消费样例、U03 消费患者事项方法、U04 接入实际操作；App 的旧用户提示由 U04 同步。
