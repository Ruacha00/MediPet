# 医院 Skill 与聊天业务闭环

Type: spec
Status: resolved

## 目标

让已注册的七个医院 Tool 在开发环境通过一个首方、版本化的“医院预约挂号协助”Skill 完成启用、绑定、发布和聊天激活，使就诊参与者可以在同一就诊事项中查询服务医院资料、科室、医生、号源及当前患者预约，并在选择号源后通过服务器权威确认创建预约挂号。

## 能力装配

- 仓库保存 Agent Skills 兼容的 `SKILL.md`，内容只指导服务医院查询与预约挂号流程，不承担平台安全策略。
- 开发 seed 通过幂等 bootstrap 同步 `HospitalToolProvider`、启用七个 Tool、创建或复用 Skill、绑定固定 Tool 版本并发布。
- 当前虚构医院 Adapter 只在开发流程中激活；生产环境不随应用启动自动创建或发布该 Skill。
- 每轮开始只暴露已发布 Skill 的发现入口；模型加载固定 Skill 版本后，后续模型调用才可见该版本绑定且当前获准的 Tool。
- 没有医院能力时继续明确提示无法查询；能力可用时只把受信 Tool 结果作为服务医院事实来源。

## 聊天流程

1. 就诊参与者可以查询服务医院、科室、医生、号源及当前患者预约。
2. 没有医院认可的导诊规则时，Skill 不根据症状自行声称医院推荐科室；必要时列出科室并建议人工导诊。
3. 号源查询在聊天中产生包含科室、医生、时间和费用的结构化卡片。
4. 就诊参与者可以点击号源卡片或通过自然语言选择；点击选择以独立结构化字段把准确 `slot_id` 提供给本轮模型，不把客户端选择当作预约事实。
5. 创建预约只生成待确认提案。确认卡展示来自已校验就诊事项和医院 Adapter 的患者显示名称、服务医院、科室、医生、时间和费用，不展示内部患者 ID。
6. 确认或拒绝后原卡片更新为服务器状态；确认成功展示预约信息和收据 ID，不再次依赖模型转述。
7. 号源卡、提案、确认状态和收据属于聊天历史；刷新后按原顺序恢复。

## 验收

- 真实 `HospitalToolProvider` 经过 bootstrap 后存在一个已发布 Skill、七个启用绑定，并通过严格加载门控进入 ReAct Runtime。
- 未调用 `load_skill` 前医院 Tool 不发送给模型；加载后才可调用，未绑定、停用、越权或阶段不符仍被拒绝。
- 系统提示与 Web 能力状态不会在医院能力可用时继续声称“医院数据未配置”。
- 端到端测试覆盖查号源、结构化选择、预约提案、权威确认、幂等提交、确认/拒绝展示和历史恢复。
- API 测试、Ruff、Pyright、Web 测试、Lint 和构建通过。

## 不在本次范围

- 真实医院 Adapter、生产凭据或生产自动激活。
- 症状到科室的医院导诊规则或模型医学判断。
- 取消预约、医院管理界面或通用工作流引擎。
