# 上下文感知的症状选科边界策略

Type: spec
Status: ready-for-agent

## Problem Statement

当前的症状选科边界把识别结果直接压缩成固定回复或空值，只检查当前消息，并依赖一组字符串条件。这能阻止部分明显的症状到科室推荐请求，却无法稳定处理口语化问法、省略式追问、已经由就诊参与者明确选择科室或号源的请求，以及症状陈述整理等正常就诊协助。

就诊参与者需要得到一致的边界行为：当其要求 MediPet 根据症状选择、比较或判断科室时，应被确定性地引导至服务医院人工导诊；当其已经自行选定科室、号源或院内服务地点时，仍应能够查询医院服务目录、号源和院内方位指引；明显急症必须继续优先触发紧急转介。

## Solution

MediPet 将在 Assistant 内、进入普通 Agent 之前应用一个结构化且上下文受限的边界策略。明显急症仍由独立的紧急转介规则优先处理。其余消息由纯策略返回人工导诊、明确目标放行或普通 Agent 放行三种结果，并附带稳定的原因码。

策略只使用当前消息、必要时的一条紧邻的上一条参与者消息，以及当前轮界面提交的号源选择。它不会读取完整就诊事项来寻找症状，也不会把历史院内方位选择当作当前轮的放行依据。人工导诊结果继续绕过模型和 Tool；放行结果继续使用现有的 Skill-first Agent Runtime，并受医院事实、医疗边界、授权和确认规则约束。

## User Stories

1. As a 就诊参与者, I want 症状选科请求稳定地转向服务医院人工导诊, so that 我不会把没有医院认可依据的模型判断误认为科室推荐。
2. As a 就诊参与者, I want “挂哪科”“看什么科”“应该去哪里”等口语化请求被正确识别, so that 表达方式不会改变医疗边界。
3. As a 就诊参与者, I want 在上一轮陈述症状后用“那挂哪科”追问时仍得到人工导诊提示, so that 多轮对话不会绕过确定性约束。
4. As a 就诊参与者, I want 较早且已不相关的症状陈述不影响当前请求, so that 新的就诊协助不会被陈旧上下文误拦截。
5. As a 就诊参与者, I want 已经自行决定科室后继续查询该科室的医生或号源, so that MediPet 仍能完成非诊断性的就诊协助。
6. As a 就诊参与者, I want 当前轮选择了明确号源后继续生成预约确认, so that 结构化界面选择不会被症状选科边界阻断。
7. As a 就诊参与者, I want 已经明确院内服务地点后继续获得方位指引, so that 症状陈述不会妨碍我前往自己选定的地点。
8. As a 就诊参与者, I want 查询服务医院的科室目录及公开说明, so that 我可以在不接受自动科室推荐的前提下自行了解医院服务。
9. As a 就诊参与者, I want 请求整理症状陈述或就诊问题时进入普通 Agent, so that 合法的诊前准备不会被误认为选科请求。
10. As a 就诊参与者, I want 否定、历史和科普语境中的症状提及不自动触发人工导诊, so that 非当前选科请求能够得到正常回答。
11. As a 就诊参与者, I want 即使已经提到某个科室，在询问该科室是否适合症状时仍被引导至人工导诊, so that 明确名称不会伪装成自主选择并绕过边界。
12. As a 就诊参与者, I want 在明确表示“已经决定”某个科室并请求查号时获得正常协助, so that MediPet 不会替我作医学判断，也不会否定我已作出的选择。
13. As a 就诊参与者, I want 明显急症与选科请求同时出现时优先得到紧急转介, so that 常规门诊协助不会延误线下紧急处理。
14. As a 就诊参与者, I want 人工导诊提示保持简洁且固定, so that 我能清楚知道 MediPet 的能力边界和下一步行动。
15. As a 就诊参与者, I want 明确目标被放行后只使用服务医院的受信任数据, so that 科室、医生、号源和院内位置不会由模型猜测。
16. As a 就诊参与者, I want Agent 不声称我选择的科室在医学上适合相关症状, so that 查询和操作不会被包装成医疗建议。
17. As a 就诊参与者, I want 预约挂号继续经过服务器权威确认, so that 边界重构不会削弱现有预约确认规则。
18. As a 就诊参与者, I want 重复提交同一轮请求时得到一致的持久化结果, so that 重试不会重复调用模型、Tool 或创建业务操作。
19. As a 就诊参与者, I want 人工导诊、紧急转介和 Agent 回复都保持现有的消息事件顺序, so that 聊天界面可以继续可靠展示和恢复历史。
20. As a 就诊参与者, I want 被取消或失败的流仍记录正确的终态, so that 边界重构不会破坏就诊事项的恢复和审计行为。
21. As a 维护者, I want 每个策略结果包含稳定的结果类型和原因码, so that 行为能够被解释、测试和审计，而不依赖回复文案反推分类。
22. As a 维护者, I want 策略保持纯函数并使用有限、可审计的识别条件, so that 安全边界不依赖额外模型调用或概率阈值。
23. As a 维护者, I want 普通业务意图继续由 Skill-first Agent Runtime 处理, so that 新策略不会演变成第二套服务端意图路由器。
24. As a 维护者, I want 通过无付费模型调用的对照语料验证阻断与放行行为, so that 每次修改都能低成本复现关键边界。
25. As a 维护者, I want 评估报告明确指向其验证的实现提交, so that 历史报告和当前实现证据不会混淆。

## Implementation Decisions

- Assistant 是边界调度所在的应用模块。HTTP delivery、Agent Runtime、能力治理和持久化接口不承担新的医疗边界判断。
- 有效执行路线保持四条：紧急转介、人工导诊、明确目标放行和普通 Agent 放行。紧急转介独立于新策略并拥有最高优先级。
- 纯策略输入固定为 `current_message`、可选的 `previous_participant_message` 和 `has_selected_slot`。不得向策略传入持久化模型，也不得把从历史消息恢复的院内方位选择作为当前轮放行信号。
- 当前轮文本中明确命名的科室或院内服务地点可以构成明确目标；其真实性和可用性仍由普通 Agent 通过受信任 Tool 验证。历史院内方位解析只在策略已经允许进入 Agent 后执行。
- 上一条参与者消息通过当前轮标识排除当前已持久化消息后取得：在同一就诊事项的已完成消息中，选择最近的一条更早参与者消息，跳过中间的 Assistant 消息。不得按固定列表位置猜测，也不得向更早历史继续搜索症状。
- 上一条参与者消息只在当前消息属于省略式选科、比较、适合性或目的地追问时提供症状上下文；其他当前请求不得继承上一轮症状。
- 策略结果包含结果类型、稳定原因码和可选固定回复。是否允许进入 Agent 必须由结果类型派生，不保存一个可能与结果类型矛盾的独立模式字段。
- 结果类型固定为 `MANUAL_TRIAGE_REQUIRED`、`EXPLICIT_TARGET_ALLOWED` 和 `AGENT_ALLOWED`。
- 原因码固定为 `CURRENT_SYMPTOM_ROUTING_REQUEST`、`FOLLOWUP_SYMPTOM_ROUTING_REQUEST`、`CURRENT_SLOT_SELECTION`、`CURRENT_EXPLICIT_TARGET` 和 `ORDINARY_ASSISTANCE`，分别对应当前轮症状选科、承接上一轮症状的省略式选科、当前轮明确号源选择、当前轮明确科室或服务地点，以及普通就诊协助。多个条件同时成立时遵循既定策略优先级并只返回一个原因码。原因码属于内部可测试契约，不暴露给客户端。
- `MANUAL_TRIAGE_REQUIRED` 必须携带固定人工导诊回复，并且不得进入模型或 Tool；两个允许结果不得携带固定人工导诊回复，并汇合到现有 Agent 路径。
- 策略内部优先判断是否存在基于症状的科室选择、比较或适合性请求，再判断当前轮明确目标，最后放行普通就诊协助。因此，“发烧，儿科合适吗”进入人工导诊，而“发烧，已经决定挂儿科，帮我查号源”属于明确目标放行。
- 症状上下文、选科意图、明确目标、省略式追问以及否定、历史和科普排除条件采用有限、命名且可审计的确定性谓词。不得增加模型分类、概率分数或医院未认可的症状到科室规则。
- Assistant 在参与者消息持久化、助手消息幂等认领及紧急转介检查之后加载一次有界已完成历史。人工导诊继续持久化固定文本并按现有顺序发送文本和完成事件。
- 当前轮界面号源选择属于就诊参与者的明确选择，但仍须通过普通 Agent 和受信任 Tool 生成权威预约确认；它不构成科室医学适合性判断。
- 普通 Agent 的系统指令明确禁止根据症状推断、比较或推荐科室，同时允许为就诊参与者已经命名或选择的目标查询医院服务目录、号源或院内方位指引，但不得宣称该目标医学上适合相关症状。
- 新策略以新增契约和测试开始，Assistant 切换完成且生产调用者清零后再移除旧的字符串或空值入口。
- 客户端消息协议、Agent 请求契约、能力快照、Tool 授权、预约确认、患者隔离和持久化接口保持不变。
- 现有历史评估报告保持不可变。新评估报告通过两阶段提交产生：先验证并提交实现、测试、语料和文档作为 implementation commit；再运行评估生成指向该 implementation commit 的报告，并将报告保存为独立 evidence commit。

## Testing Decisions

- 主验收缝是 `MediPetAssistant.handle_turn`。测试只观察事件、持久化终态、模型与 Tool 是否被调用以及对外回复，不断言私有正则表达式或内部分支布局。
- 主验收测试覆盖：当前轮症状选科、口语化选科、科室比较、症状与适合性询问、上一轮症状加省略式追问、明确科室查医生或号源、当前轮号源选择、症状陈述整理，以及急症覆盖选科。
- 主验收测试明确验证人工导诊路径为固定文本、完成终态、文本后完成的事件顺序，并且模型请求和 Tool 调用均为零。
- 主验收测试明确验证两个允许结果均进入现有 Agent 路径，并保留流式文本、持久化、取消、失败、重放、审计和指标行为。
- 增加纯策略的表驱动测试作为辅助测试缝，用于穷举阻断与放行对照、结果原因码及字段不变量；它不替代 Assistant 的外部行为测试。
- 纯策略测试必须把“上一轮症状，当前询问儿科有哪些医生”固定为 `EXPLICIT_TARGET_ALLOWED`，并把“上一轮症状，当前询问儿科是否合适”固定为 `MANUAL_TRIAGE_REQUIRED`。
- 上下文测试必须证明当前消息通过轮次标识被排除、Assistant 消息会被跳过、只选择最近的更早参与者消息，并且更旧症状不会泄漏到新的请求。
- 医院聊天集成只增加最小对照：症状驱动的目的地请求不能产生院内方位卡；当前轮明确科室或院内服务地点仍可通过现有 Skill-first 流程产生受信任的号源或方位结果。
- 系统指令测试同时断言禁止症状到科室推荐和允许查询参与者已选目标，避免只测试禁止面造成正常能力退化。
- 新增独立、全部标记为非 live 的小型策略评估语料，覆盖代表性的人工导诊、明确目标、普通就诊协助和紧急转介路线。确定性路线的最大模型请求数必须为零，允许路线只能使用案例声明的 Skill 和 Tool。
- 评估语料测试验证案例标识唯一、阻断和放行路线均有代表、确定性预算为零、Tool 白名单受限，并保持现有 live 核心语料数量不变。
- 沿用现有 Assistant 急症与人工导诊场景测试、医院聊天流程测试和评估评分测试作为先例，不复制它们已经覆盖的预约、取消和能力治理矩阵。
- 完成实现后在 Windows 运行聚焦后端测试、策略 fake 评估、现有 fake 核心评估和静态检查；GitHub Ubuntu/PostgreSQL CI 作为干净环境中的补充回归验证。付费 live 运行不是合并门槛。
- 每次修改受影响符号前执行 GitNexus 上游影响分析；提交实现和 evidence 前分别执行完整且非 partial、非 truncated 的 change analysis，并检查所有直接依赖。

## Out of Scope

- 自动根据症状生成候选科室、比较科室或推荐科室。
- 新增 `guide_department` Skill、候选科室数据卡或医院未认可的导诊规则。
- LLM 意图分类、概率阈值、人工审核队列或模型生成后的流式语义拦截。
- 构建通用服务端意图路由器，或修改现有 Skill-first Tool 暴露顺序。
- 按请求过滤能力快照、修改 Agent 请求契约或增加新的 Tool 授权层。
- 扫描完整就诊事项寻找症状上下文，或支持超过一条参与者消息的症状承接。
- 多语言症状及选科识别。
- 修改紧急转介规则、预约确认、患者隔离、事务或持久化模型。
- 覆盖或重写已有 live、targeted 或 fake 历史评估报告。
- 修改既有关于 Skill-first、紧急转介和不建设自动科室导诊的 ADR。

## Further Notes

- 当前策略入口的上游影响分析为 HIGH：直接影响 Assistant，并通过两个 HTTP turn 流程扩散至现有测试。实现必须在切换调用者时保留持久化和事件顺序。
- 该计划文档未生成规划工具专用的 evidence provenance 摘要；这不属于 MediPet 的产品验收或 Definition of Done。
- Windows 是主要开发与本地验收环境；GitHub Ubuntu/PostgreSQL CI 仅补充验证干净环境中的可重复运行，不要求为项目单独维护 Docker、WSL 或 Linux 开发环境。
- 一条上一参与者消息是本 spec 明确采用的上下文上限。若产品以后要求更长的症状承接，应作为新的范围决定，而不是静默扩大策略输入。
- 新的 fake 策略报告应记录 implementation commit；报告自身由后续 evidence commit 保存，从而避免报告指向尚未提交或已经改变的工作树。
