# MediPet 业务流程说明

本文档从业务视角说明 MediPet 如何处理一次就诊请求：什么时候先识别意图，什么时候切换 Agent，什么时候并行协作，什么时候压缩会话，什么时候更新用户画像，什么时候触发升级或降级。

当前 MediPet 的主链路是一个**路由驱动的多 Agent 运行时**。它不是单点回答，而是把识别、路由、执行、记忆、监控和评测串成一条业务链。

## 1. 一次用户请求的完整流程

用户调用/chat或CLI输入消息后，系统按下面顺序处理。CLI复用聊天入口，但没有患者管理、上传和确认UI。

```text
用户消息
  → 校验user_id/patient_id/conv_id；无事项才创建
  → detect_emergency当前急症前置
     命中 → EMERGENCY/CRITICAL → Escalation固定提示/120
          → 保存历史与不压缩窗口 → 返回，不调用普通模型
     未命中 → 读取记忆上下文
        - Redis当前事项工作窗口和摘要
        - Chroma同患者情景记忆
        - 当前患者明确资料、参与者表达偏好
  → 意图识别：LLM + 本地中文语义向量（字符hash为后备）+ Pattern
  → 领域打分、选择主角色与辅助角色、选择同类实例
  → 按角色/关键词匹配Skills，注入system prompt
  → 角色调用白名单工具；需要公开资料时才调用RAG
  → 主辅结果整合：文字、严格卡片、失败与tool trace
  → 完整事项历史落盘
  → 更新工作窗口（普通路径可能在这里等待摘要）
  → 安排BackgroundTasks画像更新
  → HTTP返回；后台任务随后执行
```

不能把“async函数”理解为不等待。await历史写入、记忆压缩仍在响应前；画像任务通过FastAPI BackgroundTasks安排在响应后。同步Chroma操作部分经asyncio.to_thread移出事件循环，但不等于任意数据库操作都自动并发。

### 1.1 身份为什么先校验

VisitIdentity是用户、患者、事项三元组。已有conv_id必须存在、属于当前用户、患者一致且未归档；模型参数不允许覆盖身份。一个家长的本人和孩子共用user_id，也不能共用预约、报告和最近号源。

### 1.2 评测请求的完整流程

```text
/eval/run
  → 意图分类，计算Accuracy/Macro-F1
  → 每例隔离Redis前缀/Chroma集合与固定时钟
  → 显式setup用户动作 → 单轮/多轮Agent回复 → between/after用户动作
  → 核查真实工具与业务断言
  → 四维Judge：relevance/accuracy/completeness/helpfulness
  → 对比已接受baseline → 保存candidate与失败/跳过 → 清理隔离数据
```

选择、确认等显式动作由评测夹具执行，不交模型猜测。Judge失败单列，不纳入有效质量平均；高语言分不能覆盖业务失败。人工接受是独立动作，不会每跑一次自动覆盖基线。

U002 意图专项采用另一条离线链路：固定输入 → 真实向量排名和保存的 LLM 响应 → 三模式分类重放 → 独立指标。它不执行本节的业务工具、HTTP 和 Judge 全链路。候选未接受与测试失败是不同状态；本轮专项确有故障接受准确率未过门槛，具体结论见[指标模板](带数据指标的加强版简历模板.md)。

## 2. 什么时候会切换 Agent

MediPet并不是固定使用一个Agent，而是根据用户问题动态选择。先分清意图、领域和实例：识别给语义线索，领域决定职责，同类实例才比较性能。

### 2.1 就诊材料、流程、路线切到 GuidanceAgent

当意图为visit_preparation、visit_process、wayfinding，或包含明确材料/路线需求时，选择就诊指引领域。

典型输入：

```text
第一次带孩子来要带什么材料？
到院后先报到还是先候诊？
从门诊入口到儿科怎么走？
需要无障碍路线
```

业务效果：

```text
主领域选择 → GuidanceAgent
  → get_visit_checklist / get_wayfinding / search_knowledge_base
  → 材料或路线卡片与可核查来源
```

Guidance匹配skills/visit_guidance/SKILL.md。未知地点应澄清，不补造楼层。“准备预约”没有材料需求，不能因为裸词“准备”调用Guidance；“需要的资料”“准备材料”才构成具体信号。

### 2.2 号源、预约、取消切到 AppointmentAgent

相关意图包括slot_query、appointment_create、appointment_status、appointment_cancel。典型输入：

```text
明天儿科还有号吗？
帮我选第一个号源
查询当前就诊人的预约
请准备取消预约，预约编号：实际预约ID
```

业务效果：

```text
AppointmentAgent → 查真实号源/预约 → 准备方案
用户核对方案 → 独立确认端点 → 实际回执
```

角色工具只查询和prepare，不提供execute确认工具。skills/appointment_assistance约束不以文字承诺成功。最近列表缺失、已过期或查询失败时，“第一个”不能沿用旧列表猜号源。

### 2.3 普通咨询使用 GeneralAgent

如果问题没有明确落到专业领域，通常由General处理。

```text
你好
医院有哪些科室？
儿科有哪些医生？
如何联系导诊？
```

General通过公开目录和共享知识工具回答。公开排班不等于动态余量；不能看到医生排班就承诺可以预约。general_visit Skill提示引用实际目录，不替患者猜疾病或剂量。

### 2.4 转人工或明确急症会触发升级

导诊联系与急症不是同一种结果。

```text
我要联系人工导诊 → contact_info，只提供联系资料
我现在呼吸困难 → 当前急症规则 → CRITICAL → 固定Escalation/120
```

项目不会发送人工工单或通知医院。急症检测复用于API、编排和分诊；当前胸痛、呼吸困难、意识异常以及超过39.5℃的有限演示规则有否定、历史、引用反例。超过不是等于及以上，未命中不证明安全。

急症跳过普通get_context、分类、RAG、角色工具循环、整合、摘要和画像；历史追加使用compress=False。零普通模型调用应由计数/替身测试核查，不能只凭页面快。

### 2.5 症状与报告切到Triage，药品资料切到Medication

```text
我30岁，咳嗽两天，没有呼吸困难，应该看什么科？
→ triage_symptoms → triage_guidance建议与缺失信息

请整理这份血常规 / 核对本事项最近报告
→ preprocess_report / read_current_report → report_summary

布洛芬的注意事项？我还在用华法林
→ medication_information → 明确药名剂型、来源和未收录澄清
```

Triage只作有限分诊和报告信息整理，不个体诊断；Medication使用当前两份明确药品标签，未收录不能猜。多个药品可以有多张卡，不能假设一次请求只有一张medication_info。

### 2.6 三路意图与领域打分如何衔接

三路权重LLM/向量/关键词为0.7/0.2/0.1，关闭向量为0.85/0.15。意图主后端为本地BGE中文语义ONNX，256维字符hash是显式对照/后备；两者分别校准分数和跨类分差，不共用Chroma知识模型。未校准或空间不匹配时向量弃权，不把正余弦视为可靠分类。

LLM异常先检查强细粒度关键词与有独立资格的语义是否冲突；冲突OTHER，无冲突时强关键词优先。没有强关键词时，语义须通过门槛、模板未变且非受控省略句才独立接管，hash还需一致细粒度关键词。不足就澄清，不是重新归一化剩余权重。即使分类为appointment_create，也仍只准备方案，不能替代按钮确认。

`_domain_scores`对General有0.1起点，意图映射给通用加0.55/专属加0.75，专属关键词每个0.18最多0.45，通用每个0.12最多0.35，实体还有加分。分数是规则证据，不是医疗正确概率。缓存含完整清洗消息、最近三条完整历史、上海日期及空间/`generation`/模板/校准版本；失败LLM或运行时降级不进入普通缓存。满1000删除最早插入500，不能称严格LRU。

## 3. 什么时候会多 Agent 并行协作

如果一句话同时涉及多个业务领域，系统先计算领域分数确定primary_agent，再通过_collaboration_targets检测明确专业信号，将其他命中领域加入supporting_agents。不会因为主分数较高就过滤明确辅助需求。

| 领域 | 对应Agent | 主要证据 |
|---|---|---|
| general | General | 医院、科室、医生公开查询 |
| appointment | Appointment | 号源、日期、选择序号、准备/取消预约 |
| guidance | Guidance | 材料、流程、路线、无障碍 |
| triage | Triage | 症状分诊、报告整理/读取 |
| medication | Medication | 药名、用法注意事项、相互作用资料 |

```text
命中的专业领域 → supporting_agents
primary_agent不重复加入
General不作为辅助角色
没有明确协作信号 → 再看至少0.45且达到主分数55%的弱信号兜底
```

### 3.1 预约 + 就诊指引复合问题

典型输入：

```text
查明天儿科号源，并说明第一次带孩子来需要的资料。
```

系统需要分别处理：

```text
预约：查询当前真实号源
指引：首次儿童就诊资料
```

业务处理示意，主次由当次实际打分决定：

```text
primary_agent = appointment
supporting_agents = [guidance]
AppointmentAgent + GuidanceAgent并行处理
```

观察响应的agent_types、slot_list、visit_checklist和tool_traces。文字可能被ResponseComposer整合；整合模型失败才按主次拼接已有文字。卡片单独合并，不从最终文字重新猜结构。

反例“请为当前就诊人准备预约，号源编号：真实ID”没有材料需求，只需要Appointment。两轮分别出现两个角色也不能证明同轮协作。

### 3.2 为什么要并行而不是只选一个 Agent

如果只选Appointment，材料问题可能被忽略；只选Guidance，不能查询动态号源。

| 业务问题 | 并行协作的收益 |
|---|---|
| 一个问题跨多个领域 | 避免漏答 |
| 用户一次提出多个诉求 | 分领域处理 |
| 专属工具不同 | 主角色处理主要诉求，辅助补充 |
| 需要可观测路由 | 返回主辅角色、原因和实际轨迹 |

源码通过asyncio.gather(..., return_exceptions=True)运行主辅任务。它同时等待任务，但一个角色失败会作为结果保留，不立即掩盖另一角色成功；之后仍需显式检查异常。没有同条件对照，不声称固定提速比例。

### 3.3 工具回环的实际边界

每次角色执行最多三个messages.create请求，每次可含多个tool_use。程序校验白名单/参数后调用实际handler，把tool_result发回模型；第三次仍索要工具会失败结束。

三次是单角色上限，不是整个聊天最多三次：意图、辅助角色、RAG改写重排、整合和记忆可能另有模型请求。MCPToolManager是进程内管理器，不代表部署了远程MCP服务器。

## 4. 什么时候会降级到 GeneralAgent

降级是系统可靠性策略。即使专属Agent出问题，也尽量给用户一个通用答复。

| 情况 | 结果 |
|---|---|
| 目标类型无可用实例 | 尝试General |
| 专属角色执行失败 | 可尝试General兜底，保留失败记录 |
| 整合模型失败 | 保留成功角色文字并按主次拼接 |
| 业务工具失败 | 保留真实错误，不能伪造号源或预约 |
| General或存储仍失败 | 明确错误，不保证总能成功回复 |

```text
专属失败 → 可用General兜底 → 保留原失败与真实卡片
```

通用答复只改善表达，不意味着原业务办理成功。特别是库存、确认、身份错误必须由确定性服务处理；不能让LLM重写错误为“已预约”。

## 5. 什么时候会话会被压缩

MediPet 会把当前会话最近消息存在 Redis 中，叫工作记忆。

默认规则：

```text
WORKING_MAX = 20
COMPRESS_AT = 15
```

当同一个 `user_id + patient_id + conv_id` 的工作记忆达到 15 条消息时，会触发压缩。

### 5.1 压缩前

Redis 中可能有很多轮消息：

```text
user: 你好
assistant: 你好，请问有什么可以帮你？
user: 我要准备预约
assistant: 请先核对就诊人和号源
...
```

### 5.2 压缩时

系统会：

```text
旧消息 -> LLM 总结 -> 会话摘要
```

然后执行三件事：

```text
1. 摘要写入 Redis medipet:summary:{user_id}:{patient_id}:{conv_id}
2. 摘要写入 ChromaDB medipet_episodic
3. Redis 工作记忆只保留最近 5 条
```

### 5.3 压缩后

后续上下文包含摘要、相关历史、有限最近消息、明确画像和当前选择。先观察压缩的三部分：

```text
会话摘要
相关历史
最近 5 条消息
```

业务价值：

| 问题 | 压缩带来的收益 |
|------|----------------|
| 对话太长 | 控制 prompt 长度 |
| 历史信息不能丢 | 用摘要保留关键信息 |
| 后续还要查历史 | 写入 ChromaDB 供语义检索 |


### 5.4 怎样观察而不制造收费对话

完整使用指南第10—11章提供LRANGE/TTL/summary与Chroma身份过滤。可用tests/test_conversation_memory.py中working_memory_and_summary_keep_patient_and_visit_scope的fake参数，在第15次add_message前后观察；不连接生产存储或真实模型。

原先完整历史不应随压缩丢失，VisitStore另存全部消息和卡片。窗口过期后从同事项历史最多恢复20条，带卡片metadata，不重放预约工具；WATCH避免并发覆盖。压缩本身发生在普通响应前，急症用compress=False跳过。

## 6. 什么时候会更新用户画像

普通/chat回复准备完成后，系统安排后台更新；急症路径不安排。触发时机：

```text
Agent回复 → 完整历史 → 工作窗口 → 安排BackgroundTasks
HTTP响应发送 → 后台update_profile → 提取与检查原话 → Chroma写入
```

模型提取的结构示意：

```json
{"patient_facts":["我30岁"],"preferences":["回答请简短一点"]}
```

模型提出内容必须逐字存在于最近用户原句中，不能从助手答复或另一患者资料推断。患者记录ID为patient:{user_id}:{patient_id}，表达偏好ID为participant:{user_id}，存入medipet_profiles。

| 画像信息 | 后续作用 | 限制 |
|---|---|---|
| 明确患者资料 | 当前患者上下文 | 不合成诊断，不跨家属 |
| 表达偏好 | 回答语言/长短 | 不共享病情 |
| 动态预约状态 | 不作为长期画像事实 | 重新查业务工具 |

后台更新不阻塞当前HTTP回复，但它仍可能失败或耗费模型请求；响应成功不证明画像已落库。日志与第9.6存储检查分别验证。同步Chroma调用通过to_thread处理，不在事件循环直接长时间阻塞；这不同于把所有await都放到后台。

## 7. 什么时候会查询知识库

知识库有两种使用方式：

| 入口 | 用途 |
|---|---|
| /chat | 角色按需调用search_knowledge_base工具 |
| /search | 单独调试查询改写、并行召回、去重、重排 |

典型问题：

```text
首次就诊需要什么材料？
儿童就诊有哪些准备？
到院报到和候诊流程是什么？
```

实际检索流程：

```text
角色决定需要公开资料 / 独立search
  → 保留原查询，最多补3个不同角度
  → 并行召回medipet_knowledge
  → 按稳定chunk_id去重
  → 候选超过top_k时LLM索引重排
  → 返回真实结果/来源及错误字段
  → tool_result送回角色
```

改写失败保留原问题；重排失败保留原序前top_k；部分召回失败保留成功片段并标partial；全部失败与真正空结果分开。fallback文字不是来源。

### 7.1 接入 `/chat` 后业务上有什么变化

单独/search只能证明检索接口可用；主链按实际工具调用，才能把资料和当前回答关联。当前/chat并没有把旧_build_knowledge_context作为必经步骤，不能写成每次分类后自动预检索。

例如问儿童就诊材料：

```text
Guidance → search_knowledge_base
  → title/source/source_id/doc_id/chunk_id等实际来源
  → 回答与材料说明
```

检查response.tool_traces里该工具的success与sources，并与页面运行详情对照。来源列表缺失时不能凭result_count声称找到可靠文档。号源、药品标签、报告有独立事实服务，不要求都绕RAG。

### 7.2 缓存和降级怎样影响观察

知识工具可用300秒静态缓存、默认30秒超时、连续失败5次熔断、60秒后恢复尝试；这些不适用于个人报告或预约写操作。直接Chroma查询没有改写/重排模型，便于区分向量召回与语言加工各自的问题。

## 8. 什么时候会加载和注入 Skills

Skills是可热加载的业务处理规范，和知识库互补：

| 类型 | 解决的问题 | 示例 |
|---|---|---|
| 知识库 | 业务事实是什么 | 就诊材料、报到流程、公开说明 |
| Skills | 应怎样处理 | 如何澄清、如何核对、不能承诺什么 |

启动时api/main.py创建SkillManager，从MEDIPET_SKILLS_DIR加载。当前六组：general_visit、appointment_assistance、visit_guidance、health_triage、medication_information、service_boundaries。

```text
用户消息 → 选择Agent → BaseAgent._build_system_prompt
  → SkillManager.prompt_for(message, agent_type)
  → enabled=true → agents匹配 → keywords命中或为空
  → 按预算拼入system prompt
```

### 8.1 通用 Agent 加载 Skills 的具体例子

用户消息：

```text
医院有哪些科室？
```

系统选择General后执行：

```text
agent_type.value = general
BaseAgent._build_system_prompt(req)
SkillManager.prompt_for('医院有哪些科室？', 'general')
```

skills/general_visit/SKILL.md头部实际字段：

```yaml
name: 医院公开信息
description: 查询明和虚构医院的科室、医生、地点和门诊说明

|---|---|

print([s.name for s in m.skills if s.matches('医院有哪些科室？', 'appointment')])
```

容器内路径用/app/skills。本地复制文件到临时目录，分别改enabled、agents、keywords观察正反例；不要直接改运行规则作为实验。正式修改后：

```powershell

curl.exe http://localhost:8000/skills
```

检查count、errors、适用角色和新请求。加载成功不证明模型必然遵守；Skill不能增加工具权限或跳过身份检查。Escalation虽然在service_boundaries配置角色中，固定急症输出不读取Skill prompt，由代码保证。

## 9. 什么时候 Monitor 会影响路由

Monitor 每 10 秒采集一次 Agent 和工具表现。

采集指标：

```text
Agent 成功率
Agent 平均延迟
工具成功率
工具平均延迟
工具连续失败次数
```

如果某个 Agent 成功率低或延迟高，Monitor 会计算 `monitor_penalty` 并写回 Orchestrator。

路由分数：

```text
base_score = success_rate * 0.7 + latency_score * 0.3
latency_score = 1 / (1 + avg_ms / 1000)
routing_score = base_score * max(0, 1 - monitor_penalty)
```

业务效果：

```text
表现差的 Agent -> routing_score 降低 -> 后续更少被选中
```

当前已按同类实例选择；先定职责领域，再在同类中比较性能，不把更快的通用角色当作医生角色替代。

手算示例：成功率1.0、平均1000ms、penalty=0.1时，latency_score=0.5，base=0.85，routing_score=0.765。该值是性能选择分数，不是回答准确率。没有同条件实验，不宣称降低固定比例延迟。

## 10. 常见业务场景示例

### 场景一：普通问候

```text
用户：你好
角色：General
结果：普通欢迎语；不要求知识检索
```

### 场景二：就诊指引

```text
用户：第一次带孩子来需要什么材料？
角色：Guidance，匹配visit_guidance
结果：实际清单和来源，缺失条件明确补问
```

### 场景三：预约问题

```text
用户：查明天儿科号源
角色：Appointment
结果：真实slot_list及remaining；未扣库存
```

### 场景四：预约 + 材料复合问题

```text
用户：查明天儿科号源，并说明第一次带孩子来需要的资料
角色：主辅appointment/guidance同轮执行
结果：号源和材料两类卡片，失败分支保留
```

### 场景五：预约 Skill 约束执行承诺

```text
用户：就这个号，直接给我约好
角色：Appointment准备方案
结果：展示核对卡；必须独立确认端点才执行
```

确认执行采用Redis WATCH/MULTI/EXEC、库存校验与原回执重放，没有Lua。方案过期/患者不符/库存不足返回明确错误。重复同proposal_id返回同回执，稳定message_id去重；业务提交和历史写入不是跨存储总事务，历史失败应重试原ID补写。

取消也先prepare再confirm，只恢复一次余量。归档事项可读历史，不能继续执行；文字切患者不能绕过服务端绑定。

### 场景六：长对话

```text
普通窗口达到15条消息 → 摘要 + 最近5条
完整事项历史保留 → 刷新恢复卡片和回执
```

使用隔离假模型夹具观察，不以连续付费请求代替测试。

### 场景七：导诊联系与急症

```text
我要联系人工导诊 → 提供contact_info，不发送工单
我现在呼吸困难 → 固定Escalation/120，零普通模型
```

### 场景八：报告上传与只读追问

```text
当前事项上传文字/扫描/混合PDF或图片
  → 10MB/10页及格式/像素/时间检查
  → pypdf文字 + pdfium/Pillow/Tesseract本地OCR
  → extracted_text/observations/warnings → 完整历史report_summary
追问本报告 → read_current_report → 同事项最新卡
```

原件不持久保存，不送外部OCR或vision模型。混合页保留原文字与OCR分区；缺单位/范围或疑似OCR只标unassessed。没有报告可以安全澄清，不强求模型一定调用一个失败工具。切患者/事项不能复用旧报告；上传不清除预约选择和方案。

### 场景九：症状与药品信息

```text
30岁咳嗽两天、无呼吸困难 → 有限分诊/缺失信息/来源
布洛芬与华法林 → 指定标签与未收录说明；可能多张卡
```

建议不等于诊断，标签不等于个人处方，未知剂型和范围外问题保留澄清，不以“模型知道”补造目录事实。

## 11. 业务规则速查表

| 触发条件 | 系统行为 |
|---|---|
| 普通公开咨询 | General + 实际目录/按需RAG |
| 材料、流程、路线 | Guidance + 清单/路线工具 |
| 号源、预约、取消 | Appointment，只查询和准备 |
| 症状/报告 | Triage，有限规则/原报告数据 |
| 药品问题 | Medication，明确标签与范围外澄清 |
| 当前明确急症 | 固定Escalation/120，跳过普通模型 |
| 角色/关键词匹配Skill | 注入普通角色prompt，不能增加权限 |
| 修改Skill文件 | 显式reload再核查新请求 |
| 同轮复合需求 | 主辅并行并保留真实卡片/失败 |
| 专属失败 | 可尝试General，不冒充业务成功 |
| 工作窗口达到15条 | 普通路径压缩、保留5条，不裁完整历史 |
| 普通响应后 | 后台画像，只存明确用户原话 |
| 实例成功率低/延迟高 | Monitor同类实例降权 |
| 需要公开资料 | 实际知识工具按需检索 |
| 查询失败/空列表 | 清理可选择列表，不能沿用旧号源 |
| 用户核对后调用确认 | 事务提交、回执、幂等重放 |
| 已执行但历史失败 | 原方案重试补写，不重复办理 |
| 报告追问 | 当前事项最新卡；不跨患者/事项 |
| 每次模型评测 | 保存`candidate`，不自动接受baseline |

学习时按“触发输入→路由依据→实际工具→存储变化→可观察证据”逐步复述。既能讲正常流程，也要能解释失败分支和不改变业务状态的请求。
