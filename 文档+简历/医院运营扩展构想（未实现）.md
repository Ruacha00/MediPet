# MediPet 医院运营扩展构想（未实现）

> 本文沿着“定位 → 背景 → 场景 → 角色 → 处理链路 → 对外表达”的顺序，讨论 MediPet 如何继续向医院服务协同扩展。当前已实现就诊咨询、预约办理和健康信息处理，以及 RAG、分层记忆、多 Agent 路由、Skills 和评测机制；真实医院身份认证、HIS 接入、人工工单队列和生产运营体系仍是构想。下文分别标明已有基础和待扩展部分。

## 1. 定位概述

### 一句话定位

MediPet 的扩展方向是面向医院就诊服务的智能协同系统：统一接入咨询请求，识别意图、提取关键实体、检索就诊知识，分派专业 Agent 协同处理，并通过监控与评测发现服务问题。真实医院接入需要在当前演示系统之外继续建设。

### 更技术化的表达

```text
MediPet 已有基础 = Intent Recognition + RAG + Memory + Multi-Agent Routing + Skills + Monitor + Evaluation
医院运营扩展 = 已有基础 + 真实身份体系 + 医院系统适配 + 人工工单协作 + 生产运维
```

它适合被描述为：

- 医院就诊服务协同系统的演示基础
- 多 Agent 就诊服务编排运行时
- 面向咨询与预约引导任务的 Agent Orchestration Platform
- 支持可观测、可评测、可迭代的医院服务 Agent 项目

## 2. 为什么不只叫智能客服

“智能客服”通常容易被理解成：

```text
用户问一句 -> 机器人答一句
```

MediPet 的设计重点是把就诊服务请求拆成一条可核查的工程链路：

```text
业务请求
  -> 就诊人和会话绑定校验
  -> 急症规则检查（命中后直接返回固定升级响应）
  -> 普通请求读取记忆
  -> 意图识别与实体提取
  -> 多 Agent 路由
  -> 动态规则注入
  -> Agent 按需调用业务工具或 RAG
  -> 专业 Agent 回复
  -> 完整历史与工作记忆写入
  -> 运行监控
  -> 按需运行评测
  -> 根据评测结果修订并复测
```

因此，学习这个项目时，需要同时理解服务编排、状态一致性和工具边界。评测由接口或脚本发起，并不在每条聊天请求后自动运行。

当前项目已经覆盖的关键能力包括：

- 细粒度业务意图识别
- 结构化实体提取
- RAG 就诊知识库检索
- Redis + ChromaDB 分层记忆体系
- 主 Agent + 辅助 Agent 的结构化路由
- 动态 Skills 规则注入
- 工具缓存、超时、熔断和 fallback
- Monitor 在线观测与路由降权
- LLM-as-Judge 端到端评测
- 就诊人隔离、预约提案确认与报告预处理

“当前覆盖”表示代码中存在这些机制，不代表已完成真实医院上线、临床效果验证或生产规模验证。

## 3. 业务背景

医院服务场景中会持续收到跨部门、跨系统、跨规则的问题：

- 导诊人员需要回答科室、医生、就诊材料和院内路线问题
- 预约服务人员需要查询号源、核对就诊人和处理预约变更
- 咨询人员需要识别超出信息服务范围的问题，并引导用户就医或联系人工
- 内容运营人员需要维护科室介绍、就诊流程、说明书来源和升级边界
- 管理者需要观察 Agent 成功率、延迟、工具稳定性和回复质量

传统处理方式通常依赖人工分流：

```text
用户问题 -> 一线人员判断 -> 查就诊知识 -> 联系导诊/预约服务 -> 回复 -> 复盘
```

本项目试图应对的流程问题是：

- 分流慢，用户等待时间长
- 上下文容易在部门流转中丢失
- 复合问题容易只处理其中一部分
- 业务知识更新后难以及时同步到所有处理人员
- 缺少统一的自动化评测和回归检测机制
- 管理者很难量化不同 Agent、工具和规则的实际效果

MediPet 的目标是让这条链路可观测、可评测、可迭代。上述问题是场景设计动机；当前没有真实医院等待时间、人工工作量或满意度的对照数据，不能据此宣称已经产生业务收益。

## 4. 目标场景

下面先列出当前已有的演示能力，再说明接入真实医院时还需补足什么：

| 场景 | 用户示例 | 当前系统处理方式 | 真实医院扩展工作（未实现） |
|---|---|---|---|
| 科室与医生咨询 | 儿科在哪里？有哪些医生？ | `department_info/doctor_info`，查询预置医院目录或知识库 | 接入医院维护的目录与更新流程 |
| 号源与预约 | 明天儿科还有号吗？帮孩子预约 | `slot_query/appointment_create`，查询演示号源并准备确认提案 | HIS 接口、真实身份、医院预约约束与对账 |
| 预约变更 | 查看我的预约，取消这次预约 | `appointment_status/appointment_cancel`，验证绑定后处理演示记录 | 对接真实订单状态及取消规则 |
| 复合问题 | 明天儿科还有号吗？第一次就诊带什么？ | Appointment 主处理，Guidance 补充就诊准备 | 多部门内容维护与人工协作流程 |
| 健康信息 | 症状该咨询哪个科室？这份报告写了什么？ | Triage 提供有限分诊参考和报告预处理说明 | 业务审核、真实接入所需的治理流程 |
| 用药信息 | 这个药的说明书有什么限制？ | Medication 查询有限的已收录说明书内容 | 扩充并审核说明书来源与版本 |
| 升级诉求 | 帮我转人工 | 返回升级标记和引导 | 真实人工队列、工单接收和状态回传 |

当前急症规则命中时走固定紧急响应，优先于普通路由。它是有限规则实现，不能从上述场景表推导出完整临床分诊能力。

## 5. Agent 角色包装

代码中的 Agent 可以用贴近就诊服务的中文名称解释；对外说明仍保留真实类名，便于回到源码核对：

| 代码中的 Agent | 对外角色名 | 职责说明 |
|---|---|---|
| `GeneralAgent` | 通用咨询 Agent | 医院信息、信息澄清和通用服务问题 |
| `GuidanceAgent` | 就诊引导 Agent | 就诊准备、流程和路线查询 |
| `AppointmentAgent` | 预约服务 Agent | 查询号源和预约记录，准备创建/取消提案 |
| `TriageAgent` | 预检分诊 Agent | 有限症状分诊参考与报告信息预处理，不做诊断 |
| `MedicationAgent` | 用药信息 Agent | 查询有限说明书资料及信息边界，不开处方 |
| `EscalationAgent` | 服务升级通道 | 固定响应与升级标记，人工队列接入尚未实现 |

对外表达时，可以把项目描述为：

```text
一个面向就诊服务场景的多角色 Agent 协同演示系统。
```

## 6. 核心处理链路

```text
业务请求
  -> /chat 统一入口
  -> 校验就诊人、用户与就诊会话绑定
  -> 急症规则检查；命中时直接返回固定响应并保存历史
  -> 普通请求读取 Redis 工作记忆、ChromaDB 历史摘要和患者范围内画像
  -> 识别细粒度业务意图、意图组、置信度和紧急程度
  -> 提取科室、医生、日期、时段、地点等结构化实体
  -> 生成结构化路由决策
     - primary_agent
     - supporting_agents
     - routing_reason
     - routing_confidence
  -> 注入历史上下文、结构化实体和匹配的 Skills
  -> 专业 Agent 按需调用工具
     - 查询目录、号源、预约或当前就诊报告
     - search_knowledge_base：查询改写、多子查询召回、去重、重排
     - 准备预约提案：此时不扣减号源
  -> 协同分支返回；编排器合并文字，保留可信工具卡片
  -> 写入完整就诊历史，再更新工作窗口
  -> 后台按规则更新画像等记忆
  -> Monitor 采集成功率、延迟、熔断状态和路由表现
  -> 请求结束；后续可单独运行 Evaluator 评测质量与回归风险
```

这条链路用于理解当前 Agent Runtime 的职责分工。分类器没有结构化症状实体字段，分诊工具从当前用户原文处理症状。RAG 位于 Agent 工具调用阶段，不能画成 `/chat` 在路由前必做的步骤。`EscalationAgent` 使用固定代码响应，不经过普通 Agent 的 Skills 提示词构建。

另有两条独立入口需要一起学习：用户点击提案后，确认接口通过 Redis WATCH/MULTI/EXEC 原子校验与提交号源、预约和回执；报告上传接口执行本地文本提取/OCR，不调用模型，随后聊天才能引用同一就诊会话的报告。业务提交与聊天历史补写并非一个全局事务，重复确认可以返回已有回执并补齐历史。

## 7. 技术能力与业务价值

| 技术能力 | 业务价值 |
|---|---|
| 细粒度意图识别 | 区分科室、号源、预约、导诊、症状、用药、报告和转人工等请求 |
| `intent_group` 归一化 | 同时保留细粒度业务语义和上层路由类别，便于统计和路由 |
| 结构化实体提取 | 提取科室、医生、日期、时段、地点等线索，提供给路由和工具使用；症状由分诊工具处理原文 |
| 按需工具检索 RAG | 专业 Agent 需要知识资料时检索，动态业务状态从业务工具读取 |
| 查询改写与重排 | 尝试扩大召回并调整相关性顺序；效果需由评测验证 |
| 主辅 Agent 路由 | 复合问题有主处理 Agent，也能让辅助 Agent 补充专业意见 |
| 动态 Skills | 就诊引导与信息服务规范可显式重载；固定急症响应与交易校验仍由代码执行 |
| Redis 工作记忆 | 当前会话保持连续性，支持多轮补充信息 |
| ChromaDB 长期记忆 | 支持历史摘要、用户画像和知识库语义检索 |
| MCPToolManager 工具治理 | 当前为进程内管理器，支持超时、熔断、降级；静态知识查询可缓存，动态预约数据不缓存 |
| Monitor 路由降权 | 表现差的 Agent 会被动态降低路由分数 |
| LLM-as-Judge 评测 | 对 Agent 回复质量做自动化评估和回归检测 |
| 就诊隔离与确认提案 | 区分用户、就诊人和会话，显式确认后提交预约，重复确认复用回执 |
| 报告预处理 | 支持粘贴文字、PDF 和图片；保留原文与不确定性供核对 |

表中的业务价值描述的是设计用途，不是已测量的效率提升。例如“减少追问”“提高召回”需要另设对照实验，不能直接换成简历中的百分比。

## 8. 分层能力架构

```text

  用户—就诊人—会话绑定、急症规则前置

  ChromaDB 知识库
  ChromaDB 情景记忆

编排层
  AgentOrchestrator
  primary_agent / supporting_agents

执行层
  GeneralAgent
  GuidanceAgent / AppointmentAgent
  TriageAgent / MedicationAgent / EscalationAgent

治理层
  工具缓存、超时、熔断、fallback
  Monitor 在线观测

  真实认证与授权、HIS 适配、人工工单、生产运营治理
```

## 9. 多 Agent 协同示例

用户输入：

```text
明天儿科还有号吗？孩子第一次就诊要带什么？
```

下面用简化字段演示如何阅读一条可能的路由结果，不是某次真实请求的逐字输出；实际实体、置信度和工具结果以运行记录为准。

系统识别：

```text
intent = slot_query
intent_group = appointment
科室线索 = 儿科
日期线索 = 明天（按 Asia/Shanghai 解释）
辅助线索 = 初诊所需材料
```

领域打分：

```text
appointment = 高
guidance = 中高
general = 低
```

路由决策（节选，不为示意案例虚构置信度）：

```json
{
  "primary_agent": "appointment",
  "supporting_agents": ["guidance"],
  "agent_types": ["appointment", "guidance"],
  "routing_reason": "主要询问儿科号源，同时包含初诊准备问题"
}
```

回复形态：

```text
[appointment - 主处理]
查询真实工具返回的演示号源，并展示可选项；不凭文字承诺预约成功。

[guidance - 辅助处理]
查询就诊准备资料，补充初诊材料与流程说明；资料不足时明确说明。
```

这个例子可以突出三点：

- 系统没有把复合问题粗暴归为单一类别
- 主 Agent 和辅助 Agent 的职责边界清晰
- 路由结果可解释，便于调试和评测

继续追问“帮孩子预约”时，还要核对当前会话绑定的就诊人。Agent 只能准备提案；用户点击确认并通过业务校验后，系统才提交演示预约。这个后续步骤把“回答问题”与“改变业务状态”连接起来，也是本项目值得单独演示的部分。

## 10. 与普通方案的差异

这里以仅做单轮问答的教学示例为比较对象，不代表其他客服产品都缺少这些能力。

| 对比项 | 单轮问答示例 | MediPet 当前基础 |
|---|---|---|
| 问题理解 | 关键词或单轮 prompt | 细粒度意图、意图组、实体、紧急程度 |
| 知识使用 | 直接塞知识库结果 | Agent 按需工具检索，支持查询改写、召回和重排 |
| 上下文 | 只依赖当前 prompt | Redis 工作记忆 + ChromaDB 历史摘要 + 用户画像 |
| 多领域问题 | 容易漏答或答偏 | 主 Agent + 辅助 Agent 协同 |
| 运营规则 | 写在 prompt 中 | Skills 按角色注入并支持显式重载；业务不变量由代码保证 |
| 工具可靠性 | 失败后直接报错 | 缓存、超时、熔断、fallback |
| 质量优化 | 靠人工试用 | Monitor 指标 + 规则断言 + LLM-as-Judge 评测 |
| 可解释性 | 很难知道为什么这么答 | 返回路由原因、置信度和运行指标 |

## 11. 可展示的项目亮点

### 1. Multi-Agent Harness，而不是单 Agent

- 支持主 Agent 和辅助 Agent
- 支持路由原因和路由置信度返回
- 支持复合问题协同处理
- 支持运行状态影响后续路由

### 2. 结合意图按需调用 RAG，而不是无差别检索

- 专业 Agent 根据任务需要调用知识库工具
- 问候不要求预检索；急症固定通道不调用模型或 RAG
- 检索前可做查询改写
- 检索后可做结果重排

### 3. 动态 Skills，而不是硬编码规则

- 通过 Markdown/JSON/TXT 维护处理规范
- 按 Agent 类型和关键词匹配注入
- 支持热加载
- 适合就诊 SOP、分诊信息范围和用药资料边界
- 显式调用 `/skills/reload` 重载；没有文件监听器
- Skills 是提示词约束，不能替代代码中的事务与权限校验

### 4. 分层记忆，而不是临时上下文

- Redis 保存当前会话工作记忆
- ChromaDB 保存历史摘要
- ChromaDB 保存用户画像
- 支持多轮补充、患者范围内历史召回和偏好读取
- 完整就诊历史与临时工作窗口分开保存；切换患者不能串用记忆

### 5. 评测闭环，而不是只看能不能回答

- `/eval/run` 支持端到端评测
- 统计意图识别 Accuracy 和 Macro-F1
- 使用 LLM-as-Judge 评价回复质量
- 输出回归风险和优化建议
- 当前真实模型验收记录仍是候选结果；局部修复复测不能代替全量复测

- 将分层记忆关联到就诊人和会话，分开保存完整历史与临时工作窗口，支持同一患者范围内的历史摘要召回。
- 使用 Skills 管理就诊准备、健康信息和用药说明边界，支持按角色匹配与显式重载，并保留代码级急症拦截。
- 在演示预约流程中实现“查询—提案—显式确认”，以 Redis 乐观事务提交业务状态，复用回执处理重复确认。
- 结合工具轨迹、Monitor、规则断言和 LLM-as-Judge 验证业务行为，记录全量候选与定向复测结果及其适用范围。

### 面试介绍模板

```text
这个项目是在已有多 Agent 项目基础上扩展的就诊服务演示。我学习和复用了意图识别、RAG、分层记忆、路由和评测机制，自己实际负责的部分是 [填写具体模块和验证记录]。

用户请求进入 /chat 后，先校验就诊人和会话绑定，并检查急症规则。普通请求继续读取记忆、识别意图和提取实体，Orchestrator 生成包含主 Agent、辅助 Agent、路由原因和置信度的结构化决策。专业 Agent 根据任务调用业务工具或知识库，并结合匹配的 Skills 回复。系统保存完整历史和工作窗口，运行状态由 Monitor 记录，质量评测则按需单独运行。

我会重点演示一条预约链路：Agent 查询号源并准备提案，用户点击确认后由业务服务提交，重复确认返回已有回执。当前以预置数据验证业务流程；真实认证、HIS 和人工队列是后续扩展方向，尚未实现。
```

## 13. 对外展示建议

### 更适合强调的关键词

- Multi-Agent Orchestration
- Agent Runtime
- RAG with Intent Gating
- Memory-Augmented Agent
- Dynamic Skills Injection
- Tool Reliability
- LLM-as-Judge Evaluation
- Observability-Driven Routing
- Patient-Scoped Memory
- Explicit Confirmation and Idempotent Receipts

### 不建议过度强调的说法

- “完全替代导诊人员或医生”
- “全自动处理所有医疗问题”
- “已接入真实医院 HIS”
- “零配置即可适配任何业务”

更稳妥的说法是：

```text
MediPet 面向门诊服务场景，支持就诊咨询、预约确认、健康信息和多 Agent 协同处理，返回可核查的工具结果与升级标记；真实医院接入和人工队列仍需另行实现。
```
