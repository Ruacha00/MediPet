# MediPet 学习文档

这是一份把项目定位、业务流程、关键代码、使用方式和技术亮点合并后的学习文档。本篇按源码快照 `bb0600c` 校正场景与实现，继续按“先看懂系统，再看懂代码，最后能跑起来”的顺序组织。

## 1. 项目定位

MediPet 是一个面向虚构医院门诊任务的多 Agent 就诊助手与编排运行时。医院、医生、排班、费用都是演示数据，当前不接入真实医院、支付或诊疗系统。

它解决的不是“能聊天”，而是这类真实问题：

- 用户一次说多个诉求，既要查儿科号源，也要知道第一次带孩子来需要什么材料
- 用户信息不完整，需要系统先追问再处理
- 用户要人工导诊或出现预设急症信号，系统要提供明确联系信息或中断普通聊天
- 同一参与者为本人和家属办理，需要把患者、事项和历史分开
- 模型能准备预约方案，但执行必须经过用户明确确认
- 知识库要能接入真实业务规则，而不是只靠模型记忆
- 系统要能评测、监控、降权、回归，形成闭环

从工程上看，它的目标不是单纯堆一个更强的模型，而是把就诊服务系统里最容易出问题的几层拆开处理：

- 先判断“这句话到底在问什么”
- 再判断“该谁来处理”
- 再判断“需不需要查知识库”
- 再判断“要不要补充信息、要不要升级”
- 最后把结果写回记忆和监控系统

这类拆分的意义在于，就诊服务系统真正难的地方往往不是生成回复，而是前面的判断链条。如果前面几步错了，后面模型再强也会答偏。

## 2. 总体架构

```text
用户请求
  -> /chat：读取事项，绑定 user_id / patient_id / conv_id
  -> 共享急症检测
     - 命中：固定响应，跳过普通记忆召回和模型
     - 未命中：MemoryManager 读取工作记忆、情景记忆、画像、摘要
       -> IntentRecognizer 三路融合识别意图、紧急度、实体
       -> AgentOrchestrator 生成结构化路由决策
          - primary_agent / supporting_agents
          - routing_reason / routing_confidence
       -> 调用对应 Agent，注入记忆、实体和匹配 Skills
       -> Agent 按需选择工具，知识工具调用时才进入 RAG
       -> LLM 组织回复；卡片和工具轨迹来自实际工具结果
  -> VisitStore 保存完整历史，再更新工作窗口
  -> 普通聊天安排后台画像更新；急症不压缩、不更新画像
  -> 返回完整 JSON；Monitor 周期观测，Evaluator 单独运行
```

图中的监控和评测是支撑链路，不是每次回答后自动执行完整评测。前端目前没有 SSE 逐 token 输出。完整历史与有限模型记忆也不是同一份数据。

### 2.1 为什么是这个顺序

这个顺序对应的是就诊服务系统最常见的依赖关系：

1. **身份先行、普通路径再取记忆**：先验证事项属于谁，才能读取该患者上下文。没有上下文，很多问题会被误判成新问题；明确急症则先中断，不等待普通模型。
2. **意图优先**：只有先知道用户大概在问什么，才能决定交给哪个角色、需要哪些工具。
3. **事实按需补齐**：业务问题如果完全靠模型回忆，容易出现事实错误。当前由角色按需调用知识工具；号源、预约、药品目录和报告有各自的事实服务，不统一改成 RAG。
4. **路由决策**：不同领域的问题要交给不同 Agent，避免一个 prompt 处理所有场景。
5. **记忆回写**：系统每轮都要把新信息沉淀回去，否则多轮就失真。
6. **监控评测闭环**：没有闭环，系统只能“看起来能用”，不能持续优化。

### 2.2 这个架构和普通 Chatbot 的区别

普通 chatbot 往往是：

```text
用户消息 -> 单一 LLM -> 回复
```

MediPet 是：

```text
用户消息 -> 身份/急症 -> 记忆 -> 意图 -> 路由 -> 工具（含按需RAG） -> 回复/卡片 -> 完整历史与记忆回写
运行统计 -> 周期监控；固定用例 -> 独立评测
```

差别不只是多了几个模块，而是把“回答能力”拆成了几个可治理的能力层。

## 3. 核心业务流程

### 3.1 `/chat` 主链路

入口在 [api/main.py](../api/main.py)，重点看 `chat`、`_load_visit` 与 `ChatRequest`。

当前链路是：

1. 根据服务器生成的事项 ID 读取事项，核对参与者和绑定患者；省略事项 ID 才创建新事项。
2. 检查急症；命中时用固定结果，跳过以下普通记忆和分类步骤。
3. 读取 Redis 工作记忆、Chroma 情景记忆和画像，构造最近对话历史。
4. 做三路融合意图识别，将意图、实体、身份和上下文封装为 `Request`。
5. 生成路由决策，调用主 Agent 或主辅 Agent。
6. 角色按需调用工具；检索、预约查询和报告读取各自返回真实结果，随后组织文字。
7. 先保存完整消息、卡片和轨迹，再写回工作窗口；普通聊天在后台更新画像。

这里有两个关键细节：

- **意图识别在普通 Agent 执行之前**，它提供领域分工与澄清线索；API 已预分类时，编排器不再重复分类。直接调用编排器且没传意图时才补做识别。
- **画像更新是异步的**，因为它属于“延后沉淀”，不应该拖慢用户当前请求；急症不安排画像，工作窗口也使用 `compress=False`。

`user_id` 是参与者，`patient_id` 是就诊人，`conv_id` 是该患者的事项。模型不能从文字改绑身份。当前字符串归属校验是演示机制，不等于生产登录认证。

### 3.2 什么时候切 Agent

- 医院、科室、医生公开信息 -> `GeneralAgent`
- 材料、流程、普通/无障碍文字指引 -> `GuidanceAgent`
- 号源、预约查询、准备创建或取消方案 -> `AppointmentAgent`
- 有限症状方向、报告整理和同事项报告追问 -> `TriageAgent`
- 指定药品说明书与已收录组合警示 -> `MedicationAgent`
- 明确要求人工导诊或预设急症中断 -> `EscalationAgent`

这背后的原则是“按风险和职责切分”：

- 通用 Agent 负责第一层接待，不替其他角色办理预约或给出个人处方。
- 指引 Agent 专注于材料、流程和已有文字路线。
- 预约 Agent 专注于真实号源和待确认方案，没有直接执行确认的模型工具。
- 分诊、药品 Agent 提供有界资料，不诊断、不开处方、不评价其他医生方案。
- 升级 Agent 返回固定导诊资料或急症提示，不声称已经联系真实工作人员。

这样做的好处是每个 Agent 的 prompt 更聚焦，工具边界更清楚，风险更容易核查。症状与报告共用 Triage，没有额外的 ReportAgent。

### 3.3 什么时候并行协作

当一个普通请求同时命中多个领域且满足协作规则时，可以派发多个 Agent，然后由编排器合并结果；急症等优先路径另行处理。

例如：

```text
明天儿科还有号吗，孩子第一次就诊要带什么材料？
```

可能会得到：

- 主 Agent：`appointment`
- 辅助 Agent：`guidance`

这种“主辅协作”比“简单多路并发回复”更像真实业务协作：

- 主 Agent 负责给出主结论
- 辅助 Agent 负责补充另一个领域的证据或限制
- 最终由编排器统一成一段可读回复

它的价值在于，用户不需要自己理解“这是两个模型说的话”，系统会替用户整理成一个结果。

实际用 `asyncio.gather(..., return_exceptions=True)` 并行；`ResponseComposer` 合并成功文字，整合失败时保留主辅原文。卡片独立汇总，同 ID 同内容去重，同 ID 内容冲突则丢弃冲突项并记错；不能用流畅正文遮住失败工具。

### 3.4 什么时候降级

- 专业 Agent 不可用
- 置信度不足
- 请求超出当前角色边界

这些情况处理不同：分类分数不足可能回到 `OTHER` 并澄清；专业角色执行失败可尝试 `GeneralAgent`；明确人工请求或共享急症规则进入 `EscalationAgent`。不是任意失败都会自动转人工。

这一步很重要，因为它避免系统“硬答”：

- 不够确定时，先问必要字段
- 命中预设急症时，返回立即就医和中国大陆120提示；人工导诊只提供联系资料
- 专业 Agent 掉线或失败时，先保底返回通用接待逻辑

比起让系统在不确定场景下胡说，明确降级反而更符合就诊服务场景的边界要求；演示规则未命中不表示临床安全。

### 3.5 什么时候压缩记忆

普通工作窗口达到15条消息时，较早内容会被压缩成摘要（不是15轮对话）：

- 旧消息 -> LLM 摘要
- 摘要写入 Redis
- 压缩生成的情景摘要及身份 metadata 写入 Chroma
- 工作记忆保留最近5条消息，窗口与摘要 TTL 为24小时

当前实现里，患者事实按参与者+患者稳定存储，表达偏好按参与者保存，避免把孩子情况记到家长身上。完整消息另存 VisitStore，不随摘要裁剪；窗口失效后可恢复最近最多20条。

压缩的真正目的不是“省一点字数”，而是防止上下文膨胀之后把高价值信息冲掉。\
就诊服务场景里，最近几轮消息通常最重要，但前面的历史也不能全丢，所以才有“摘要 + 最近若干轮 + 长期画像”的组合。

### 3.6 准备、确认与报告为什么另有入口

预约准备只生成默认15分钟有效的 pending 方案，不预占库存。页面确认调用独立接口，HospitalService 使用 WATCH/MULTI/EXEC 校验归属、当前方案、快照与余量，再保存预约、库存和原回执。重复确认重放原回执，重复取消只恢复一次余量；实现没有 Lua。业务执行后历史写入失败，重试同一方案可补写稳定 ID 的历史，不应另建一次预约。

报告上传走独立的本地提取接口，支持文字/扫描/混合 PDF 和 PNG/JPEG/WebP，10MB、PDF最多10页。Tesseract中英文OCR与参考范围比较不调用模型；原件不持久存储，提取文字和卡片保存在当前事项。后续聊天通过 read_current_report 读取同事项最新报告，可能调用模型解释；不跨患者或事项补取，不从异常数值推断疾病。

## 4. 关键模块

### 4.1 意图识别

文件：`core/intent_recognizer.py`

MediPet 的意图识别不是单模型分类，而是三路融合：

- LLM 语义理解
- Embedding 相似度
- Pattern 关键词匹配

输出包括：

- `intent`
- `intent_group`
- `confidence`
- `source_scores`
- `urgency`
- `entities`

#### 代码里是怎么做的

`recognize()` 里会同时启动：

- `llm_task`
- `emb_task`
- 同步的 pattern 识别

然后用 `_vote()` 融合结果。这样做的好处是：\
LLM 负责语义理解，Embedding 负责模板相似度，Pattern 负责即时兜底，三者互补。模板示例实际插入LLM分类prompt；learn补充模板并清缓存，不是在线训练模型权重。

#### 为什么这样设计

- LLM 负责复杂语义
- Embedding 负责模板相似度
- Pattern 负责不增加模型请求的快速兜底
- 三路并行，减少串行耗时

更具体一点：

- 只有 LLM 时，成本高且容易受提示词波动影响
- 只有 Pattern 时，覆盖窄，稍微换个说法就失效
- 只有 Embedding 时，对细粒度业务边界不够稳定

三路融合的设计目标是让不同错误类型互相补充；是否提高准确率，需要同条件对照验证，不能只凭分支数量推断。

实际正常权重为 LLM/向量/关键词 0.7/0.2/0.1，关闭向量则为0.85/0.15。每个类别累计支持它的“权重×分支分数”。例如 LLM与向量支持号源查询，分别0.9和0.8，关键词以0.7支持医生信息，则号源得0.79，医生信息得0.07。这是算法手算示例，不是实测准确率。

这里有两种不同的向量：当前 Anthropic SDK 无 embeddings 资源，意图分支使用默认256维字符1/2/3-gram哈希与余弦相似度，并非训练过的医学语义向量；知识库由 Chroma 客户端默认 all-MiniLM-L6-v2 计算向量，HTTP模式也在客户端执行。

#### 置信度和降级

识别结果不会无条件相信最高分，而是有阈值控制：

- 分数够高，保留细粒度意图
- 分数不足，回退成 `OTHER`
- 模型失败时，优先由 Embedding 或 Pattern 接管

需要读清 `_vote()` 的实际分支：LLM失败时先用有效非OTHER向量，再用关键词，直接返回，不重新归一化也不经过末尾阈值；正常投票若胜出宽泛类别、具体关键词分至少0.5且融合分低于0.8，会先具体化修正。只有未提前返回的结果才应用默认0.5阈值。这些机制提供降级，不保证永不误路由；confidence不是校准概率。

#### 支持的细粒度意图

下表保留“意图对应什么输入”的学习方式，换成当前医院场景。示例用于理解类别，不保证每个自然语言变体都得到同样预测。

| 意图 | 示例 |
|---|---|
| `hospital_info` | 医院几点开始门诊 |
| `department_info` | 医院有哪些科室 |
| `doctor_info` | 明天有哪些儿科医生出诊 |
| `slot_query` | 明天下午儿科还有号吗 |
| `appointment_create` | 就选刚才列表第一个号，帮我准备预约 |
| `appointment_status` | 查看孩子的预约记录 |
| `appointment_cancel` | 准备取消这条预约 |
| `visit_preparation` | 第一次带孩子来需要什么材料 |
| `visit_process` | 到院后先在哪里报到 |
| `wayfinding` | 从门诊大厅怎么去眼科诊区 |
| `human_handoff` | 我想联系人工导诊 |
| `emergency` | 我现在胸痛、呼吸困难 |
| `symptom_query` | 我30岁，咳嗽流鼻涕，先看哪个科 |
| `medication_query` | 布洛芬200mg普通片的说明书注意什么 |
| `report_query` | 帮我整理这份报告的数值和原参考范围 |

还保留 `query/request/guidance/appointment` 等宽泛类别，以及 greeting、feedback、complaint、escalation、other。`intent_group` 用于归一化分组，不能当作全部细粒度标签。完整枚举在 [IntentCategory](../core/intent_recognizer.py)。

#### 实体提取

当前实体提取是规则优先，不是每轮都让模型抽：

- `department`、`doctor`
- `date`、`period`
- `slot_id`、`appointment_id`（仅提取原文已有标识）
- `origin`、`destination`、`accessibility`
- `selection_index`（一基位置，不是业务ID）

这样做的原因很现实：

- 这些实体非常结构化，规则提取更稳
- 不需要额外 LLM 成本
- 后续路由和工具调用都能复用线索，但仍需服务端验证

“第一个”必须从当前事项最近成功号源列表解析，失败或空列表不可沿用旧选择。日期使用上海业务时钟；缓存键包含消息、有限历史和业务日期，跨午夜不会复用昨天的“明天”。缓存满1000项删最早插入500项，命中不调整位置，并非严格LRU。

#### 紧急度

紧急度分四级：

- `LOW`
- `MEDIUM`
- `HIGH`
- `CRITICAL`

它不只是展示字段，也参与升级逻辑。普通输入通常LOW，投诉默认MEDIUM，人工请求默认HIGH；明确命中共享急症检测时CRITICAL。实际还会匹配紧急关键词，应一起阅读 `_urgency()` 和 `core/emergency.py`。否定、历史描述和一般咨询需排除，预设高烧条件是超过39.5℃，不是普遍临床分级标准。

### 4.2 Agent 编排

文件：`agents/agent_orchestrator.py`

编排器负责：

- 识别意图
- 计算领域分数
- 选择主 Agent 和辅助 Agent
- 执行单 Agent 或并行多 Agent
- 合并响应
- 记录路由原因和路由置信度

#### 路由不是黑盒

`RoutingDecision` 会明确记录：

- 主 Agent 是谁
- 有没有辅助 Agent
- 为什么这样路由
- 当前路由置信度多高

这点在面试里很好讲，因为它说明系统有可检查的路由层。分类、领域路由和同类实例选择是三个步骤：`_domain_scores`叠加意图、关键词、实体分，`_collaboration_targets`找复合诉求，`_best_agent`再选择同类最高运行分数实例。路由分不代表医学正确概率。

#### 当前角色设计

| Agent | 职责 |
|---|---|
| `GeneralAgent` | 公开医院目录与澄清 |
| `GuidanceAgent` | 材料、流程、文字指引 |
| `AppointmentAgent` | 号源、预约记录与待确认方案 |
| `TriageAgent` | 有限症状方向、报告整理与追问 |
| `MedicationAgent` | 指定药品说明书资料 |
| `EscalationAgent` | 固定人工导诊资料与急症提示 |

#### 角色契约

每个 Agent 都有自己的 `AgentProfile`，包含：

- `role`
- `mission`
- `workflow`
- `input_contract`
- `output_contract`
- `handoff_conditions`
- `tool_scope`

这比只靠 prompt 区分角色更可控。

#### Agent 里真正差异化的东西

现在的 Agent 差异不只是 system prompt：

- 输入契约不同
- 输出契约不同
- 工具白名单不同
- 需要的风险边界不同
- temperature 和 max_tokens 也不同

也就是说，它们已经不是“同一个模型换个提示词”，而是不同职责的运行时角色。

### 4.3 工具系统

文件：`agents/tools.py`

工具已集中管理，并按角色白名单暴露：

- 通用工具
- 指引与预约工具
- 分诊、药品与报告工具
- 升级工具
- 共享 RAG 工具

#### 典型工具

- `query_hospital_catalog`（医院、科室、医生和地点目录）
- `search_slots`、`list_appointments`
- `prepare_appointment`、`prepare_cancellation`
- `get_visit_checklist`、`get_wayfinding`
- `triage_symptoms`、`medication_information`
- `preprocess_report`、`read_current_report`
- `search_knowledge_base`

这里列的是模型工具名称；它们的handler再调用相应领域服务。确认不是模型工具，独立HTTP入口是 `POST /appointment-proposals/{proposal_id}/confirm`。

#### 设计要点

- 工具参数有 JSON Schema
- 编排器会做参数校验
- 工具只暴露白名单
- RAG 由有该工具白名单的普通角色共享；Escalation走固定返回路径

#### 为什么要集中到一个文件

工具集中后有三个好处：

1. **更容易审计**：一眼能看到每个工具能做什么
2. **更容易复用**：共享 RAG 不用在多个 Agent 里重复写
3. **更容易控制风险**：不会出现某个 Agent 误调用不该有的能力

#### 工具设计原则

- 工具必须确定性强
- 工具必须尽量可解释
- 工具不伪造外部系统结果
- 工具只返回“可以确认的事实”或“明确的降级结果”

这和就诊服务场景是匹配的，因为这里最怕的是“模型编了一个看似合理但实际不对的操作结果”。

每个角色执行最多3次模型请求，一次可含多个工具；第三次仍要求工具时，没有第四次续问机会。它不是整次聊天的模型调用上限。`AgentTurn`保存本轮trace和卡片，失败前已得到的有效结果也保留；动态号源和个人报告不使用公共知识缓存。

### 4.4 三级记忆

文件：`memory/conversation_memory.py`

当前是三层记忆：

| 记忆层 | 存储 | 作用 |
|---|---|---|
| 工作记忆 | Redis | 当前会话最近消息 |
| 情景记忆 | ChromaDB | 历史对话摘要，支持语义检索 |
| 用户画像 | ChromaDB | 患者明确事实、参与者表达偏好 |

另有 VisitStore 完整历史与最近选择，它是产品事实存储，不是要全部塞进模型的第四层上下文。

#### 当前实现特点

- 普通工作记忆达到阈值会压缩；急症写入显式跳过压缩
- 摘要采用合并更新，不再无限拼接
- 情景记忆先过滤参与者、患者、当前事项，不足时回退同一患者其他事项，不跨家属
- 患者事实按 `user_id+patient_id`，表达偏好按 `user_id` 稳定存储；模型提取内容还需是最近用户原句的子串
- `to_prompt_text()` 只拼最近少量消息，避免上下文过长

#### 为什么要分三层

如果只保留最近对话，系统会忘记用户长期偏好。\
如果只保留长期画像，系统会失去当前上下文。\
如果把所有历史全塞进 prompt，又会触发上下文爆炸。

所以三层记忆本质上是在做“时间尺度分离”：

- 工作记忆管当前轮
- 情景记忆管跨会话线索
- 用户画像管长期偏好

#### 现在的优化方向

以下是可以进一步学习的设计方向，不代表当前全部实现，也不暗示已测得相对提升：

- 摘要更结构化，显式记录“待办、风险、实体、结论”
- 检索加入时间衰减
- 在已有 `patient_facts/preferences` 分别合并、去重并保留最近20项的基础上，增加字段冲突、时效与撤回策略
- 对高价值实体做显式索引

这些方向旨在减少“记住了，但没记对”的问题，实际收益仍需单独验证。

### 4.5 知识库与 RAG

文件：`mcp/tool_manager.py`、`mcp/knowledge_base.py`

知识库链路包括：

1. 查询改写
2. 并行召回
3. 合并去重
4. LLM 重排
5. Top-K 注入上下文

知识库不是独立演示功能，而是通过角色的 `search_knowledge_base` 工具接入 `/chat`。当前不是 API 在每轮路由前调用旧 `_build_knowledge_context()`。`mcp` 是进程内工具管理模块，未实现远程MCP协议服务器。

#### 为什么要先看意图再查知识库

不是所有请求都值得检索：

- 问候、反馈、转人工不需要查
- 材料、报到和医院公开规则可按需查资料
- 动态号源与预约应直接查业务服务，不能拿知识文本当库存

如果所有问题都盲目检索，系统会：

- 增加延迟
- 引入无关上下文
- 让模型被噪声干扰

所以仍应先理解诉求，再决定事实来源。当前的实现是意图影响角色选择、角色按需选知识工具；并不是一个所有业务意图都会触发的 API 检索开关。

#### 工具可靠性设计

RAG 工具不是直接查一下就完了，还加了：

- 参数校验
- 缓存
- 超时
- 熔断
- fallback

这些可靠性机制有必要，因为检索系统也会坏，不能让失败伪装成成功资料。管理器默认30秒超时，连续失败5次熔断、60秒后尝试恢复；静态知识缓存300秒。

多查询保留原问题并最多补3条改写，按chunk_id或内容去重。改写失败留rewrite_error，部分失败留partial/recall_errors；全部失败retrieval_failed与空结果no_results不同。重排索引必须完整、唯一、合法，失败回原顺序，不能始终写reranked=true。

当前24份内置知识有doc_id/title/source_id/source，按约500字切片，ID为doc_id:序号。内置启动同步会更新变化片段、删除该文档过时片段并保留独立上传；普通add/upload是补缺去重，不是同ID覆盖接口。sources只能来自真实返回，不能从模型正文猜。

### 4.6 Skills 动态注入

文件：`core/skill_loader.py`

Skills 用于把就诊服务规范、处理边界、角色约束动态注入到 Agent 的 system prompt。

适合表达：

- 指引 Agent 如何解释材料与文字路线
- 预约 Agent 只准备方案，不能以文字承诺已经执行
- 医疗 Agent 不诊断、不开处方、不评价其他医生方案
- 通用 Agent 先澄清再处理

支持主动热加载，不需要重启服务。六组为general_visit、appointment_assistance、visit_guidance、health_triage、medication_information、service_boundaries。

按enabled、agents、关键词匹配，空关键词对指定角色常驻。修改文件后须POST /skills/reload，没有自动文件监听；单正文约3200字符、总预算默认5000字符。Escalation固定返回，不走Skill prompt，不能用重载改变其输出。

#### Skills 和工具的区别

- **工具**解决“能做什么”
- **Skills**解决“应该怎么做”

比如：

- 工具可以返回实际号源或待确认方案
- Skills 会告诉预约 Agent 不能把“已准备”说成“已预约”，但真正执行边界仍由工具白名单和服务端保证

这个分层很重要，因为它让业务规范可以独立更新，而不必改代码。

### 4.7 Monitor 与降权

文件：`monitor/performance_monitor.py`

Monitor 会采集：

- Agent 成功率
- Agent 平均延迟
- 工具成功率
- 工具平均延迟

并把异常反馈给路由层，影响后续 `routing_score()`。

#### 路由为什么要吃监控结果

因为静态路由不够现实。\
一个 Agent 即使逻辑上最适合，实际在线上也可能出现：

- 成功率下降
- 延迟变高
- 工具依赖异常

Monitor 的作用就是把“运行时健康度”纳入同类实例选择。`routing_score = (成功率×0.7 + 1/(1+平均毫秒/1000)×0.3) × max(0,1-monitor_penalty)`，`_best_agent`取最高分，不是随机抽样。当前每角色默认只有一个实例，降分不会产生新备用实例，也不代表跨域换角色或自动换供应商。MCP工具统计不自动覆盖全部直连业务工具，运行成功率不是医学准确率。

### 4.8 端到端评测

文件：`evaluation/evaluator.py`

评测包括：

- 意图识别 Accuracy
- Macro-F1
- LLM-as-Judge 四维评分
- 回归检测
- 优化建议
- 当前新增真实业务状态断言：库存、身份、回执、卡片、故障路径

LLM-as-Judge 评分维度：

- 相关性
- 准确性
- 完整性
- 有用性

#### 为什么要做这个

如果没有评测，系统优化会变成纯感觉：

- 你可能觉得 prompt 更好了
- 但实际意图识别可能更差了
- 你可能觉得回复更长了
- 但用户体验反而更糟

所以评测是为了把“感觉”变成“指标”。

Accuracy是预测正确数/样本数；每类Precision看“预测为该类的有多少正确”，Recall看“真实该类找回了多少”，F1是二者调和平均，Macro-F1对各类F1等权平均，避免大类掩盖小类。Judge四维0–1平均达到0.75是质量通过条件，不代替业务断言。

Judge只看真实旧上下文、本轮卡片/工具成败/来源、身份与业务时钟，背景存入metadata.judge_context；不传预期断言和未来动作。无效评分、调用失败、Judge失败和跳过单列。场景用独立Redis前缀和Chroma记忆集合；这是编排器与服务链路评测，HTTP和浏览器仍需另外验收。普通运行保存candidate，人工明确复核后才accept_baseline。

#### 适合面试怎么说

可以说：

> 我把意图识别、回复质量和业务状态分别接进评测链路：Accuracy/Macro-F1检查分类，四维Judge检查回复，状态断言检查库存、患者与回执；候选经人工复核后才可作为回归基线。

### 4.9 医疗资料和报告的范围

医疗能力沿用现有角色、工具、知识和Skills扩展点，不另起一个诊疗框架。Triage只在演示医院内科、儿科、眼科中给有限初步方向；“咳嗽3个月”是症状持续时间，不是月龄，年龄不足需澄清。

Medication当前仅收录两个指定美国DailyMed标签：对乙酰氨基酚500mg普通片、布洛芬200mg普通包衣片。不同规格、缓释、复方不能套用这两份标签；未知药物或组合明确未收录，不能推断安全。工具wrapper还检查药名来自用户原话，避免模型截短剂型。儿童、孕哺、肝肾异常、个人剂量等需医师药师核对，不把标签数字变成处方，也不推广为任意国产品牌说明书。

报告只整理原文数值、单位和原参考范围。混合PDF不能因页眉有文字就漏掉扫描正文；OCR低置信度或缺范围时标待核对，不补常见范围、不根据偏高偏低诊断。报告追问通过同事项最新卡片重新读取事实，不依赖摘要里的模糊数字。资料来源和细节见[健康咨询](../docs/health-consultation.md)。

### 6.2 环境准备

核心依赖：

- `ANTHROPIC_API_KEY`

- `MEDIPET_THINKING=disabled`
- `REDIS_URL`
- `CHROMA_HOST`
- `CHROMA_PORT`

- 当前兼容供应商的密钥是否可用，SDK变量名不代表实际调用Claude

- ChromaDB 是否启动

因为这几个组件任何一个缺失，都会影响主链路。

- `/monitor`：运行健康状态

### 6.5 `/chat` 是怎么走的

一次请求里，`/chat` 的关键动作其实是：

1. 先核对患者事项并检查急症；普通路径从memory拿上下文
2. 再从intent recognizer得到结构化判断
3. 再由orchestrator决定主辅Agent
4. 角色按需使用知识库或相应业务工具
5. Agent组织回复，工具提供实际卡片
6. 完整历史先落盘，再写回memory；普通路径安排后台画像

这条链路的重点是：**根据输入、trace和实际状态逐层检查**；回看历史不等于重放有副作用的工具。

### 6.6 调试记忆

如果要排查上下文问题，优先看：

- Redis 工作记忆
- Redis summary
- ChromaDB `medipet_episodic`
- ChromaDB `medipet_profiles`
- 当前事项完整历史与最近成功选择

一般排障顺序是：

1. 先看工作记忆有没有写进去
2. 再看摘要有没有生成
3. 再看情景记忆有没有存成功
4. 最后看画像是否更新

这样能判断问题是在写入、压缩还是检索。普通窗口达到15条才压缩，画像由普通聊天后台任务更新，不应看到空集合就认定失效。

具体自查：先用GET /visits/{conv_id}/messages确认完整历史存在；在隔离测试夹具使该事项窗口失效，再调用get_context，预期恢复自身最近最多20条，含卡片与metadata，不读取家属历史。急症达到阈值仍应零压缩模型调用。参照[test_conversation_memory.py](../tests/test_conversation_memory.py)，不要删除运行数据库来模拟测试。

### 6.7 调试知识库

如果 `/chat` 没有触发知识库：

- 先看路由给了谁、该角色是否有search_knowledge_base白名单
- 再看本轮tool_traces是否真的发起调用，不以旧_should_use_knowledge函数存在推断已调用
- 最后看knowledge_search真实返回的success、sources和错误字段

如果知识库结果不准，通常排查这几个点：

- 查询改写是否偏题
- 召回是否太少
- 重排是否把关键文档压下去了
- 工具回填和后续生成时是否遗漏了已召回资料

具体自查：用POST /search的query/top_k查询字符串单独检索；查看knowledge/stats的total_chunks（片段数不是文档数），逐项核对doc_id、chunk_id、source。测试夹具注入改写失败时，应保留原查询且有rewrite_error；重排重复索引时应回原顺序且reranked=false。普通导入同ID不会覆盖正文；内置文档修改后需重建API触发同步。

### 6.8 调试路由

如果 Agent 选错了，通常看三处：

- `intent_group` 是否正确
- `RoutingDecision.reason`，它在 HTTP 响应中对应 `routing_reason`
- `AgentStats.routing_score()` 是否被降权影响

这比单看最终回复更有用，因为路由问题通常不是在生成阶段出现的。再把“分类错误”“领域选择错误”“同类实例降分”分开：routing_score只解决最后一项。复合输入应查看实际agent_types、slot_list与visit_checklist，而不只看回答同时出现“号源”和“材料”。

### 6.9 评测建议

建议优先跑：

1. 意图识别用例
2. 对话质量用例
3. 业务状态与边界用例
4. 人工接受后的回归基线

这样能比较快定位问题是出在识别、路由还是回复质量。

如果是拿来面试，最好能讲出：

- 哪个指标代表识别能力
- 哪个指标代表生成质量
- 哪个指标代表系统稳定性
- 哪个指标代表回归风险

这样可以说明你不仅会启动系统，也能解释每个指标测了什么。

## 8. 常见问题

### 8.1 为什么不是直接用一个大模型回答

因为真实就诊服务场景里，单模型容易：

- 分流不准
- 上下文断裂
- 无法约束业务边界
- 没法做评测和治理

### 8.2 为什么要有多个 Agent

因为不同业务域的输入、风险边界和工具都不同。

### 8.3 为什么不是把所有能力都塞进一个大 Prompt

因为那样会出现三个问题：

- 角色边界不清
- 工具权限不清
- 出错后难定位

拆成多个 Agent 后，每个角色都可以独立调优、独立评测、独立降权。

### 8.4 为什么要做三层记忆

因为单轮历史不够，长期用户信息也不能每次都塞进 prompt。

### 8.5 为什么要做评测

因为没有评测，就很难知道是模型、路由、知识库还是工具出了问题。

### 8.6 为什么要做监控

因为线上系统不是静态的。模型、工具、知识库、延迟、失败率都会变化，必须有运行时治理。

### 8.7 怎样确认自己已经看懂

按下面顺序在独立测试夹具练习，操作细节可对照[重点代码](重点代码.md)和已有测试。这里是学习任务，不是本次已重新执行的测试记录。

1. 手算LLM与向量支持号源、关键词支持医生信息的0.79/0.07；改成LLM失败，预期直接采用有效向量分，而非重新归一化。
2. 固定上海时钟跨午夜查询“明天”，预期日期与缓存键一起变化；“第一个”仍只是序号，必须解析当前成功列表。
3. 用事件协调两个假Agent，确认同时进入；让Composer失败，预期主辅文字和有效卡片保留。连续工具请求最多3次模型调用。
4. 同一方案确认两次，预期同receipt_id、一次库存变化；模拟历史写入失败后重试，预期补齐稳定ID历史而非新增预约。
5. 本人和孩子各建事项，让窗口失效再恢复，预期只看到自身历史；报告追问只取同事项最新报告。
6. 临时Skill修改后先不reload，再reload并捕获system prompt，预期仅重载后改变；字符串注入成功和真实模型遵守仍需分开证明。

MediPet 的核心不是“会聊天”，而是把就诊服务系统里最关键的几件事工程化了：

- 分配角色
- 调用工具
- 维护记忆
- 接入知识库
- 监控质量
- 量化评测

> 我做的是一个可观测、可评测、可降级的多 Agent 就诊服务编排系统，把意图识别、路由、知识检索、记忆、Skills、监控和评测串成了完整闭环。
