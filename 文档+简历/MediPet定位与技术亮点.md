# MediPet 定位与技术亮点

这份文档面向第一次接触 MediPet 的人，用来快速理解：这个项目是什么、现在的多 Agent 架构是什么、它与“只有 prompt 区分 Agent”的简化方案有什么不同，以及它为什么不只是一个就诊助手聊天 Demo。

## 一句话定位

MediPet 是一个面向门诊就诊与健康信息任务的多 Agent 就诊助手编排运行时。

它不是单个“就诊助手机器人”，也不是简单把几个 prompt 拼在一起，而是一个把意图识别、知识检索、记忆、路由、工具、监控和评测串起来的协同系统。系统先理解用户问题，再决定由哪个 Agent 主处理、是否需要其他 Agent 辅助、是否应该查知识库、是否应该升级到人工，最后再把结果写回记忆和观测系统。

## 它解决什么问题

就诊服务同时涉及信息咨询、跨轮上下文和事务办理，系统需要协调不同角色，并让工具结果与业务状态保持一致。运行数据及接入范围见[运行说明](../README.md#用-docker-compose-启动)，健康信息边界见[健康咨询说明](../docs/health-consultation.md)。

用户常常会同时提到：

- 医院、科室、医生等公开信息查询
- 号源、预约创建、查询和取消等就诊事务
- 材料、报到流程、普通或无障碍文字指引
- 症状的有限科室方向、指定药品标签、报告整理
- 人工导诊、投诉和明确急症提示

如果只用一个缺少明确分工与状态约束的 Agent，容易出现三类问题（这不是单Agent对照实验结论）：

1. **分流不准**\
   预约问题被当成普通咨询，材料要求被只负责查号的 Agent 忽略。

2. **上下文断裂**\
   多轮对话里用户补充科室、日期和选择序号后，系统无法稳定延续；切换本人和孩子时还可能混用事实。

3. **难以迭代**\
   没有评测、监控和规则热更新，项目只能“看起来能聊”，很难持续优化。

MediPet 的目标就是把这些能力做成一条完整链路，而不是只做一个能说话的模型壳子。

## 当前是什么架构

现在的 MediPet 不是“单 Agent + prompt 变体”的做法。\
它当前是一个 **路由驱动的多 Agent 编排架构**，核心形态可以概括成：

```text
意图识别 -> 路由决策 -> 单 Agent / 并行多 Agent 执行 -> 响应合并 -> 记忆回写 -> 监控/评测反馈
```

更具体一点：

- `IntentRecognizer` 先做三路融合意图识别
- `AgentOrchestrator` 基于意图、实体、关键词、运行状态做路由
- `GeneralAgent / GuidanceAgent / AppointmentAgent / EscalationAgent / TriageAgent / MedicationAgent` 不是同一种 prompt 的简单拷贝，而是有各自角色契约、工具白名单、输入输出边界的运行时角色
- 当请求同时覆盖多个业务域时，编排器会并行派发多个 Agent，再由 `ResponseComposer` 合并结果
- Monitor 根据运行表现更新惩罚项，影响同类 Agent 实例的 routing_score；默认每类只有一个实例，不自动训练模型

这意味着，MediPet 的多 Agent 设计重点不是“Agent 数量”，而是**路由、协作、降级和治理**。

## 和之前版本的不同

把“只有 prompt 区分角色”的简化方案作为对照，它更像：

```text
用户消息 -> 一个编排器 -> 几个 prompt 不同的 Agent
```

以下比较用于解释架构层次，不表示本项目发布过这个简化版本。当前实现的关键区别有四个：

### 1. 从“prompt 区分”变成“角色契约区分”

现在每个 Agent 都有自己的 `AgentProfile`，里面不只是角色名，还包括：

- `role`
- `mission`
- `workflow`
- `input_contract`
- `output_contract`
- `handoff_conditions`
- `tool_scope`

这意味着 Agent 的差异不只是“说话风格不同”，而是：

- 接收什么输入
- 产出什么结构
- 能用哪些工具
- 什么情况下必须升级

这些字段使职责更清楚，但稳定性仍须测试。workflow、input_contract 等文字会进入提示；实际工具权限由 tool_scope 和服务校验执行，不能把全部字段理解为强类型工作流引擎。

### 2. 从“单点路由”变成“结构化路由 + 主辅协作”

现在编排器不只是选一个 Agent，而是会生成 `RoutingDecision`：

- `primary_agent`
- `supporting_agents`
- `reason`
- `confidence`

后两项在 HTTP 响应中对应 `routing_reason`、`routing_confidence`。

这允许系统处理复合问题。\
比如“查孩子明天儿科号源 + 告诉我要带什么”，可以由 Appointment 主处理，Guidance 辅助处理，而不是强行塞给一个模型回答。识别器仍输出一个主要意图，复合需求由领域打分和协作规则补充。

### 3. 从“一个 Agent 一套能力”变成“共享工具 + 角色白名单”

现在工具已经集中到 `agents/tools.py`，并且：

- 有共享 RAG 工具
- 有通用工具
- 有材料、流程和文字指引工具
- 有号源、预约查询与方案准备工具
- 有症状、药品和报告只读工具
- Escalation 直接返回固定联系资料，不经过普通模型工具循环

Agent 不再是“看 prompt 自己决定能不能调用什么”，而是显式受工具白名单约束。

### 4. 从“能回答”变成“可治理”

现在系统里有：

- 监控：看成功率、延迟、熔断、工具质量
- 降权：运行差的 Agent 会被路由权重压低
- 评测：意图识别 Accuracy / Macro-F1，回复质量 LLM-as-Judge

这意味着运行表现可以影响同类实例选择；领域分工仍由意图和规则决定。它不是自动学习、自动改写提示词或已经验证的多实例负载均衡系统。

## 核心处理链路

```text
用户请求
  -> /chat：绑定参与者、患者和事项
  -> 共享急症规则：命中则固定响应，不进入普通模型
  -> 普通路径读取 Redis 工作记忆、ChromaDB 历史摘要和患者资料
  -> 识别细粒度意图、意图组、置信度和结构化实体
  -> 生成结构化路由决策
     - primary_agent
     - supporting_agents
     - routing_reason
     - routing_confidence
  -> 单 Agent 执行或并行多 Agent 执行
  -> 注入记忆、结构化实体和动态 Skills
  -> Agent 按需调用 RAG / 医院 / 医疗信息工具
  -> LLM 组织文字，程序独立汇总真实卡片
  -> 写完整事项历史，再更新工作记忆
  -> 普通路径用 BackgroundTasks 更新资料/偏好
  -> Monitor观察运行；Evaluator通过独立手动入口评测，不是每条聊天都评分
```

这条链路的重点不是“流程长”，而是每一步都在解决一个独立问题：

- 记忆解决上下文
- 意图解决分流
- 路由解决主辅协作
- RAG 提供可追溯的资料依据，不能单独保证回答正确
- Skills 解决业务规范
- 监控解决在线健康度
- 评测解决迭代质量

## 核心技术亮点

### 1. 细粒度意图识别

MediPet 不只识别“咨询、投诉、指引、预约”这种粗粒度意图，还支持更贴近业务的细粒度分类。

例如：

| 细粒度意图 | 归一化意图组 | 示例 |
|---|---|---|
| `hospital_info` | `query` | 门诊几点开始？ |
| `slot_query` | `appointment` | 明天儿科有哪些号？ |
| `appointment_cancel` | `appointment` | 帮我准备取消预约 |
| `visit_preparation` | `guidance` | 孩子第一次就诊带什么？ |
| `symptom_query` | `query` | 我36岁，咳嗽两天该看哪科？ |
| `medication_query` | `query` | 查布洛芬200mg普通片的标签 |
| `report_query` | `query` | 整理我粘贴的报告原文 |
| `human_handoff` | `escalation` | 怎么联系人工导诊？ |

这里intent_group是粗分类（query/appointment/guidance/escalation等），不等于六种AgentType。症状、药品和报告的group仍为query，编排器根据具体intent映射到Triage或Medication。

意图识别使用三路融合：

- **LLM**：负责语义理解和上下文判断
- **Embedding / 本地中文语义向量**：负责模板相似度匹配；字符hash保留为明确后备或对照
- **Pattern**：负责关键词兜底

最终输出的不只是 `intent`，还包括：

- `intent_group`
- `intent_confidence`
- `intent_source_scores`
- `urgency`
- `entities`

这让意图识别不只是分类器，而是后续路由、澄清和升级的结构化输入层。

意图主后端为固定BGE中文模型的本地FP32 ONNX，512维、CLS+L2；原256维字符hash仅为显式模式或整路后备，不调用远程embedding。三路正常权重0.7/0.2/0.1，关闭向量0.85/0.15；各后端先过绑定`space_id`的分数/跨类分差门槛，融合分不是校准概率。见[识别器](../core/intent_recognizer.py)与[编码provider](../core/intent_embeddings.py)。API将confidence/source_scores映射为intent_confidence/intent_source_scores，并增加`intent_embedding`诊断。

为什么不是“换个模型名”就完成：模板与查询必须同空间，降级更新`generation`并重算整套模板，结果缓存随空间/模板/校准版本失效。`learn`只改当前实例模板；追加后正常融合保留同空间门槛，但未经新校准不能在LLM故障时独立定类。故障时无冲突的强细粒度关键词优先；语义过门槛且有独立资格才接管，hash还需同类关键词。冲突或证据不足返回OTHER。实际效果须由独立留出与同份LLM输出回放确认，不能从模型名推导。

### 2. 结构化多 Agent 路由

MediPet 的多 Agent 路由不是简单“命中两个关键词就并行”。

当前实现是一个路由驱动的多 Agent 编排架构：

1. 先通过意图识别得到业务方向
2. 再按意图、关键词和实体打分
3. 选出主 Agent
4. 对足够强的其他领域选择辅助 Agent
5. 必要时并行执行并合并结果

系统内部的打分逻辑并不只是“谁像就选谁”，还会考虑：

- 意图类别
- 关键词命中
- 结构化实体
- 当前 Agent 是否可用
- 在线表现和监控降权

#### 现在的路由结构

```text
general
guidance
appointment
escalation
triage
medication
```

主处理 Agent 由 `primary_agent` 表示，辅助 Agent 由 `supporting_agents` 表示。\
如果是复合问题，系统会让多个 Agent 同时工作，而不是强行交给单个模型拼答案。

#### 和之前版本的区别

简化方案更像是“某个 Agent 负责一个 prompt 版本”。\
现在是“多个具备契约和白名单的运行时角色 + 一个可解释的路由层 + 一个结果合并层”。

这两个层次完全不是一回事。

### 3. RAG 知识库增强

MediPet 使用 ChromaDB 构建知识库，用于存放医院流程、材料清单和有来源的医疗知识。当前24份默认文档；动态余号、个人预约和当前报告另由业务工具读取。

检索链路包括：

```text
原始问题
  -> 查询改写
  -> 多子查询并行召回
  -> 合并去重
  -> LLM 重排
  -> Top-K 注入 Agent 上下文
```

但不是所有请求都会触发 RAG。

系统先完成意图与路由，由选中的 Agent 在工具循环中决定是否调用共享检索；没有API统一按意图先检索的步骤。固定急症/人工联系路径不走普通RAG工具循环。Chroma客户端默认all-MiniLM-L6-v2生成知识向量，与意图BGE语义/hash后备不同；本次不重建知识或患者记忆集合。检索失败、空结果与部分成功分别保留状态，不能把降级提示当检索成功。

### 4. Redis + ChromaDB 记忆体系

MediPet 把记忆拆成三层：

| 记忆类型 | 存储 | 作用 |
|---|---|---|
| 工作记忆 | Redis | 当前会话最近消息 |
| 情景记忆 | ChromaDB `medipet_episodic` | 历史对话摘要，支持语义检索 |
| 用户画像 | ChromaDB `medipet_profiles` | 用户偏好和关键实体 |

Redis 读写使用异步客户端，ChromaDB 的同步操作放入线程池，减少主请求链路阻塞。

当前会话消息过多时，系统会压缩旧消息，生成摘要，保留最近几轮对话，避免上下文无限膨胀。

#### 患者范围与完整历史

一个事项固定绑定一位患者。工作窗口24小时TTL，达到15条压缩、保留最近5条；完整历史与卡片另存Redis，不随压缩或归档删除。窗口过期后从当前事项历史恢复；情景召回只可回退到同患者其他事项。报告追问更严格，只读当前事项最新报告。见[记忆说明](../docs/memory-skills.md)。

### 5. 动态 Skills 注入

知识库解决的是“业务事实是什么”，Skills 解决的是“就诊助手应该怎么处理”。

例如：

- 就诊指引需要先核对科室、起终点或材料需求
- 预约必须先准备方案，明确确认后才能执行
- 症状缺信息先澄清，药品只复述明确标签
- 通用就诊助手需要先澄清用户诉求
- 涉及敏感信息时需要提醒用户不要公开密码或验证码

MediPet 支持从 `skills/` 目录加载 Markdown / JSON / TXT 规则文件，并根据 Agent 类型和关键词动态注入到 system prompt。

修改规则后可以通过 /skills/reload 主动热加载，不需要重启服务；不是文件监听自动生效。当前6组Skills，单份正文默认3200字符、总注入预算5000字符。service_boundaries配置匹配六角色；Escalation实际直接执行固定代码，不读取Skill prompt，重载不会改写其固定响应。

### 6. MCP 工具可靠性治理

MediPet 把知识库检索封装成工具，并加入完整的可靠性机制：

- 参数校验
- TTL 缓存
- 超时控制
- 熔断器
- fallback 降级
- 查询改写
- LLM 重排
- 工具成功率和延迟统计

这让工具调用不只是“能调”，还具备可治理、可观测和可降级能力。

这里的MCPToolManager是进程内管理器，没有远程MCP协议服务。静态知识查询配置300秒缓存、默认30秒超时；连续失败5次熔断，60秒后尝试恢复。医院和健康信息工具直连各自服务，不进入公共检索缓存。见[工具链](../docs/tools-rag.md)。

#### 从工具结果到预约与报告

每个角色的工具循环最多请求模型3次，一轮可有多个tool_use；白名单和参数校验后才执行handler。预约只生成pending方案，用户点击 /appointment-proposals/{proposal_id}/confirm 后由医院服务用WATCH/MULTI/EXEC校验并提交；重复确认取原回执，稳定消息ID使历史可重试补齐。

报告的文字/PDF/图片通过本地程序提取，扫描及混合页使用本地Tesseract，不调用云端OCR或视觉大模型；10MB、PDF最多10页。原件不持久保存，提取文字与卡片保存在患者事项历史。后续聊天仍可能向模型提供这些内容。详见[预约](../docs/appointments.md)、[健康咨询](../docs/health-consultation.md)。

### 7. Monitor 在线观测和路由降权

Monitor 会定期采集：

- Agent 成功率
- Agent 平均延迟
- 工具成功率
- 工具平均延迟
- 连续失败次数
- 熔断状态

如果某个 Agent 表现变差，Monitor 会写回 `monitor_penalty`，影响后续 `routing_score`。

也就是说，监控不只是展示指标，还会影响后续同类实例选择分数。默认每类一个实例，不保证有其他实例可切换；没有受控数据证明该机制带来特定比例的性能提升。

### 8. LLM-as-Judge 端到端评测

MediPet 内置 `/eval/run` 评测入口。

评测内容包括：

- 意图识别 Accuracy
- Macro-F1
- 端到端 Agent 回复质量
- LLM-as-Judge 四维评分
- 回归检测
- 优化建议

LLM-as-Judge 会从四个维度评价回复：

- 相关性
- 准确性
- 完整性
- 有用性

这让项目不只是“能回答”，而是能持续评估回答质量。

#### 当前业务与验证边界

Judge四维平均以0.75为通过阈值；调用或评分失败单列，不混入有效均值。实际角色、卡片、库存和患者状态另用业务断言；显式确认由场景动作执行，不能让模型代替用户授权。报告先存`candidate`，人工接受后才作基线；回归比较是相对已接受基线下降超过5%。

U001（2026-09-16）历史完整候选：66条意图全对、30/30质量项、26/27业务组，共57/58结果项。路线提示修复后的原样两轮3/3不能改写成完整58/58，候选未接受。后端684 passed/21 skipped与前端35项属于工程测试；最后提示修复后另有119项定向回归，未重跑全量。见[完整候选](../evaluation/reports/live-20260916-u001/notes.md)与[验收汇总](../docs/internal/updates/U001-health-consultation/evidence/acceptance.md)。

U002 的语义意图专项已有真实向量、真实 LLM 响应和三模式重放证据：单路低重合结果改善，融合持平，故障接受准确率未达门槛，仍不能宣布最终验收。专项不是重新执行整条 HTTP、Agent 工具和 Judge 链路；数字及解释见[指标模板](带数据指标的加强版简历模板.md)。

医疗只覆盖有限症状与演示三科、两个指定美国药品标签和原文报告比较。明确急症规则前置，提示中国120/境外当地急救；否定、历史和知识询问有反例，39.5℃是产品阈值，不是通用诊断标准。

## 为什么它不是普通就诊助手 Demo

普通就诊助手 Demo 通常只有：

```text
用户输入 -> LLM 回复
```

MediPet 则是：

```text
用户输入
  -> 绑定患者事项 / 急症前置
  -> 普通记忆读取
  -> 意图识别与实体提取
  -> 结构化多 Agent 路由
  -> Skills 注入与按需工具/RAG
  -> Agent 回复 + 真实业务卡片
  -> 记忆写入
  -> 画像更新
  -> 监控反馈
  -> 评测回归
```

它更像一个小型的 Multi-Agent Runtime，而不是单轮聊天机器人。
