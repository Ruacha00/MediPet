# MediPet 完整使用指南

本文档说明 MediPet 的部署、启动、API 调用、知识库使用、ChromaDB 数据查看、监控评测和常见排障。依次学习环境准备、接口、业务操作、存储观察、监控评测与排错。

MediPet 是基于明和虚构医院的门诊就诊助手，用于学习和展示。模型解释语言，工具提供事实，确认端点执行事务；默认 anonymous 是演示参与者，不是完整生产认证。

```text
用户请求 → /chat 校验患者事项 → 急症前置判定
  → 普通路径读取记忆 → 三路识别 → 领域/同类实例选择
  → Skills 注入 → 白名单工具（RAG 按需）→ 文字/卡片/轨迹
  → 保存完整历史、更新窗口 → 返回响应 → 普通路径后台画像
```

急症命中时固定 Escalation 响应及120提示，不进入普通模型；预约“询问/方案/执行”分开，聊天说确认不执行预约。患者报告本地处理，不导入公共知识库。

```text
/eval/run → Accuracy/Macro-F1 → 隔离业务断言 → 四维 Judge
  → 与已接受 baseline 比较 → 保存 candidate → 人工复核
```

业务步骤使用 PowerShell；存储章节保留 Bash/容器内 Python 的分步写法，分别注明执行位置。示意 JSON 的 ID、时间和分数不是实测数据。只读存储检查不需要调用模型；不要为了触发压缩连续发送付费聊天。

## 1. 项目结构

```text
api/main.py                     HTTP 与 CLI 入口
api/evaluation_runtime.py        每个评测场景的隔离环境
core/intent_recognizer.py        三路意图识别、实体、版本缓存
core/intent_embeddings.py        本地语义ONNX、字符hash后备与共享编码生命周期
core/emergency.py                普通模型调用前的急症检查
core/skill_loader.py             Skills 加载与匹配
core/llm_utils.py                Anthropic 兼容请求选项
agents/agent_orchestrator.py     六角色、主辅路由、工具循环、整合
agents/tools.py                 角色工具与实际服务接线
hospital/                      医院事实、号源、方案、预约事务
health/                        有界分诊、药品目录、报告提取
memory/visit_store.py           患者、事项、完整历史、选择状态
memory/conversation_memory.py   工作窗口、摘要、情景记忆、画像
mcp/                           进程内工具管理与知识检索
knowledge/                     24 份内置医院和医疗资料
skills/                        6 组场景规则
frontend/                      Vue 页面与 Nginx 同源代理
evaluation/                    用例、评测器和保存的候选证据
monitor/                       统计、告警与性能反馈
tests/                         单元、接口、真实组件及浏览器检查
docker-compose.yml             唯一默认部署编排
```

源码和运行数据分开。Redis、Chroma、API 报告使用命名卷；`.env`、依赖目录、缓存和构建产物不纳入提交。

## 2. 环境准备

### 2.1 必需依赖

安装 Docker 和 Docker Compose v2，并准备自己的 Anthropic 兼容模型配置。完整部署不要求宿主机预装 Redis、Chroma 或 Tesseract。

### 2.2 配置 `.env`

#### 首次准备

需要Docker、Docker Compose、聊天模型可用密钥及已核验的本地意图ONNX资产。资产准备好后Compose运行不要求宿主另装Python、Node或Tesseract；从固定源权重自行准备资产时需下面的独立Python 3.12构建环境。首次镜像构建还会下载运行依赖、系统包和Chroma默认模型，不能把离线运行说成首次构建完全离线。

首次复制配置；已有 `.env` 时保留并编辑：

```powershell
if (-not (Test-Path -LiteralPath .env)) { Copy-Item .env.example .env }
```

在本地文件中填入以下配置。密钥是占位内容，不能直接用于请求：

```dotenv
ANTHROPIC_API_KEY=填写自己的本地密钥
ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic
ANTHROPIC_MODEL=deepseek-flash
MEDIPET_THINKING=disabled
```

代码保留 Anthropic SDK 的 Messages 调用协议，通过 DeepSeek 兼容入口请求 `deepseek-flash`。环境变量名表示协议，不表示实际调用 Claude。`core/llm_utils.py` 将 `MEDIPET_THINKING=disabled` 转换成 SDK `extra_body`，适配分类、查询改写等短 JSON 输出预算；空值保留供应商默认行为，其他非空值会报配置错误。

#### 本地意图模型的首次准备

意图模型不从聊天SDK获取，也不会在请求里下载。已有完整资产时先用verify检查；需要从固定官方源准备时，在仓库根目录使用独立构建环境，避免把torch/transformers装进生产环境：

```powershell
py -3.12 -m venv .scratch/intent-model-build
.\.scratch\intent-model-build\Scripts\python.exe -m pip install -r requirements-embedding-build.txt
.\.scratch\intent-model-build\Scripts\python.exe scripts/prepare_intent_embedding.py download
.\.scratch\intent-model-build\Scripts\python.exe scripts/prepare_intent_embedding.py export --python .scratch/intent-model-build/Scripts/python.exe --evidence .scratch/intent-model-export.json
.\.scratch\intent-model-build\Scripts\python.exe scripts/prepare_intent_embedding.py verify --smoke
```

download获取固定revision；export在已有本地源文件上离线导出；verify核对模型/tokenizer哈希与清单，--smoke只做本地向量编码，不发聊天请求。运行资产在被忽略的data/models/intent/bge-small-zh-v1.5；构建环境和证据在被忽略的.scratch，不提交这些大文件或缓存。

模型身份与预处理以[模型清单](../config/intent_embedding_model.json)为准。重新导出若改变清单/`space_id`，原[校准文件](../config/intent_embedding_calibration.json)不能自动沿用；先核对版本，不手改指纹绕过弃权。镜像构建核验并将模型放在/opt/medipet/models/intent，避免被/app/data卷遮住；应用请求只离线读取。

#### 端口和其他配置

| 配置 | 默认值/作用 |
| --- | --- |
| `MEDIPET_WEB_PORT` | `8088`，页面宿主机端口 |
| `MEDIPET_API_PORT` | `8000`，API 宿主机端口 |
| `MEDIPET_REDIS_PORT` | `6379`，Redis 宿主机端口 |
| `MEDIPET_CHROMA_PORT` | `8001`，Chroma 宿主机端口 |
| `MEDIPET_REDIS_PASSWORD` | 演示默认 `medipet-demo`，数据库与应用必须一致 |
| MEDIPET_INTENT_EMBEDDING_BACKEND | semantic主后端；可显式hash或disabled |
| MEDIPET_INTENT_EMBEDDING_MODEL_DIR | 宿主模型目录；Compose用镜像内/opt/medipet/models/intent/bge-small-zh-v1.5 |
| MEDIPET_INTENT_EMBEDDING_FALLBACK | hash或disabled；故障后在当前provider生命周期保持 |
| MEDIPET_INTENT_EMBEDDING_TIMEOUT_MS | 默认2000，包含排队的向量等待上限，不是聊天模型超时 |
| MEDIPET_INTENT_EMBEDDING_THREADS | 默认2，ONNX CPU线程数 |
| `MEDIPET_SKILLS_MAX_PROMPT_CHARS` | `5000`，动态 Skills 总正文预算 |
| `MEDIPET_COMPOSER_MAX_TOKENS` | `1000`，多角色回复整合预算 |
| `MEDIPET_COMPOSER_TEMPERATURE` | `0.1`，整合温度 |
| `MONITOR_INTERVAL` | `10` 秒，监控采集间隔 |
| `ALERT_WEBHOOK_URL` | 默认空，不发送外部告警 |

Compose 把容器间连接设置为 `redis:6379`、`chromadb:8000`、`api:8000`。宿主机的 Chroma 地址是 `localhost:8001`，不能在容器间照搬。API 数据目录为 `/app/data`，接受基线路径是 `/app/data/eval/baseline.json`。

终端同名变量可能覆盖 `.env`。若当前 PowerShell 继承了旧模型设置，可只清理当前进程环境：

```powershell
Remove-Item Env:ANTHROPIC_API_KEY, Env:ANTHROPIC_BASE_URL, Env:ANTHROPIC_MODEL, Env:MEDIPET_THINKING -ErrorAction SilentlyContinue
```

这不修改系统变量。用 `docker compose config --quiet` 检查配置，不把包含真实密钥的完整配置输出贴入文档或日志。


### 2.3 全栈部署和开发调试的区别

全栈部署会同时启动应用和依赖服务；开发调试仍基于同一 Compose 定义，不再提供另一套手拼 docker run 启动方式。

| 对比项 | Compose 全栈 | 开发调试 |
|---|---|---|
| 网络 | 服务名 redis/chromadb | 宿主机使用127.0.0.1和映射端口 |
| 代码 | 镜像复制，修改后build | 本机源码和测试即时读取 |
| Skills | 只读挂载，修改后reload | 可独立预览匹配 |
| 适用 | 演示、完整页面、联调 | 断点、单元测试、实验夹具 |
| 常见问题 | 初始化/配置失败 | 端口冲突、误用容器主机名、漏装OCR |

只有配置变化时用 force-recreate，代码变化时用 build；restart 不重新读取 .env。

## 3. Docker Compose 全栈部署

```powershell
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose logs --tail 80 api
Invoke-RestMethod http://localhost:8000/health
Invoke-RestMethod http://localhost:8088/api/python/health
```

等待依赖、API 和前端健康，打开 `http://localhost:8088`。默认映射为：

| 服务 | Compose 名称 | 宿主机入口 | 容器端口 |
| --- | --- | --- | --- |
| 页面与代理 | `frontend` | `http://localhost:8088` | 80 |
| FastAPI | `api` | `http://localhost:8000` | 8000 |
| Redis | `redis` | `127.0.0.1:6379` | 6379 |
| Chroma | `chromadb` | `127.0.0.1:8001` | 8000 |

Swagger 是 `http://localhost:8000/docs`，OpenAPI 是 `/openapi.json`。页面通过 `8088/api/python` 访问后端；`8088/health` 不是 API 健康地址。健康响应含status: ok、agents及`intent_embedding`摘要；ok表示应用初始化完成，不证明每个模型请求都成功或语义分支已启用。

```powershell
$health = Invoke-RestMethod http://localhost:8000/health
$health.intent_embedding | Select-Object configured_backend, active_backend, model, space_id, dimension, status, fallback_reason
```

检查实际`semantic_ready`、`hash_explicit`/`hash_fallback`或`disabled_explicit`/`disabled_fallback`。/chat响应的`intent_embedding`另给`top1`/`margin`、accepted、校准状态、truncated和cache_hit；缓存命中不能当作本次推理耗时。未校准时向量弃权，急症则在单次分类的向量初始化/普通模型分支前中断。

独立 Prometheus 默认不开启，需要时使用同一 Compose：

```powershell
docker compose --profile monitoring up -d
```

默认入口为 `http://localhost:9090`；应用内运行统计不依赖该可选服务。

## 4. Compose 环境下的开发调试

开发时先理解“源码”和“已部署镜像”的区别。当前只有一份 Compose 运行定义；不维护旧的独立 docker run 模式，但保留进入容器、CLI、断点、测试和更新代码的学习路径。

### 4.1 查看日志与进入容器

```powershell
docker compose ps
docker compose logs --tail 100 api
docker compose exec api sh
```

容器工作目录是 /app，退出用 exit。不要把直接修改容器作为持久实现，重建后会丢失。

### 4.2 CLI 与能力限制

```powershell
docker compose run --rm api python -m api.main --cli
```

CLI 复用初始化与聊天链路，输出文字并保存默认本人事项；没有患者切换、上传与确认卡片UI。CLI 输入“确认”同样不执行事务。它会调用真实模型，学习内部逻辑优先使用假模型测试。

### 4.3 本机开发依赖与测试循环

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest tests/test_conversation_memory.py -k fake -q
Push-Location frontend
npm ci
node --test tests/*.test.mjs
npm run build
Pop-Location
```

上述记忆测试选择 fake 参数，使用内存存储和替身模型，不发真实模型请求。外部存储测试需显式环境；跳过不代表真实组件已验证。本机OCR需额外安装Tesseract及chi_sim/eng语言包，生产镜像已经安装。

### 4.4 断点与前端联调

宿主 .env.example 指向宿主映射端口；容器使用服务名。若需要独立调试API，可使用不冲突端口：

```powershell
.\.venv\Scripts\python.exe -m uvicorn api.main:app --host 127.0.0.1 --port 8010 --reload
```

另一个终端：

```powershell
$env:MEDIPET_PYTHON_API_URL = 'http://127.0.0.1:8010'
Push-Location frontend
npm run dev -- --host 127.0.0.1
Pop-Location
```

Vite 在5173将 /api/python 代理到上述API。改端口不等于隔离数据；只有准备隔离数据配置后才做写入实验，不把生产患者作为测试夹具。可在 api.main.chat、AgentOrchestrator.run、MemoryManager.get_context 设置断点。

### 4.5 将修改部署到统一环境

```powershell
docker compose up -d --build api frontend
curl.exe -f http://localhost:8088/api/python/health
```

源码测试、前端构建、实际容器验证是三个不同层次。最终演示回到8088页面，不把开发服务的结果冒充生产构建结果。

### 4.5 就诊页面与管理入口（U003）

本节对应 U003 源码；现有 8088 容器不会随源码编辑自动更新。开发预览、生产构建和容器部署应分别核对。

默认首页用于就诊操作：先选择本人或家属，再选择或新建事项。顶栏持续显示当前就诊人和事项；手机宽度下点击“切换”打开列表，Esc 关闭并返回触发按钮。重命名、归档和恢复仍作用于各自事项，完整记录继续由服务端保存。

消息支持列表、强调和表格排版，宽表格在自身区域横向滚动；原始 HTML 不执行，模型提供的远程图片不加载。当前事项的来源名称保留在回复下方，完整来源编号、工具轨迹和回执详情在“管理与调试 → 运行与请求详情”中查看。

上传报告按钮可用键盘访问，支持 PDF、PNG、JPEG、WebP，最多 10 MB；PDF 页数与识别结果由服务端校验。输入框支持 Ctrl/⌘ + Enter 发送，中文输入法正在选字时不触发发送。快捷示例只填入草稿。切换事项保存本标签页内的草稿，刷新记录不覆盖草稿；关闭或刷新整个网页不承诺保存未发送内容。阅读旧消息时新增结果提供“有新消息 · 查看最新”，不强制跳走。

预约仍经过查号、选号、准备方案、卡片显式确认和服务端回执；取消也需单独准备并确认。若确认请求中断，卡片显示“结果待核对”并暂时阻止重复提交，使用“刷新记录”读取权威回执。未拿到匹配回执时不能把网络错误理解为预约未执行；没有自动重试或客户端猜测成功。

“管理与调试”包含“知识与场景规则”“评测报告”“运行与请求详情”和 API 文档。首页不预加载知识、规则、监控或评测数据；进入相应管理页才读取。进入评测页不会自动运行评测，返回就诊保留当前事项、草稿和阅读位置。管理入口是页面分层，不提供新的权限认证。

## 5. Swagger 和接口总览

PowerShell先设置 `$Api = "http://localhost:8000"`；本章只介绍单接口，完整连续业务在第6章。

MediPet 基于 FastAPI 构建，启动 HTTP 服务后可以直接在浏览器访问 Swagger UI 调用接口。

本地 Swagger 地址：

```text
http://localhost:8000/docs
```

网页经8088同源代理访问API；Swagger请直接使用8000/docs。

打开 Swagger 后，可以点击任意接口右侧的 **Try it out**，填写参数后点 **Execute** 直接调用本地服务。常用调试顺序：

```text
1. GET /health                确认服务是否就绪
2. POST /chat                 测试主对话链路
3. GET /knowledge/stats       查看知识库是否已有数据
4. POST /knowledge/upload     上传演示知识库文件
5. POST /search               测试知识库检索、查询改写和重排
6. GET /monitor               查看 Agent 和工具运行指标
7. GET /skills                查看当前已加载 Skills
8. POST /skills/reload        修改 Skill 文件后热加载
9. GET /metrics               查看 Prometheus 指标文本
10. POST /eval/run            运行端到端评测
```

### 5.1 接口总览

| 方法 | 路径 | 参数位置 | 作用 | 适合场景 |
|------|------|----------|------|----------|
| `GET` | `/health` | 无 | 健康检查，返回服务状态和 Agent 统计 | 启动后确认服务可用 |
| `POST` | `/chat` | JSON Body | 主对话接口，完成记忆读取、意图识别、Agent 路由、回复生成、记忆写入 | 业务主链路 |
| `GET` | `/monitor` | 无 | 查看 Agent/工具统计、告警和优化建议 | 观察在线表现 |
| `GET` | `/metrics` | 无 | 暴露 Prometheus 指标文本 | Prometheus 抓取和排查监控 |
| `POST` | `/search` | Query 参数 | 执行知识库检索优化链路：查询改写、并行召回、合并去重、LLM 重排 | 测试 RAG 检索 |
| `GET` | `/skills` | 无 | 查看当前加载的 Skills、适用 Agent、关键词和解析错误 | 确认动态规则是否生效 |
| `POST` | `/skills/reload` | 无 | 运行时重新扫描 Skill 目录 | 修改业务规范后无需重启 |
| `POST` | `/knowledge/add` | JSON Body | 批量导入文档到 ChromaDB 知识库 | 程序化导入文档 |
| `POST` | `/knowledge/upload` | Form File | 上传 `.txt`、`.md`、`.json` 文件导入知识库 | 手动上传知识库文件 |
| `GET` | `/knowledge/stats` | 无 | 查看知识库文档片段总数 | 确认知识库是否有数据 |
| `POST` | `/eval/run` | 可选 JSON Body | 运行内置或自定义意图识别和端到端对话评测 | 演示 LLM-as-Judge 评测 |
| `GET` | `/docs` | 浏览器访问 | Swagger UI | 浏览和调试所有接口 |
| `GET` | `/patients` | user_id查询参数 | 当前参与者患者 | 身份选择 |
| `GET/POST` | `/visits` | 查询参数/JSON | 列出/创建事项 | 连续业务 |
| `PATCH` | `/visits/{conv_id}` | JSON | 标题/归档/恢复 | 事项管理 |
| `GET` | `/visits/{conv_id}/messages` | user_id查询参数 | 完整历史 | 刷新恢复 |
| `POST` | `/appointment-proposals/{proposal_id}/confirm` | JSON | 确定性确认 | 创建/取消 |
| `POST` | `/reports/preprocess` | multipart | 本地PDF/图片提取 | 患者报告 |
| `GET` | `/trace/tool/{request_id}` | 路径参数 | 真实调用轨迹 | 请求排错 |

### 5.2 Skills 动态能力加载

Skills 是可热加载的业务规则文档，用来把医院公开信息、预约、就诊指引、有限医疗规则动态注入对应 Agent 的 system prompt。知识库回答“业务事实是什么”，Skills 约束“怎样处理、何时澄清、哪些承诺不能做”。


```powershell
$Api = 'http://localhost:8000'
Invoke-RestMethod "$Api/skills"
Invoke-RestMethod "$Api/skills/reload" -Method Post
```

| 目录 | 注入范围 |
| --- | --- |
| general_visit | General 的医院相关关键词 |
| appointment_assistance | Appointment 常驻 |
| visit_guidance | Guidance 常驻 |
| health_triage | Triage 常驻，含报告边界 |
| medication_information | Medication 常驻 |
| service_boundaries | 配置覆盖六角色；普通角色常驻注入，Escalation 由固定代码保证边界 |

修改流程：保存原文件 → 保留 frontmatter → 修改一项可验证表达规则 → reload → 核对解析错误/字符数 → 发新请求核对实际效果 → 恢复文件并再次 reload。Compose 将宿主机 skills 只读挂载到 API；页面没有规则文件编辑器。Escalation 直接返回固定响应，不读取 Skill prompt，修改并重载规则不会改变它的固定内容。

frontmatter 的 `name/description/keywords/agents/enabled` 决定名称、说明、匹配词、角色和启用状态。空 keywords 表示该角色常驻，不是从不匹配。正文受单项约 3200 字符和总计默认 5000 字符预算限制，应把关键规则放前面。加载成功不证明模型每次遵循；Skill 也不能修改工具权限、身份或确认事务。


当前 skills/general_visit/SKILL.md 的头部示例：

```yaml
name: 医院公开信息
description: 查询明和虚构医院的科室、医生、地点和门诊说明
keywords: 医院,科室,医生,门诊,儿科,眼科,内科
agents: general
enabled: true
```

实际文件以三条短横线包围头部，后接Markdown正文。name是标题，description用于摘要，agents限定角色，keywords决定消息匹配，enabled控制启用。空关键词对指定角色常驻；不能因此增加工具权限。6.6给出完整匹配/不匹配/重载步骤。

### 6.1 主对话接口

以下辅助函数只负责编码和发送。确认步骤分开列出，避免把演示脚本误当成自动办理：

```powershell
$Api = 'http://localhost:8000'
function Send-MediPetJson {
    param([string]$Path, [hashtable]$Body, [string]$Method = 'Post')
    $json = $Body | ConvertTo-Json -Depth 30
    Invoke-RestMethod -Uri "$Api$Path" -Method $Method `
        -ContentType 'application/json; charset=utf-8' `
        -Body ([Text.Encoding]::UTF8.GetBytes($json))
}
```


```powershell
$patients = Invoke-RestMethod "$Api/patients?user_id=anonymous"
$patients.items | Format-Table patient_id,name,relationship
$child = $patients.items | Where-Object patient_id -eq 'patient_child'
if (-not $child) { throw '未返回该患者，请先检查患者列表。' }

    user_id='anonymous'; patient_id=$child.patient_id; title='儿童门诊教程'
}
$conv = $visit.conv_id
Invoke-RestMethod "$Api/visits?user_id=anonymous&patient_id=$($child.patient_id)&archived=false"
```

`POST /visits` 返回 HTTP 201，Visit 字段为 `user_id/patient_id/conv_id/title/archived/created_at/updated_at`。保存服务产生的 `conv_id`。给 `/chat` 传自造的不存在 ID 会得到 404；只有省略该字段才创建新事项。


```powershell
$reply = Send-MediPetJson '/chat' @{
    message='查明天儿科的号，顺便告诉我第一次带孩子来要带什么。'

}
$reply.response
$reply.artifacts | ConvertTo-Json -Depth 30
$reply.tool_traces | ConvertTo-Json -Depth 30
```

请求只包含 `message/user_id/patient_id/conv_id`；message 必填，user_id 默认 anonymous。已有事项上的 patient_id 若提供，必须与绑定患者一致。当前字符串归属检查用于本地演示，不是生产登录认证体系。

| 返回字段 | 用途 |
| --- | --- |
| `conv_id/patient_id/visit` | 实际事项与患者，后续请求沿用 |
| `response` | 生成文字，不是事务凭据 |
| `artifacts` | `{id,type,data}` 数组，data 按卡片专属模型校验 |
| `intent/intent_group` | 小写细粒度意图与归一化分组 |
| `agent_type/agent_types` | 主返回角色与实际参与角色 |
| `primary_agent/supporting_agents` | 主辅分工 |

| `knowledge_used` | 是否实际成功调用共享知识检索 |

### 6.4 预约业务示例

#### 查询与准备

```powershell
$slots = ($reply.artifacts | Where-Object type -eq 'slot_list' | Select-Object -First 1).data.slots
$slot = $slots | Where-Object remaining -gt 0 | Select-Object -First 1
if (-not $slot) { throw '没有可用号源，请重新查询。' }
$prepared = Send-MediPetJson '/chat' @{
    message="请为当前就诊人准备预约，号源编号：$($slot.slot_id)"
    user_id='anonymous'; patient_id=$child.patient_id; conv_id=$conv
}
$proposal = ($prepared.artifacts | Where-Object type -eq 'appointment_proposal' | Select-Object -First 1).data
if (-not $proposal -or $proposal.status -ne 'pending') { throw '没有有效待确认方案。' }
$proposal | ConvertTo-Json -Depth 30
```

方案含身份、`proposal_id/operation/target_id/snapshot/status/created_at/expires_at/result`。费用 `fee_fen` 单位为分。快照来自真实号源，模型不能提交自造价格和医生资料。


#### 明确确认

核对上一段输出后，单独执行以下请求，它会创建演示预约：

```powershell
$confirmed = Send-MediPetJson "/appointment-proposals/$($proposal.proposal_id)/confirm" @{
    user_id='anonymous'; conv_id=$conv
}
$confirmed.receipt | ConvertTo-Json -Depth 30
```

确认请求不接受患者覆盖、价格、库存或方案快照，也不请求 LLM。返回契约为：

```text
user_id, patient_id, conv_id
receipt:
  receipt_id, proposal_id, operation, status="executed"
  appointment:
    appointment_id, user_id, patient_id, conv_id, snapshot
    status="active" 或 "cancelled", created_at, cancelled_at
  executed_at
artifacts: 实际结果卡片
```

重复提交同一方案时 receipt_id 应相同。实现使用 Redis `WATCH/MULTI/EXEC` 乐观事务，检查库存后更新业务事实；没有 Lua 实现。历史消息另用 WATCH 和稳定 `message_id` 去重。响应丢失时保留原方案 ID，不另造方案当成“重试”。


#### 取消同一预约

```powershell
$appointmentId = $confirmed.receipt.appointment.appointment_id
$cancelReply = Send-MediPetJson '/chat' @{
    message="请准备取消预约，预约编号：$appointmentId"
    user_id='anonymous'; patient_id=$child.patient_id; conv_id=$conv
}
$cancelProposal = ($cancelReply.artifacts | Where-Object type -eq 'appointment_proposal' | Select-Object -First 1).data
$cancelProposal | ConvertTo-Json -Depth 30
```

核对 `operation=cancel` 和目标后再确认：

```powershell
$cancelled = Send-MediPetJson "/appointment-proposals/$($cancelProposal.proposal_id)/confirm" @{
    user_id='anonymous'; conv_id=$conv
}
$cancelled.receipt.appointment.status
```

应为 cancelled。生成取消方案不代表已取消。

### 6.7 分诊、药品与急症

为本人新建事项，再尝试：

| 输入 | 需要核对 |
| --- | --- |
| “我30岁，咳嗽流鼻涕两天，想先挂什么科？” | triage_guidance 的科室理由、缺失信息、来源，不确诊 |
| “30岁，眼睛发红发痒两天，想看什么科？” | 有界规则与现有科室；严重信号不能按普通预约处理 |
| “查询布洛芬200mg普通片的禁忌和说明书用法。” | medication_info 的明确剂型、资料分节、来源和核对日期 |
| “我还在服用华法林，可以一起用吗？” | 实际合并用药警示；未收录药不能因此被视为安全 |
| “布洛芬缓释胶囊呢？” | 不套用普通片标签，明确未收录或要求核对 |

药品目录只收录对乙酰氨基酚 500 mg 普通片与布洛芬 200 mg 普通包衣片的两个指定美国标签。可展示说明书数字，但不计算个人剂量、不开处方、不替代手中产品说明书。未知药、不同规格/剂型、儿童、孕哺或肝肾异常交由医师或药师核对。

急症是前置路径。有限的当前呼吸困难、胸痛、意识异常表达及**超过 39.5℃**的演示条件优先提示立即就医，中国大陆拨打 120。API 在普通记忆召回和意图模型前检查；固定回复保存历史时不压缩、不更新画像，相关测试验证零普通模型调用。恰好 39.5℃ 不应被写成一定命中该数值条件。一般咨询、否定、过去经历和引用有反例规则；未命中不表示安全。这是工程演示规则，不是普适医学阈值。



### 6.8 报告文字、PDF和图片


#### 粘贴文字

```text
请整理以下报告：
白细胞 6.2 x10^9/L 4.0-10.0
C反应蛋白 8 mg/L 0-5
```

粘贴进入 `/chat`，由 Triage 的 `preprocess_report` 工具处理当前原话，仍有模型理解与答复。比较只使用原文数值、单位及闭合范围，不上网补范围。`within/below/above` 只是与原报告范围的关系；缺字段、异常格式或疑似 OCR 字符为 `unassessed`，不是疾病判断。


#### 文件上传

页面入口对应 **POST `/reports/preprocess`**，不是知识库上传。准备自己的合成 `report.pdf` 后，在 PowerShell 用原生 curl.exe：

```powershell
curl.exe -sS -X POST "$Api/reports/preprocess" `
    -F "file=@report.pdf;type=application/pdf" `
    -F "user_id=anonymous" -F "patient_id=$($child.patient_id)" -F "conv_id=$conv"
```

此例使用前面的孩子事项，上传前应确认报告归属。PNG/JPEG 可换为相应文件和 MIME。file 必需，user_id 默认 anonymous；已有事项必须存在且可写。

文件最多 10 MiB，PDF 最多 10 页，单图/渲染页最多 1600 万像素，文字最多 100000 字符。每页 OCR 10 秒、总工作进程 120 秒，同时最多两个工作进程。损坏、加密、假扩展名、多帧图片、空内容与超限均有明确错误。

纯文字 PDF 用 pypdf；扫描页、含图片的混合页用 PDFium 渲染，再由本地 Tesseract 中英文识别。混合页即使有文字页眉也识别图片正文，同时保留准确文字层，将 OCR 补充标为未校对，只去除完全相同行。低置信度时数值全部待核对。不调用外部 OCR 服务或视觉模型。

响应含 `user_id/patient_id/conv_id/visit/response/artifacts/extracted_text/input_kind`。报告卡为：

```text
type = report_summary
data:
  title, summary, input_kind: text | pdf | image
  extracted_text
  observations[]:
    item, value, unit, reference_range
    flag: unassessed | below | within | above
    raw_line
  warnings[], sources[]
```

上传预处理不请求大模型、不修改号源选择。原件处理后不持久保存，**提取文字和卡片仍保存到事项完整历史**，显示为“报告整理”。原件不保留不等于内容不保存。


#### 上传后追问

发送“请核对这份报告里哪些项目超出原参考区间”。`read_current_report` 先验证身份，再读取同一事项最新报告卡，不凭摘要补数值，不跨事项回退。刷新后记录仍可读取。

切换另一患者并新建事项后重复询问，应要求上传/粘贴或明确未找到，不能显示前一患者卡片和数值。安全澄清不一定需要调用一个失败工具。报告范围异常不能直接推导疾病或触发自动治疗。

```powershell
}
```

返回 `message/added_chunks/total_chunks`。文本按约 500 字分片，以 doc_id 和片段序号生成稳定 ID。普通导入是补缺/去重，**不是同 ID 覆盖更新接口**，不能依据重复上传成功就宣称旧正文已替换。


### 7.3 上传文件导入知识库

知识文件使用 UTF-8 txt/md/json。JSON 顶层是数组，不带 documents 包装：

```json
[
  {"doc_id":"tutorial-upload-v1","title":"上传示例","content":"仅供演示的公开知识。","source_id":"tutorial","source":"合成资料"}
]
```

保存为 tutorial-knowledge.json，再上传：

```powershell
curl.exe -sS -X POST "$Api/knowledge/upload" -F "file=@tutorial-knowledge.json;type=application/json"
```

知识 API 限制 10 MB，普通 Nginx 路径的请求体限制可能更小，大文件调试直接走 8000；报告专用路径单独允许 11 MiB 以容纳 multipart 边界。知识上传按文本处理，不进行 PDF/图片 OCR。患者报告不能导入共享公开知识集合。


### 7.4 检索知识库

```powershell
Invoke-RestMethod "$Api/knowledge/stats"
$query = [Uri]::EscapeDataString('儿童首次就诊需要带哪些材料')
Invoke-RestMethod "$Api/search?query=$query&top_k=3" -Method Post
```

`total_chunks` 是片段数，不是文档数；当前内置 24 份资料。POST `/search` 的 query/top_k 位于查询字符串，不是 JSON。它可调用模型做改写和重排。

结果字段包含 `query/results/reranked/success/error/error_code/rewrite_error/rerank_error/recall_errors/fallback_used/partial`。条目有 `chunk_id/doc_id/title/source_id/source/content/score/chunk`。距离转换分不是答案准确率。空结果、全部失败、部分召回成功和重排降级要分别看。


检索无匹配结果的完整结构示意（不是本次实际响应）：

```json
{"query":"示意问题","results":[],"reranked":false,"success":false,"error":"检索没有匹配结果","error_code":"no_results","rewrite_error":null,"rerank_error":null,"recall_errors":[],"fallback_used":false,"partial":false}
```

先检查 `success/error_code`，再检查 `results` 各片段的 `source/source_id/doc_id/chunk_id`，不能把 HTTP 200 当作检索业务成功。`/search` 没有独立 `sources` 字段；聊天知识工具的 trace 才另有来源汇总。

### 7.5 内置知识如何更新

`knowledge/*.md` 随镜像发布，修改后重建 API。启动时按内置 doc_id 更新正文/元数据，移除该文档失效的旧片段，不变内容不重复嵌入，保留其他上传资料。医院事务初始化仍只补缺，不恢复已消耗库存。

普通聊天并非每次先做 RAG；角色实际调用 `search_knowledge_base` 才进入检索。号源、事务、药品目录和报告分别走真实服务，不通过公共知识缓存决定业务事实。

## 10. Redis 工作记忆查看

Redis不只保存窗口，还保存医院事务、患者事项、完整历史和选择上下文。先确认键的职责，再解释TTL。

进入API容器运行Python，使用容器已有REDIS_URL而不打印密码：

```python
import os, json, redis
r = redis.Redis.from_url(os.environ['REDIS_URL'], decode_responses=True)
print(r.ping())
user_id, patient_id, conv_id = 'anonymous', 'patient_self', '替换为真实事项ID'
wm = f'medipet:wm:{user_id}:{patient_id}:{conv_id}'
summary_key = f'medipet:summary:{user_id}:{patient_id}:{conv_id}'
print('keys:', list(r.scan_iter(match=f'medipet:wm:{user_id}:{patient_id}:*', count=100)))
print('type:', r.type(wm), 'length:', r.llen(wm), 'TTL:', r.ttl(wm))
```

使用SCAN限定当前演示患者，而不是KEYS *遍历所有用户。Redis CLI等价命令（连接信息按自己的环境配置，不把密码写进教程截图）：

```redis
TYPE medipet:wm:anonymous:patient_self:实际事项ID
LLEN medipet:wm:anonymous:patient_self:实际事项ID
LRANGE medipet:wm:anonymous:patient_self:实际事项ID 0 -1
TTL medipet:wm:anonymous:patient_self:实际事项ID
```

TTL正数表示剩余秒数，-2表示不存在，-1表示无过期。工作窗口正常写入会续期86400秒；完整历史不应因此24小时后消失。

Python逐条查看内容和顺序：

```python
raws = r.lrange(wm, 0, -1)
for raw in reversed(raws):
    row = json.loads(raw)
    print(row['role'], row['content'], row['ts'])
    print('metadata:', row.get('metadata', {}))
```

Redis LPUSH最新消息在前，源码 `_get_working_memory` 用reversed还原时间顺序。卡片可能出现在metadata；完整历史仍以GET /visits/{conv_id}/messages为准。上传或确认会失效窗口，下一次普通读取从完整历史恢复，不能把暂时没有wm键解释成丢失预约。

## 11. 查看工作记忆压缩内容

工作记忆压缩发生在memory/conversation_memory.py。默认规则：

```text
WORKING_MAX = 20
COMPRESS_AT = 15
旧消息 → 模型摘要 → Redis summary
同一摘要 → ChromaDB medipet_episodic
最近5条 → Redis wm
完整事项历史 → 保持原样
```

条数是消息数，不是用户轮数。普通用户和助手各写一条；某次用户追加触发压缩后，紧接着助手追加，观察时可能看到6条而不是恰好5条。急症入口compress=False，即使达到阈值也不触发摘要模型。

### 11.1 查看 Redis 中的会话摘要

沿用第10章当前患者、事项与r：

```python
print('summary TTL:', r.ttl(summary_key))
print('summary:', r.get(summary_key))
```

Redis CLI等价语句：

```redis
GET medipet:summary:anonymous:patient_self:实际事项ID
TTL medipet:summary:anonymous:patient_self:实际事项ID
```

摘要存储也有86400秒TTL。源码合并旧摘要与新摘要，最多800字符；没有摘要、摘要失败占位和成功摘要是三种不同事实。

### 11.2 查看压缩后仍保留的最近5条工作记忆

```python
raws = r.lrange(wm, 0, -1)
```

压缩取messages[:-5]生成摘要，保留messages[-5:]。这不代表完整历史仅剩5条；用HTTP历史再比对消息总数。若此前发生确认/上传，窗口恢复也可能触发压缩，需要同时看历史和请求顺序。

### 11.5 Redis summary 和 ChromaDB episodic 的区别

| 存储 | 目的 | 读取方式 | 保留边界 |
|---|---|---|---|
| Redis wm | 当前有限窗口 | 身份键+列表 | TTL24小时，压缩裁剪 |
| Redis summary | 当前事项合并摘要 | 身份键GET | TTL24小时、字符上限 |
| Chroma episodic | 相关历史摘要 | 身份过滤+向量查询 | 持久化、可同患者回退 |
| VisitStore完整历史 | 页面、卡片、回执恢复 | 用户与事项校验 | 不随模型压缩删除 |

摘要不能替代预约库存、原报告或执行回执；模型上下文里“曾经有号”不意味着现在可预约。

## 13. 运行端到端评测

默认是 66 条意图、15 组对话、12 组边界。完整运行会实际调用模型，单独执行并保存：

```powershell
curl.exe --max-time 1800 -sS -X POST http://localhost:8088/api/python/eval/run -o medipet-eval-candidate.json
```

页面“管理与调试 → 评测报告 → 运行评测”也是一次默认请求。精确代理等待 1800 秒，普通聊天仍 180 秒。超时不证明服务未运行，先查日志与候选文件，不立即重复点击。

只做一个自定义分类样本时，明确把其他组设空数组；省略或 null 会加载该默认组：

```powershell
$small = Send-MediPetJson '/eval/run' @{
    intent_cases=@(@{message='你好'; expected_intent='greeting'})
    dialog_cases=@(); boundary_cases=@()
}
$small | ConvertTo-Json -Depth 60
```

这仍会调用分类模型，不是静态检查。对话项可用 question 或 turns，支持身份、固定 clock、前置条件、断言。setup/between_turns/after_turns 是明确的场景操作，确认由评测器执行，不转成让模型擅自确认的指令。完整示例位于 `evaluation/cases/*.json`。

读报告顺序：

1. 看 run_id、模型、输入 hash、metadata.case_counts 与代码证据。
2. 分开看意图 Accuracy/Macro-F1、四维 Judge 和有效质量数。
3. 看业务失败、调用失败、Judge 失败、skipped 及逐项卡片/trace。
4. total/passed/pass_rate 是结果项，不是 93 个输入的统一准确率。
5. 看 baseline_status 与人工复核记录，不能因分数高就自动接受。

普通运行保存 `/app/data/eval/candidates/{run_id}.json`，默认 Compose 使用 api-data 命名卷，不对应宿主机 `./data/eval`。只有显式 `accept_baseline(report, reviewed_by=...)` 才保存接受基线；目前没有用户 HTTP 接受端点。此方法要求填写非空复核者标识，不执行身份认证或 HTTP 验收。候选未接受不自动等于测试失败，仍须分别检查断言、指标和人工复核。前一次候选不会自动成为基线。刷新页面不自动重新加载磁盘报告，文件仍保留。

U001 历史证据：后端 **684 passed / 21 skipped**，前端 **35 passed**；完整真实模型 **66/66 意图、57/58 结果项**，一项旧路线续问失败保留。修复后仅原样两轮定点 **3/3**，未重跑全量 58 项，不能写成全量 58/58。层次不同、子套重叠，不能相加。新旧候选均未自动接受。详见[验收汇总](../docs/internal/updates/U001-health-consultation/evidence/acceptance.md)与[完整候选](../evaluation/reports/live-20260916-u001/notes.md)。


### 13.1 读懂多轮用例

完整场景含id、patient_id、clock、turns、preconditions、assertions，可包含setup、between_turns、after_turns。显式选择、确认等用户动作由评测器执行，不交模型猜测。默认组由evaluation/cases加载。

例如只检查两轮公开咨询，其他组必须为空：

```json
{"intent_cases":[],"dialog_cases":[{"id":"tutorial-public","patient_id":"patient_self","clock":"2026-09-16T10:00:00+08:00","turns":["医院有哪些科室","儿科门诊在哪里"]}],"boundary_cases":[]}
```

这是自定义质量示例，没有声明业务assertions，不能据通过得出预约闭环正确。完整业务例子应阅读仓库固定cases，保留其setup和断言，不删失败项凑通过率。

### 13.2 报告完整字段

```json
{"timestamp":"示意时间","total":0,"passed":0,"pass_rate":0.0,"avg_scores":{},"regressions":[],"recommendations":[],"results":[],"run_id":"示意运行ID","metadata":{},"judge_failures":[],"call_failures":[],"skipped":[],"candidate_path":"示意候选路径","accepted_by":null}
```

这是空结构示意，不是可接受基线。results每项有test_id、passed、scores、detail、metadata；metadata中的实际业务事实用于核查Judge是否漏判。Judge失败不进入有效质量均值，业务失败不能被高语言分覆盖。

U002 的语义意图专项另由 [evaluation/semantic_intent.py](../evaluation/semantic_intent.py) 采集排名、保存 LLM 响应并做重放，与上述业务端到端报告分开。学习时直接阅读[冻结对照记录](../docs/internal/updates/U002-semantic-intent/evidence/calibration/implementation.md)和[逐例融合结果](../docs/internal/updates/U002-semantic-intent/evidence/calibration/holdout-semantic-fusion.json)，不必再次调用模型。先核对实际后端和证据有效性，再区分原始向量 Top1、融合准确率、故障接受准确率与覆盖率；证据有效不代表效果达标。各项分母和口头解释见[指标模板](带数据指标的加强版简历模板.md)。

## 14. 停止、重启和清理

```powershell
docker compose stop
docker compose up -d
docker compose restart api
docker compose up --build -d --force-recreate
```

分别是暂停、再启动、重启 API、更新代码后重建。修改 `.env` 后应执行 `docker compose up -d --force-recreate --no-deps api`，重新创建 API 容器以加载新环境；仅 `restart` 不会更新容器环境。`docker compose down` 删除容器与网络但保留命名卷。日常操作不需要删除卷或清空资料。

确实要重新开始演示，先停写入，预览目标，再单独执行：

```powershell
docker compose stop api frontend
docker compose run --rm --no-deps api python -m scripts.reset_demo
# 核对预览后才执行下一行
docker compose run --rm --no-deps api python -m scripts.reset_demo --execute
docker compose up -d
```

删除范围是 medipet:* Redis 键和三个精确 Chroma 集合，包含事项、预约、报告派生历史、导入资料与记忆。其他前缀/集合、数据卷及评测文件保留；下次启动补回默认事实与知识。始终对同一 Compose 项目执行，不能混用主项目和验证项目。


仅停止保留卷：docker compose stop；删除容器但保留卷：docker compose down。不要把down -v作为常规重启或排错步骤，它会删掉历史、预约和候选。清理教学采用上面的定向预览/执行，必须知道当前Compose项目与数据卷。

## 15. 常见问题

### 15.1 `/health` 返回503

```powershell
docker compose ps
docker compose logs --tail 100 api
```

先判断API是否反复重启，再核对初始化异常、模型配置变量来源和依赖健康。health检查编排器就绪，不代表某次付费模型调用已成功。若直接8000健康但8088同源失败，继续看frontend日志与代理，不要重新导入数据库。

### 15.2 ChromaDB连接失败

```powershell
docker compose ps chromadb
docker compose logs --tail 100 chromadb
curl.exe http://localhost:8001/api/v1/heartbeat
docker compose exec api python -c "import chromadb; print(chromadb.HttpClient(host='chromadb',port=8000).heartbeat())"
```

宿主失败优先核对映射端口；容器失败优先检查服务名与网络。两者成功但集合为空，再确认实际集合名和当前Compose项目。MemoryManager可能使用本地降级存储，看启动日志，不能拿宿主本地目录解释独立Chroma卷的数据。

### 15.3 Redis认证失败

比较Compose使用的MEDIPET_REDIS_PASSWORD与运行配置，不输出密码。容器API可用已加载REDIS_URL测试：

```powershell
docker compose exec api python -c "import os,redis; print(redis.Redis.from_url(os.environ['REDIS_URL']).ping())"
```

应输出True。失败先分认证错误、连接拒绝、服务名无法解析；修配置后重建容器配置，restart不读取新env。不要禁用认证掩盖配置问题。

### 15.4 `/search` 没有结果

```powershell
curl.exe http://localhost:8000/knowledge/stats
docker compose logs --tail 100 api
```

依次核查：`total_chunks` 是否为0 → 第9章直接召回是否有内容 → `/search` 的 `success/error_code/partial` → `rewrite_error/rerank_error` → `results` 中每个片段的 `source/source_id/doc_id/chunk_id`。`sources` 是聊天知识工具 trace 的汇总，不是 `/search` 响应字段。没有结果与全部检索失败不同；若需要导入，先确认公开资料，再用第7章明确写入接口，不要默认清库。

### 15.5 用户画像查不到

1. 检查用户是否在当前患者事项明确表达资料，而不是只由助手说过。
2. 普通/chat响应后才执行后台更新；急症不安排画像。
3. 查看日志“就诊资料与表达偏好已更新”或“更新用户画像失败”。
4. 按9.6查询patient和participant两个稳定ID，核对scope。
5. 若模型输出不是用户原句子串，会被过滤；空记录不必然是存储异常。

### 15.6 情景记忆查不到

1. 用10章LLEN/TTL和11.1摘要检查当前窗口。
2. 达到15条消息才压缩，不是每轮都写Chroma；普通完整历史不依赖这一触发。
3. 看“工作记忆压缩完成”与“存储情景记忆失败”日志。
4. 查询必须同时过滤用户、患者、事项，检查是否选错事项或数据项目。
5. 需要复现时运行11.2隔离fake夹具，不循环调用真实/chat。

### 15.7 新业务错误怎样继续定位

| 现象 | 核查与处理 |
| --- | --- |
| 页面不可用、502 | 看 compose ps 及 api/frontend 日志，核对同源前缀与宿主端口 |
| health 503 或 API 重启 | 查看初始化日志、Redis/Chroma 健康、模型配置；先修启动失败 |
| health ok但向量是`hash_fallback` | 查看`fallback_reason`，核对模型目录、资产哈希、线程与等待配置；修复后重建provider/重启，不把hash结果记为真实语义结果 |
| 向量`uncalibrated`或accepted=false | 核对`space_id`和校准文件，区分未校准、分数不足、跨类分差不足；不降低阈值或改hash伪装通过 |
| 模型构建缺资产 | 按2.2准备并verify本地固定模型，运行请求不会替你下载 |
| `learn`后故障时不再独立用向量 | 当前实例模板已偏离校准快照；正常融合保留，同空间重新校准前独立接管关闭 |
| 模型认证失败 | 检查终端变量是否覆盖 .env，修配置后执行 `docker compose up -d --force-recreate --no-deps api`，不打印密钥 |
| 改写 JSON 解析失败 | 检查 disabled 是否生效及 rewrite_error，保留原问题降级证据 |
| 事项 404 | conv_id 是否真实存在、是否连错项目，不手造已有事项 ID |
| 403 identity_conflict | 切到正确用户/患者/事项，不绕过归属检查 |
| 409 状态冲突 | 看 detail.code、归档、当前方案、余量，重新读取状态 |
| 410 proposal_expired | 重新查号和准备，不继续确认旧方案 |
| 422 | 区分字段校验数组、业务错误对象、文件格式问题，修输入 |
| 确认后错误 | 检查原方案与回执，重试同一 ID 补历史，不另造预约 |
| 报告 413/415/422 | 查大小、页数、像素、扩展名、加密和损坏，不改后缀冒充格式 |
| OCR 408/503 | 查超时、忙碌、语言包；缩小文件或等资源，不补造识别结果 |
| PDF 只读到页眉 | 核对运行镜像是否含混合页修复，查看完整提取文字与 OCR 分区 |
| search 无结果 | 分清 no_results、retrieval_failed、partial；看总片段数和实际来源 |
| 改 Skill 无效果 | 检查 reload、角色、关键词、预算和解析错误；新请求验证 |
| 画像/情景为空 | 是否执行普通后台更新或压缩，是否按正确患者过滤 |
| 评测超时 | 检查专用 1800 秒代理，先查运行与候选，再决定是否重新运行 |

业务错误通常在 `detail:{code,message,retryable}`；FastAPI 参数错误可能是 detail 数组，部分管理接口仍是字符串。前端应保留错误信息，不能全部改写成网络失败。

## 16. 推荐验证流程

按原来的“先启动、再业务、再管理、最后评测”顺序，不用一个脚本自动执行全部付费和写入操作。

1. docker compose up -d --build，然后分别检查8000/health和8088/api/python/health。
2. 页面读取患者，创建明确的演示事项；保存服务返回ID。
3. 按6章聊天、查号、材料、方案；只有明确核对后才确认创建/取消。
4. 刷新查看完整历史，核对卡片、回执和患者隔离。
5. 分诊/用药仅使用有限目录；报告验证文字、PDF、图片提取和原文，不推断疾病。
6. GET知识统计，按9章只读看集合，确认公开知识与个人报告分离。
7. GET Skills并做本地匹配正反例，只有发布规则时reload。
8. 查看monitor和request_id轨迹，检查失败与实际来源。
9. 用10—11章只读观察或fake夹具理解TTL、压缩和恢复。
10. 需要模型评测时单独确认范围，运行一次并保存完整`candidate`，人工复核后才考虑接受。

U001 历史已记录后端684 passed/21 skipped、前端35项与构建通过；真实全量57/58与路线定点3/3是不同运行，不能相加，也不能声称重新全量58/58。U002 意图专项已有冻结对照，但故障接受准确率未过门槛，最终业务验收仍未完成。源码检查、假模型、真实存储和真实模型证据应分别说明，专项数字见[指标模板](带数据指标的加强版简历模板.md)。
