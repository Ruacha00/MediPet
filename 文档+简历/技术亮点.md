# MediPet 技术亮点

本文档按原有亮点顺序，对照“当前代码真实实现”增量修订，重点说明 MediPet 为什么不再是“单 Agent + prompt 变体”，而是一个**路由驱动的多 Agent 就诊助手运行时**。

当前链路不是先写答案再补能力，而是先做结构化判断，再决定谁来处理、能用哪些工具、要不要并行、是否升级、最后如何回写记忆和监控。

文中的“我”是面试表达示例，只能在本人实际负责对应部分时使用；沿用与增量、职责填写见[简历包装](简历包装.md)。

## 先看结论

| 能力 | 关键模块 | 价值 |
|---|---|---|
| 三路融合意图识别 | `core/intent_recognizer.py` | 让路由建立在结构化判定上，而不是关键词猜测 |
| 路由驱动的多 Agent 编排 | `agents/agent_orchestrator.py` | 支持主 Agent、辅助 Agent、升级 Agent 协作 |
| 共享工具 + 角色白名单 | `agents/agent_orchestrator.py`、`agents/tools.py` | 工具可复用，但调用边界可控 |
| 路由后的按需 RAG | `api/main.py`、`mcp/tool_manager.py`、`mcp/knowledge_base.py` | 只在该搜的时候搜，减少噪声 |
| 三层记忆 | `memory/conversation_memory.py` | 兼顾短期上下文、跨轮线索和长期偏好 |
| 动态 Skills 注入 | `core/skill_loader.py` | 业务规则可热更新，不用每次改代码 |
| 在线监控与路由降权 | `monitor/performance_monitor.py` | 把运行时质量反馈回路由层 |
| 端到端评测 | `evaluation/evaluator.py` | 支持意图识别和回复质量的持续回归 |

## 总体架构

```text
用户请求
  -> api/main.py：校验患者与事项，先检查共享急症规则
  -> 普通路径 MemoryManager.get_context()
      - Redis 工作记忆
      - ChromaDB 情景记忆 medipet_episodic
      - ChromaDB 患者资料/偏好 medipet_profiles
  -> IntentRecognizer.recognize()
      - LLM Few-shot
      - Embedding 相似度
      - Pattern 规则
      - 输出 intent / intent_group / source_scores / urgency / entities
  -> AgentOrchestrator.run()
      - 路由到主 Agent
      - 必要时并行调用辅助 Agent
      - 升级场景交给固定响应 EscalationAgent
      - 普通角色在工具循环中按需调用业务/医疗/RAG
  -> ResponseComposer
      - 合并多 Agent 输出
  -> VisitStore.append_messages()：完整历史与卡片
  -> MemoryManager.add_message()：工作窗口
  -> 普通路径 BackgroundTasks / MemoryManager.update_profile()
  -> PerformanceMonitor记录运行；EndToEndEvaluator由独立/eval/run触发
```

## 亮点一：三路融合意图识别

**文件**：`core/intent_recognizer.py`

### 解决的问题

就诊助手路由最怕两件事：

1. 把“取消预约”误判成“查询预约”
2. 把“查号源 + 就诊材料”这种复合问题拆错

如果只靠关键词，鲁棒性差。只靠 LLM，成本高、延迟高、行为不稳定。MediPet 的做法是把三种方法一起用：

- `LLM` 负责语义理解和上下文判断
- `Embedding` 负责和模板样本做相似度匹配
- `Pattern` 提供无模型请求的关键词兜底和具体类别匹配

### 具体怎么做

`recognize()` 会并行启动 LLM 和 Embedding 识别，Pattern 同步执行，最后通过加权投票合并：

- LLM 权重最高
- Embedding 负责补足常见表达
- Pattern 负责兜底和细粒度意图纠偏
- 未走具体类别修正且低于阈值时回退到 `OTHER`

正常权重LLM/向量/规则为0.7/0.2/0.1；关闭向量为0.85/0.15。意图主后端为本地BGE中文语义ONNX，原256维字符1/2/3-gram哈希保留显式对照/故障后备；聊天与Chroma知识模型各自独立。融合分不是校准概率。

实现见[编码provider](../core/intent_embeddings.py)：固定资产与预处理组成`space_id`，模板与查询必须同空间；降级整路重算模板，不混新旧坐标。缓存绑定完整清洗消息、最近三条完整历史、上海日期及空间/模板/校准版本；共享只负责编码的provider，`learn`与分类缓存属于各识别器实例。

semantic/hash各按类别`top1`与跨类`margin`过门槛才贡献分数。LLM失败时强细粒度关键词优先，但多个强规则或强规则与可独立语义冲突都拒绝；语义独立接管还需模板未变及非受控省略句，hash须有一致细粒度关键词。`learn`保留同空间门槛参与正常融合，新增模板未经校准前不获得独立接管资格。这些是实现机制，不是已证明的准确率提升。

#### 一个投票演算例子

以下数值仅为算法演算，不是实测置信度，并假定向量已通过本后端门槛：LLM给slot_query 0.8，模板给slot_query 0.9，规则给visit_preparation 0.75。正常融合得到slot_query为0.7×0.8+0.2×0.9=0.74，visit_preparation为0.1×0.75=0.075，因此主要意图取slot_query。原消息若明确还要材料，编排层仍能加入Guidance；不需要把投票结果改成多标签分类器。

### 输出不只是 intent

最终输出的是结构化结果，不是一个分类标签：

- `intent`
- `intent_group`
- `confidence`
- `source_scores`
- `urgency`
- `entities`

其中 `entities` 会规则抽取：

- `department`、`doctor`
- `date`、`period`
- `selection_index`
- `origin`、`destination`、`accessibility`

这些是查询线索，不是患者授权；实际字段以[识别器](../core/intent_recognizer.py)的_extract_entities为准。患者由事项绑定，号源ID由业务列表校验。

这让后面的路由、升级、知识检索都可以直接消费结构化信息。

### 紧急度怎么来的

紧急度是 4 级：

- `LOW`
- `MEDIUM`
- `HIGH`
- `CRITICAL`

规则来源有两层：

- 共享急症规则识别有限当前肯定信号，返回CRITICAL；API先于普通记忆、分类和模型调用中断
- 普通路径另按紧急措辞、人工请求或投诉等规则分级，不把每个“紧急”都当医疗诊断

急症固定提示明确中国120/境外当地急救，仍保存完整历史与窗口；compress=False避免压缩，且不调度画像。包含否定、历史、假设和知识询问反例；超过39.5℃是产品触发条件。见[急症源码](../core/emergency.py)。

### 面试时怎么讲

> 我没有把意图识别做成单一分类器，而是做成了三路融合。LLM 负责语义，Embedding 负责相似度，Pattern 负责高精度规则兜底。最后输出的不只是 intent，还包括 intent_group、source_scores、urgency 和 entities，直接给后续路由和升级使用。

## 亮点二：路由驱动的多 Agent 编排

**文件**：`agents/agent_orchestrator.py`

### 和早期版本的区别

用早期常见的简化设计作对照（不是本项目发布历史），它更像：

```text
用户消息 -> 一个编排器 -> 几个只改 prompt 的 Agent
```

现在不是。当前版本是：

```text
意图识别 -> 路由决策 -> 主 Agent / 辅助 Agent / 升级 Agent
           -> 可能并行执行 -> ResponseComposer 合并
           -> 结果写回记忆 -> Monitor 反馈路由
```

这意味着多 Agent 的差异不只在 prompt，而是体现在：

- `AgentProfile`
- 工具白名单
- 输入/输出契约
- 路由逻辑
- 运行时统计
- 监控反馈

### 角色契约怎样落地

AgentProfile保留role、mission、workflow、input_contract、output_contract、handoff_conditions、tool_scope。前几项作为模型提示，工具范围由程序执行。源码[BaseAgent._build_system_prompt](../agents/agent_orchestrator.py)拼装规则，[get_tools](../agents/agent_orchestrator.py)限制可用handler；不要把文字workflow称为通用DAG。

### 当前有哪些角色

默认有 6 类角色：

- `GeneralAgent`
- `GuidanceAgent`
- `AppointmentAgent`
- `EscalationAgent`
- `TriageAgent`：有限症状方向、报告预处理与同事项报告读取
- `MedicationAgent`：两个指定药品标签

其中 `EscalationAgent` 负责固定急症提示和可复制的人工联系摘要，不发送工单，不声称工作人员已收到。

### 为什么 `pool` 是 list

`_pool: Dict[AgentType, List[BaseAgent]]` 这里用 `list`，不是因为现在就有很多实例，而是为了支持：

- 同角色多实例扩展
- 同类型不同模型配置
- 在线表现差异化路由
- 后续压测、灰度和降级

当前默认每类只有 1 个实例，但结构已经预留了横向扩展能力。

### 路由怎么做

路由不是纯关键词，主要看这些信号：

- 意图类别
- 紧急度
- 结构化实体
- 领域关键词
- Agent 在线表现

对于复合问题，系统会给出 `primary_agent` 和 `supporting_agents`，然后并行执行。

先用`_domain_scores`与_collaboration_targets选领域，再用_best_agent在同领域实例中选最高routing_score。后者为“成功率×0.7 + 延迟分×0.3”再乘监控惩罚因子，不会改变领域权限。并行异常可保留，文字整合失败时回退已有文本；卡片单独汇总，不让整合模型重写预约事实。

### 面试时怎么讲

> MediPet 的多 Agent 不是 prompt-only。现在每个角色都有自己的契约、工具边界和路由位置，复杂问题还能主辅协作并行处理，运行表现还会反馈到下一轮路由里。

## 亮点三：共享工具体系 + 角色白名单

**文件**：`agents/agent_orchestrator.py`、`agents/tools.py`

### 解决的问题

就诊助手 Agent 不能“什么都能调”，否则会出现两个问题：

- 能力边界失控
- 工具重复定义，维护成本高

### 当前实现

工具被统一抽象成 `AgentToolSpec`，再按角色注入。Agent 调用工具时会做：

- 白名单检查
- JSON Schema 参数校验
- 异步执行支持
- 调用结果回填给模型

### 有界循环、预约确认与医疗工具

每个角色最多3次模型请求，一轮可包含多个tool_use；不是整次聊天最多3次。AgentTurn单独保留本轮卡片和trace，避免共享实例串结果。工具参数不能覆盖Request绑定的患者。

预约先准备pending，按钮POST /appointment-proposals/{proposal_id}/confirm才进入[HospitalService.confirm_proposal](../hospital/service.py)的WATCH/MULTI/EXEC。准备不扣库存；事务核对方案、选择、患者、库存等状态，重复确认取原回执。历史在事务后写，失败可用同一回执和稳定消息ID补齐，再失效工作窗口，不能说是跨Redis/Chroma的全局事务。

Triage使用原文与有限规则给科室方向、读取同事项最新报告；Medication仅查两个指定美国标签，未收录药品、剂型和组合不推断安全。上传另走本地PDF/图片处理：10MB、PDF最多10页，扫描与混合页OCR；原件不保留，文字和卡片保存。见[健康说明](../docs/health-consultation.md)与[接口测试](../tests/test_report_upload_api.py)。

#### 从一条选择消息追到执行事实

教学示意：用户对当前号源列表说“选第一个”，模型调用prepare_appointment，参数只有selection_index=1。handler从Request取得患者/事项，服务读取该事项真实SelectionState并生成pending卡片，此时库存不变。随后用户按钮请求confirm接口；事务成功才出现appointment_record和receipt。用例应分别断言“准备后无预约”和“重复确认只有一条预约”，而不是只检查回答包含“成功”。实际字段与状态见[业务模型](../hospital/models.py)和[API闭环测试](../tests/test_demo_workflow.py)。

### 当前分层

- 通用工具
- 材料与文字指引工具
- 号源、预约查询和方案准备工具
- 症状、指定药品标签与报告只读工具
- Escalation使用固定代码，不走普通工具循环
- 共享 RAG 工具

### 设计意义

- 普通模型角色可复用RAG；Escalation固定响应不调用它
- 但每个 Agent 仍然只能调用自己的能力范围
- 避免“一个 prompt 换个身份就能乱调工具”

### 面试时怎么讲

> 我把工具做成统一的工具层，再按角色做白名单控制。这样能力可以共享，边界又不会失控，工程上比把工具写进各自 prompt 里更稳。

## 亮点四：意图路由后的按需 RAG

**文件**：`api/main.py`、`mcp/tool_manager.py`、`mcp/knowledge_base.py`

### 解决的问题

不是所有问题都适合检索。

- 问候、闲聊、转人工，不需要查知识库
- 就诊流程、材料和公开医疗资料适合检索；动态库存与个人预约必须直接查业务服务

### 当前链路

```text
用户消息
  -> 先做意图判断
  -> 路由到相应角色
  -> Agent按需调用search_knowledge_base
  -> 改写 / 并行召回 / 去重 / 重排后回填tool_result
```

### 为什么这样做

- 减少无效检索
- 避免把无关文档塞进上下文
- 降低回答被知识噪声干扰的概率

### 工程特征

原问题加最多三个改写查询；片段按稳定ID去重，重排索引需完整有效。改写失败回原问题，重排失败保留原顺序；no_results、partial、retrieval_failed与真实来源独立记录。MCPToolManager为进程内管理器，没有远端MCP协议服务器。静态检索300秒缓存、默认30秒超时、连续5次失败熔断/60秒恢复；动态患者业务不走此缓存。

知识由Chroma客户端默认all-MiniLM-L6-v2嵌入，与意图BGE语义/hash后备分开；24份默认文档按稳定ID同步、删除同文档旧片段并保留用户上传。见[工具与RAG](../docs/tools-rag.md)。

检索层不是简单向量搜索，而是围绕真实就诊助手链路做的工具化设计：

- 查询改写
- 并行召回
- 合并去重
- fallback
- 缓存
- 熔断

### 面试时怎么讲

> 我把RAG作为角色可选工具：意图帮助分工，Agent决定是否检索。资料查询可做改写、并行召回和重排，动态预约仍直接查业务服务。设计目的是减少无关上下文；是否提升召回，需要独立对照测试。

## 亮点五：三层记忆管理

**文件**：`memory/conversation_memory.py`

### 解决的问题

就诊助手对话既要记住当前轮，又不能把所有历史都塞进 prompt，还要保留跨会话偏好。

### 三层记忆

- **工作记忆**：Redis，保存当前会话最近消息
- **情景记忆**：ChromaDB `medipet_episodic`，保存压缩摘要
- **用户画像**：ChromaDB `medipet_profiles`，保存长期偏好和稳定实体

### 当前实现特点

- 工作记忆达到阈值会自动压缩
- 摘要不是简单拼接，而是合并更新
- `to_prompt_text()` 拼接摘要、有限最近消息、患者范围内情景与资料、当前选择状态
- 患者资料按参与者/患者隔离，表达偏好按参与者保存；模型提取值还要核对用户原句子串

### 患者隔离和过期恢复

工作窗口24小时TTL，达到15条压缩并保留最近5条；完整事项历史另存Redis，不随压缩删除。过期后从当前事项最近历史恢复，不重放预约。情景召回只能回退到同患者的其他事项；报告事实只读当前事项最新卡片。Redis为异步客户端，Chroma同步访问通过asyncio.to_thread移出事件循环。

### 为什么要分层

因为三种信息的时间尺度不同：

- 当前轮是短期上下文
- 历史摘要是跨轮线索
- 用户画像是长期偏好

放在一个窗口里，效果通常会互相干扰。

### 面试时怎么讲

> 我把记忆拆成工作记忆、情景记忆和用户画像三层，分别对应当前轮、跨轮线索和长期偏好。这样既控制上下文长度，也保留了跨会话连续性。

## 亮点六：动态 Skills 注入

**文件**：`core/skill_loader.py`

### 解决的问题

知识库回答的是“事实是什么”，Skills 约束的是“应该怎么处理”。

比如：

- 症状先核对必要年龄和描述，缺信息先澄清
- 预约只能准备方案，不能用聊天措辞替代按钮确认
- 药品要保留用户明确的剂型/规格，未知组合不能推断安全
- 涉及隐私和安全时要避免让用户暴露敏感信息

### 当前实现

Skills 支持热加载，常见格式包括 Markdown、JSON、TXT。系统会按以下条件决定是否注入：

- Agent 类型
- 用户消息关键词
- `enabled` 开关

### 注入预算与实际生效

单份Skill正文默认3200字符、总预算5000字符。当前6组：general_visit、appointment_assistance、visit_guidance、service_boundaries、health_triage、medication_information。/skills查看加载状态，/skills/reload主动更新后续请求；无自动文件监听。service_boundaries配置覆盖六角色，但Escalation固定代码不读取prompt，不能靠改Skill改变它。

### 为什么重要

业务规范可以独立更新，不需要每次都改主代码。

### 面试时怎么讲

> Skills 解决的是行为边界和处理规范，不是事实问答。它和知识库分工不同，而且可以热更新，业务规则调整时不需要改代码主链路。

## 亮点七：Monitor 在线观测与路由降权

**文件**：`monitor/performance_monitor.py`

### 解决的问题

多 Agent 系统不能只在设计时看起来合理，还要在运行时保持健康。

某个 Agent 即使语义上最合适，也可能因为延迟升高、成功率下降、工具异常而不再适合继续接单。

### Monitor 做了什么

- 定时采集 Agent 成功率和平均延迟
- 定时采集工具成功率和延迟
- 做异常检测
- 生成告警和建议
- 把结果写回 `monitor_penalty`

### 这意味着什么

路由不是静态的。\
在线表现差的Agent，其同类实例选择分数会降低；这是取最高分，不是概率抽样。默认每类一个实例，因此不保证能切换到其他实例，也不是自动训练。

### 面试时怎么讲

> 项目把监控结果接回同类实例选择，成功率、延迟和monitor_penalty影响routing_score。我会区分领域分工和实例选择；默认单实例下不能声称已经验证故障实例自动切换。

## 亮点八：端到端评测闭环

**文件**：`evaluation/evaluator.py`

### 解决的问题

如果没有评测，优化只能靠感觉。

### 当前评测内容

- 意图识别 Accuracy
- Macro-F1
- 单类 Precision / Recall / F1
- 对话回复质量
- 回归检测
- 优化建议

### LLM-as-Judge

回复质量由 LLM 从四个维度打分：

- relevance
- accuracy
- completeness
- helpfulness

### 业务事实、候选与回归

Judge四维均分阈值0.75；失败评分不计入有效均值。Judge接收本轮真实卡片/工具背景，不能给它预期断言或未来动作。业务断言直接读取角色、工具、库存、患者与回执，显式按钮动作由场景执行器完成。每个场景用独立数据前缀和记忆集合，清理只处理自己的数据。

报告先存`candidate`；显式人工接受后才作基线。相对已接受基线下降超过5%时标记回归；比较前还须核对输入、模型和参数。U001 历史完整候选66/66意图、30/30质量、26/27业务，共57/58；路线修复后只原样两轮3/3，不能替换原完整结果。对应工程测试684 passed/21 skipped、前端35项；最后提示修复后119项定向通过。见[评测证据](../docs/evaluation.md)。

U002 另以固定留出集、相同真实 LLM 响应重放比较语义、hash 与关闭向量：低重合向量单路改善，但融合持平，故障接受准确率未过门槛。它验证的是意图分支，不能替代业务 HTTP 验收，也不能据此宣布整个版本通过；集中数据见[指标模板](带数据指标的加强版简历模板.md)。

### 为什么这重要

它让项目从“能跑”变成“能量化迭代”。

### 面试时怎么讲

> 我不只做了多 Agent 编排，还把意图识别和回复质量都接进了评测闭环。这样系统不是靠感觉调，而是能用 Accuracy、Macro-F1 和 LLM-as-Judge 做持续回归。

## 一句话总结

MediPet 的技术亮点不在单点模块，而在于它把以下能力串成了闭环：

- 识别问题
- 路由角色
- 协作执行
- 检索知识
- 管理记忆
- 注入规则
- 监控质量
- 量化评测

一句话概括：

> MediPet 是一个可观测、可评测、可降级的多 Agent 就诊助手运行时，而不是单纯的聊天机器人。
