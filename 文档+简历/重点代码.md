## 1. `/chat` 主链路

**文件**：[api/main.py](../api/main.py)

这是整套系统的入口。MediPet 的请求处理顺序不是“直接回答”，而是：

```text
核对患者事项 -> 急症检查 -> 普通路径读取记忆/识别意图 -> 多Agent路由
-> 角色按需工具/RAG -> 生成文字并保留实际卡片 -> 完整历史 -> 工作窗口 -> 普通路径后台画像
```

下面是 [api/main.py](../api/main.py) 中 `chat` 的连续真实方法摘录。保留字段传递和写入顺序，便于逐行追踪；模块导入、生命周期、全局依赖、请求/响应模型在原文件中，因此不能把这一块单独复制成应用运行。

```python
@app.post("/chat", response_model=ChatResponse)
async def chat(req: ChatRequest, background_tasks: BackgroundTasks):
    """
    主对话接口。完整流程：
      记忆读取 → 意图识别 → Agent 路由 → 执行 → 记忆写入
    """
    if _orchestrator is None or _memory is None:
        raise HTTPException(503, "服务未就绪")

    from agents.agent_orchestrator import Request as OrcReq
    from memory.conversation_memory import MsgRole
    from core.intent_recognizer import IntentCategory, IntentResult, UrgencyLevel

    visit = await _load_visit(req.user_id, req.conv_id, req.patient_id)
    identity = VisitIdentity(user_id=visit.user_id, patient_id=visit.patient_id, conv_id=visit.conv_id)
    emergency = detect_emergency(req.message)
    history, full_context = None, ""
    if emergency:
        intent_result = IntentResult(IntentCategory.EMERGENCY, 1.0, UrgencyLevel.CRITICAL,
                                     "escalation", {}, "预设急症信号", 0.0)
    else:
        try:
            mem_ctx = await _memory.get_context(identity, query=req.message)
        except VisitStoreError as exc:
            raise _business_http(exc) from exc
        history = [{"role": m.role.value, "content": m.content} for m in mem_ctx.recent_messages[-5:]] or None
        full_context = mem_ctx.to_prompt_text()
        intent_result = await _orchestrator.recognize_intent(req.message, history=history)

    result = await _orchestrator.run(OrcReq(
        message=req.message, **identity.model_dump(), context=full_context, history=history,
        entities=intent_result.entities, intent=intent_result.intent, intent_group=intent_result.intent_group,
        urgency=intent_result.urgency, intent_confidence=intent_result.confidence,
    ))
    response = ChatResponse(
        conv_id=visit.conv_id,
        patient_id=visit.patient_id,
        visit=visit,
        artifacts=result.artifacts,
        tool_traces=result.tool_traces,
        request_id=result.request_id,
        response=result.response,
        intent=result.intent.value if result.intent else "other",
        intent_group=intent_result.intent_group,
        agent_type=result.agent_type.value,
        agent_types=[agent_type.value for agent_type in result.agent_types],
        primary_agent=result.primary_agent.value if result.primary_agent else result.agent_type.value,
        supporting_agents=[agent_type.value for agent_type in result.supporting_agents],
        tools_used=result.tools_used,
        routing_reason=result.routing_reason,
        routing_confidence=result.routing_confidence,
        escalated=result.escalated,
        latency_ms=round(result.latency_ms, 1),
        knowledge_used=any(trace.get("tool_name", trace.get("tool")) == "search_knowledge_base"
                           and trace.get("success") for trace in result.tool_traces),
        entities=intent_result.entities,
        intent_confidence=round(intent_result.confidence, 4),
        intent_source_scores=intent_result.source_scores,
        intent_embedding=intent_result.embedding_info,
    )
    # 完整历史先落盘；摘要和工作窗口都不是业务记录的来源。
    metadata = response.model_dump(mode="json", exclude={"visit", "artifacts", "response", "conv_id", "patient_id"})
    message_id = uuid.uuid4().hex
    now = _visits_ready().now()
    messages = [
        VisitMessage(**identity.model_dump(), message_id=f"user:{message_id}", role="user", content=req.message, created_at=now),
        VisitMessage(**identity.model_dump(), message_id=f"assistant:{message_id}", role="assistant", content=result.response,
                     artifacts=result.artifacts, metadata=metadata, created_at=now),
    ]
    try:
        await _visits_ready().append_messages(identity.user_id, identity.conv_id, messages)
        response.visit = await _visits_ready().get_visit(identity.user_id, identity.conv_id)
    except VisitStoreError as exc:
        raise _business_http(exc) from exc
    # 急症只追加窗口，不触发压缩/画像模型；完整历史与窗口都保留此轮。
    if emergency:
        await _memory.add_message(identity, MsgRole.USER, req.message, compress=False)
        await _memory.add_message(identity, MsgRole.ASSISTANT, result.response,
                                  metadata={"artifacts": [a.model_dump(mode="json") for a in result.artifacts]}, compress=False)
    else:
        await _memory.add_message(identity, MsgRole.USER, req.message)
        await _memory.add_message(identity, MsgRole.ASSISTANT, result.response,
                                  metadata={"artifacts": [a.model_dump(mode="json") for a in result.artifacts]})
        background_tasks.add_task(_memory.update_profile, identity)
    return response
```

### 这里最值得看懂的点

- `get_context()` 会同时拿到工作记忆、情景记忆、用户画像
- `recognize_intent()` 先输出结构化意图，编排器再决定主辅角色；RAG由角色实际选择知识工具时触发
- `OrcReq` 不仅有原始消息，还有经服务端绑定的身份、`entities`、`urgency`、`intent_group`；API已分类后编排器不重复识别
- 先持久保存完整消息/卡片，再写工作窗口；普通路径后台画像，急症路径`compress=False`且不安排画像

逐行跟一个例子：先由POST /visits取得孩子的真实事项ID，再发送“明天儿科还有号吗”。_load_visit把三项身份固定下来；history取最近5条，context来自模型记忆；IntentResult的字段进入OrcReq；返回的slot_list进入VisitMessage.artifacts。下一轮“选第一个”通过同事项最近列表解析，而不是靠模型发明slot_id。

完整JSON一次返回，不是SSE；完整历史和工作窗口也不是共同事务。若业务已成功但历史刷新失败，应按相应恢复入口处理，不能认为整条请求自动回滚。

## 2. 三路融合意图识别

**文件**：[core/intent_recognizer.py](../core/intent_recognizer.py)

这是 MediPet 的第一个核心层：先把“用户到底想干什么”结构化出来。

### 识别链路

```text
LLM Few-shot
Embedding 相似度
Pattern 规则匹配
-> 加权投票
-> intent / intent_group / confidence / source_scores / urgency / entities
```

### 代码层设计

`recognize()` 会并行启动 LLM 和 Embedding，Pattern 同步执行：

```python
llm_task = asyncio.create_task(self._llm_recognize(message, history))
emb_task = asyncio.create_task(self._embedding_recognize(message)) if self._embedding_enabled else None
pat      = self._pattern_recognize(message)
```

`_llm_recognize()` 每类仅把首条模板放入分类提示；`learn()` 追加到该类模板末尾，给已有类别增加样例通常只扩展向量模板，不会自动增加 LLM 示例。它只修改当前实例并清理分类缓存，不训练模型权重，不自动持久化或跨实例传播。然后在 `_vote()` 里做融合：

- LLM 负责语义理解
- Embedding 负责和模板样本做相似度匹配
- Pattern 负责快速兜底和细粒度纠偏

为什么要三路：LLM能读复杂语义，但有成本和失败；关键词快且可解释，但覆盖窄；模板相似度补充表达变化，但不能代替业务边界。并行减少部分串行等待，不证明整体速度或准确率提升。

当前正常权重0.7/0.2/0.1，关闭向量时0.85/0.15。每类累计支持它的权重×分数。LLM失败先做强细粒度关键词和语义信号冲突检查，再按强关键词、合格语义、带一致关键词支持的hash决定是否接管；否则OTHER，不重新归一化；正常投票还可能先用具体关键词修正宽泛类别，最后未提前返回才用默认0.5阈值。

手算示例：LLM 和已通过校准门槛的向量以 0.9/0.8 支持 `slot_query`，关键词以 0.7 支持 `doctor_info`，则分别为 0.79 和 0.07。LLM 失败后不能只看 0.8：语义还需模板未变、非受控上下文省略、无强关键词冲突；hash 则需一致细粒度关键词。条件通过时，语义分支返回向量分，hash 返回 `min(向量分, 关键词分)`，都不是再乘 0.2；条件不通过应拒绝。请对照 `_vote()` 的返回顺序。

意图编码实现位于[core/intent_embeddings.py](../core/intent_embeddings.py)：`OnnxSemanticBackend`离线加载固定BAAI/bge-small-zh-v1.5资产，FP32、512维、CLS+L2、512 token、无检索前缀。`hash_embedding`保留原256维字符1/2/3-gram算法：每个去重gram通过MD5映射到维度和正负符号，再做余弦比较。后者是显式对照或语义失败后备，不是中文训练模型；知识库的Chroma客户端all-MiniLM-L6-v2是独立路径。

继续沿调用链读：IntentEmbeddingProvider.initialize/encode_batch负责有界线程推理和整路降级；`_load_template_embeddings`在锁内以空间/`generation`/模板版本建立完整快照；`_embedding_recognize`计算各类别最佳余弦排名；`_apply_embedding_calibration`应用门槛；`_vote`融合。查询与模板空间不一致时重建，不能截短向量继续算分。

### 一段连续的校准代码

下面摘自当前IntentRecognizer._apply_embedding_calibration，是生产推理与离线回放共用的方法，不是评测另写一套公式。它依赖类字段和模块导入，须回原文件阅读，不能单独复制为程序。

```python
    def _apply_embedding_calibration(
        self, message: str, ranking: List[Dict[str, Any]], info: Dict[str, Any],
    ) -> Dict[str, Any]:
        """对同一空间的类别排名应用门槛；离线回放与真实推理共用此规则。"""
        best_cat, best_score = IntentCategory(ranking[0]["intent"]), ranking[0]["score"]
        runner_up = ranking[1]["score"] if len(ranking) > 1 else None
        margin = best_score - runner_up if runner_up is not None else best_score
        backend, space_id = info["active_backend"], info["space_id"]
        policy = self._calibration.get("backends", {}).get(backend, {})
        calibrated = bool(policy and policy.get("space_id") == space_id)
        changed = self._calibration.get("template_fingerprint") != self.template_fingerprint
        context_dependent = bool(re.fullmatch(
            r"(?:明天|后天|今天|上午|下午|那个|这个|第[一二三四五六七八九十\d]+个|还是下午)(?:呢|吧|可以吗)?[？?。！!]*",
            message.strip()))
        accepted = (calibrated and best_score >= policy["min_score"]
                    and margin >= policy["min_margin"] and best_cat != IntentCategory.OTHER)
        details = {**info, "template_revision": self._template_revision,
                   "template_fingerprint": self.template_fingerprint,
                   "calibration_version": self._calibration_version,
                   "calibration_status": "calibrated" if calibrated else "uncalibrated",
                   "template_changed_since_calibration": changed,
                   "requires_context": context_dependent,
                   "top1": best_score, "runner_up": runner_up, "margin": margin,
                   "accepted": accepted, "cache_hit": False}
        return {"intent": best_cat, "confidence": max(0.0, best_score) if accepted else 0.0,
                "accepted": accepted,
                "standalone": accepted and calibrated and not changed and not context_dependent,
                "backend": backend, "info": details, "ranking": ranking}
```

先按不同类别排序，才有`top1`与`runner_up`；同类模板多不能让`margin`虚高。空间未绑定则弃权；追加模板后正常融合保留同空间门槛，但standalone关闭。这里的上下文检查只是有限省略表达规则，不是通用语法理解。

### 模型共享与缓存隔离

API、编排器与隔离评测可注入同一个编码provider，识别器模板、`learn`和结果缓存各自独立。`_classification_version`组合空间、`generation`、模板与校准版本；`recognize`在等待LLM后再次核对向量快照，避免等待期间`learn`或降级使旧结果投票。超时后的底层线程不一定已停止，退出须回收资源，不在请求里循环加载模型。

### 输出字段

`IntentResult` 里真正有用的不是只有 `intent`，还有：

- `intent_group`
- `confidence`
- `source_scores`
- `embedding_info`：实际后端/空间、门槛、`top1`/`margin`及降级/截断/缓存状态；API映射为`intent_embedding`
- `urgency`
- `entities`

其中 `entities` 会规则抽取：

- `department`、`doctor`、`date`、`period`
- 原文已有的`slot_id`、`appointment_id`
- `origin`、`destination`、`accessibility`
- `selection_index`：一基位置，交当前事项最近成功列表解析

名称、日期和ID是查询线索，仍需服务端验证。完整清洗消息、最近三条完整历史、上海日期与模型/模板/校准版本共同进入缓存键；跨午夜“明天”不能读昨天结果，长消息也不能仅因前200字相同而共用分类。满1000项删除最早插入500项，命中不调整顺序，因此不是严格LRU。

意图输入示例见[MediPet学习文档](MediPet学习文档.md)的4.1节：医院目录、号源/准备/查询/取消、材料/流程/路线、人工/急症，以及symptom_query、medication_query、report_query。症状与报告都交Triage，不新增ReportAgent。

### 紧急度

系统把紧急度分成 4 级：

- `LOW`
- `MEDIUM`
- `HIGH`
- `CRITICAL`

规则来自两类信号：

- 消息中的紧急关键词
- 意图本身是否属于人工导诊、投诉等场景

普通输入默认LOW，投诉默认MEDIUM，人工请求默认HIGH；当前明确急症由共享detect_emergency先行检查并标CRITICAL。否定、历史和一般咨询应排除；超过39.5℃只是本演示的一个中断条件，不是完整临床分诊标准。

### 面试时怎么讲

> 我把意图识别做成了三路融合，不是单一分类器。LLM 负责语义，Embedding 负责相似度，Pattern 负责兜底，最后输出 intent、intent_group、source_scores、urgency 和 entities，直接给后续路由使用。

## 3. MCP 工具层

**文件**：[mcp/tool_manager.py](../mcp/tool_manager.py)

这个MCP模块是进程内handler管理器，没有实现独立MCP服务器、远程协议传输或服务发现。它负责两件事：

1. 把检索/外部能力标准化
2. 让调用具备缓存、超时、熔断和 fallback

### 关键机制

```text
缓存检查 -> 熔断检查 -> 参数校验 -> 带超时调用handler
-> 可选重排 -> 成功缓存/统计；失败保留错误并可降级
```

### 为什么重要

如果没有这一层，慢调用、重复查询和连续故障会更直接影响主链路。这一层限定等待并保留失败，不保证底层服务永不出错，也不自动保护没有经过管理器的业务事务。

### 重点设计

- `asyncio.wait_for()` 控制超时
- JSON Schema 校验参数
- 连续失败后触发熔断
- fallback 结果要可解释
- 每次实际调用更新成功率和延迟统计，供Monitor使用；缓存命中与实际执行需区分

默认超时30秒，连续失败5次熔断，60秒后尝试恢复；应用知识工具缓存300秒。号源、预约和个人报告直连业务服务，不进入公共RAG缓存。fallback提示仍带失败状态，不可作为真实文档来源。

### 面试时怎么讲

> 我没有把外部能力直接塞给 Agent，而是先抽象成工具层，再加缓存、熔断和 fallback。这样工具失败时系统能降级，而不是整条链路一起挂掉。

## 4. 知识库与 RAG

**文件**：[mcp/knowledge_base.py](../mcp/knowledge_base.py)、[mcp/tool_manager.py](../mcp/tool_manager.py)、[agents/tools.py](../agents/tools.py)

MediPet 的知识库不是“见词就搜”：意图先影响角色分工，再由角色按需调用 `search_knowledge_base`。管理页POST /search可独立触发相同检索链路。

### 主流程

```text
先识别意图并选择角色
-> 角色实际调用search_knowledge_base
-> 查询改写
-> 并行召回
-> 合并去重
-> LLM 重排
-> 注入上下文
```

### 为什么这样做

- 问候、闲聊、转人工，不需要查知识库
- 材料、流程和医院公开规则可按需检索
- 号源库存、预约记录、药品目录与个人报告回到各自服务，不用公开知识冒充业务状态

### 关键代码点

先从 `build_shared_rag_tools` 找到 `search_with_rewrite`。以下为 `mcp/tool_manager.py::search_with_rewrite` 的真实并行召回摘录：

```python
recall_k = max(top_k, 5)
tasks = [
    self.call(tool_name, {"query": q, "top_k": recall_k}, context, use_cache=True)
    for q in sub_queries
]
results = await asyncio.gather(*tasks, return_exceptions=True)
```

`sub_queries`保留原问题，最多加3条不同改写；同片段按chunk_id或内容去重，不能把score不同当两个来源。候选多于top_k才需要重排；重排索引要完整、唯一、合法，并排除bool。改写失败保留原查询，重排失败保留原顺序，错误字段在本次结果中记录。

不要根据API里仍存在 `_should_use_knowledge` 与 `_build_knowledge_context`，就把它们画在当前主调用链上；回到本篇第1节的真实chat摘录核对调用关系。

知识读取24份Markdown的doc_id/title/source_id/source，按句号和换行组织约500字片段；超长单句不保证严格切成500字。内置初始化按doc_id同步变化、删除该文档过时片段并保留独立上传。普通add/upload只补缺，不是同ID覆盖正文接口。Chroma的默认embedding在客户端执行，HTTP模式也一样。

### 你可以这样理解

RAG在这里既能独立管理检索，也能进入聊天工具链，而且是**按需触发**的一部分。检索到资料、资料有真实来源、模型忠实使用资料是三件事：分别检查results、sources和最终回答。no_results、retrieval_failed、partial、rewrite_error、rerank_error不能混作“检索成功”。

## 5. 多 Agent 编排

**文件**：[agents/agent_orchestrator.py](../agents/agent_orchestrator.py)

这是 MediPet 的第二个核心层：先决定“谁来处理”，再决定“怎么协作”。

### 不是 prompt-only

当前架构已经不是简单的：

```text
一个编排器 + 几个 prompt 不同的 Agent
```

而是：

```text
意图识别 -> 路由决策 -> 主 Agent / 辅助 Agent / 升级 Agent
          -> 单 Agent 执行或并行协作
          -> ResponseComposer 合并结果
```

### Agent 角色

- `GeneralAgent`
- `GuidanceAgent`
- `AppointmentAgent`
- `TriageAgent`
- `MedicationAgent`
- `EscalationAgent`

### 为什么 `pool` 是 `list`

`_pool: Dict[AgentType, List[BaseAgent]]` 的设计，是为了支持：

- 同角色多实例
- 不同模型配置
- 在线表现差异化路由
- 灰度和降级

当前默认每类只有一个实例，但结构已经预留多实例扩展。上面的不同配置、灰度方向不表示已经部署了多模型灰度平台；实际需要自己注册实例并验证配置。

### 路由依据

路由时会综合：

- `intent`
- `urgency`
- `entities`
- 关键词
- 在线表现

复杂请求会生成：

- `primary_agent`
- `supporting_agents`

比如“明天儿科还有号吗，第一次带孩子来要带什么”，可同时路由给预约和指引。

这里应分两层阅读：领域打分从General 0.1开始，意图、关键词和实体加分，显式复合信号决定辅助角色；无显式辅助时再考虑至少0.45且达到主领域55%的候选。确定角色后，`_best_agent`才在同类池按运行分数取最大值，不把线上延迟当成业务意图。

run_parallel用gather并发；ResponseComposer整合失败时保留成功主辅文字，卡片另外合并。同ID同内容去重，同ID不同内容全部丢弃并记录冲突；单个分支失败前已有的有效卡片仍保留。

### Agent 执行时的工具边界

每个 Agent 都有自己的 `AgentProfile`，里面定义了：

- 职责
- 工作流
- 输入契约
- 输出契约
- 升级条件
- `tool_scope`

这说明多 Agent 的差异不只是 prompt，而是角色契约、工具边界和路由位置都不同。下面补一段**教学伪代码**，概括 `BaseAgent._call_llm` 的连续过程；名称用于说明，不是可复制运行的实现：

```text
创建本轮AgentTurn，准备messages和该角色的工具白名单
循环最多3次模型请求：
    response = 调用模型(system、历史/背景、当前messages、工具schema)
    如果没有tool_use：提取文字，返回本轮文字和已保存结果
    保留模型本次assistant内容，让后续tool_result可对应tool_use_id
    对本次每一个tool_use：
        若名称不在白名单：记录调用失败，不执行handler
        否则校验参数；失败则记录校验错误
        否则调用绑定当前身份的handler
            分开记录调用成功与业务结果成功
            验证并保存真实artifact、source及错误信息
        为该tool_use_id建立真实成功/失败的tool_result
    把tool_result按协议交回messages，继续下一轮
如果3次后仍没有最终回复：返回失败并保留此前有效卡片/trace
```

三次请求不等于三个工具，也不是整次聊天总预算：分类、并行角色、改写、重排、整合、摘要等可能另外调用。共享“上次工具结果”会导致并发患者串数据，因此结果放请求局部的AgentTurn。

### 面试时怎么讲

> MediPet 的多 Agent 不是 prompt-only，而是路由驱动的角色编排。每个 Agent 都有自己的契约和工具边界，复杂问题还能主辅协作并行处理，在线表现还会反馈到下一轮路由里。

---

### 医院事务为什么不能藏在模型工具循环里

阅读 [hospital/service.py](../hospital/service.py) 的 `prepare_appointment`、`prepare_cancellation`、`confirm_proposal`。准备只产生pending方案，默认15分钟到期，不扣库存；改选使旧方案superseded。确认通过独立HTTP入口进行，模型没有confirm工具。

连续事务控制流的**教学伪代码**是：

```text
确认入口读取事项，固定参与者/患者/事项身份
WATCH 方案、事项、最近选择等键
检查方案归属；已执行则返回原回执
检查当前方案、pending状态与到期时间
WATCH 目标号源；取消时还WATCH原预约
核对快照、当前余量或原预约状态
计算新库存及预约/取消记录，生成原始回执
MULTI：写库存、预约、患者索引、方案回执、清理当前方案指针
EXEC：并发冲突则返回可重试conflict，不无限循环
API再以confirm:{receipt_id}/result:{receipt_id}追加去重历史
历史保存成功后失效工作窗口，让下一轮恢复真实回执
```

实现为Redis WATCH/MULTI/EXEC，没有Lua。幂等来自已执行方案及原回执，不靠模型记忆。取消后的旧创建回执仍保留当时快照；当前预约状态另查服务。业务已提交但历史失败时重试同一方案补写，不创建第二次预约。这也不是Redis、Chroma和模型的统一分布式事务。

## 6. 共享工具与 Skills

**文件**：[agents/agent_orchestrator.py](../agents/agent_orchestrator.py)、`core/skill_loader.py`

这一层解决的是“Agent 怎么说、怎么做、边界在哪”。

### 工具白名单

Agent 调用工具时不是直接裸调，而是：

- 先拿白名单
- 再做参数校验
- 再执行 handler
- 最后把结果回填给模型

### Skills 注入

`_build_system_prompt()` 会把动态 Skills 拼进 system prompt：

```python
skill_prompt = self._skill_manager.prompt_for(req.message, self.agent_type.value)
```

这意味着普通角色的Skills是在**选定Agent之后**注入的，不直接改变路由表、工具权限或确认授权。Escalation直接返回固定内容，不调用该prompt入口，不能靠重载Skill改变固定急症提示。

### 为什么这样拆

- 知识库回答“事实是什么”
- Skills 规定“应该怎么处理”

所以它们不是一回事。

### 热更新

修改 `skills/*/SKILL.md` 后可以通过POST `/skills/reload`重新加载，不用重启服务；没有自动文件监听。

当前六组为general_visit、appointment_assistance、visit_guidance、health_triage、medication_information、service_boundaries。按enabled、agents、关键词匹配，空关键词对指定角色常驻。单正文约3200字符，总预算默认5000字符，长规则会截断；解析错误要看GET /skills摘要，不能只看HTTP成功。

具体练习：将Skills复制到测试临时目录，修改一条表达规则；reload前捕获system prompt应保持旧文本，reload后才含新文本。查看[test_knowledge_skills.py](../tests/test_knowledge_skills.py)中的test_skill_changes_apply_only_after_explicit_reload。预期是验证注入链；实际模型遵循要另做受控演示。

---

### 医疗工具与报告也遵循同样分层

分诊函数 `health/triage.py::triage_symptoms` 根据有限症状和明确年龄语境给现有内科/儿科/眼科方向，不做诊断。“咳嗽3个月”不能当作婴儿月龄，缺年龄要澄清。

`health/medications.py::medication_information`只收录两个指定美国标签：对乙酰氨基酚500mg普通片、布洛芬200mg普通包衣片。未知药物/组合不推断安全，其他规格、缓释或复方不套用普通片。wrapper检查药名来自用户原文及邻接剂型，防止模型把“布洛芬缓释胶囊”截成“布洛芬”。资料不是个人处方，儿童、孕哺、肝肾异常等需医师药师核对。

报告粘贴可由Triage调用preprocess_report；文件走POST /reports/preprocess的multipart入口。文字/扫描/混合PDF和PNG/JPEG/WebP在本地提取，Tesseract中英文OCR不调用外部视觉模型，10MB、PDF10页。混合PDF有文字页眉也要读取扫描正文；低置信或无明确原参考范围时保留原文待核对，不补常见范围、不推断疾病。

原件不存，提取文字和report_summary保存在该患者事项。read_current_report先require_identity，再倒序找同事项最新报告卡；无报告则澄清或失败，不跨事项补取。上传本身零模型，不等于后续解释聊天零模型。

## 7. 三层记忆

**文件**：[memory/conversation_memory.py](../memory/conversation_memory.py)

MediPet 把记忆拆成三层：

- **工作记忆**：Redis，保存当前会话最近消息
- **情景记忆**：ChromaDB `medipet_episodic`，保存压缩摘要
- **用户画像**：ChromaDB `medipet_profiles`，按患者保存明确事实、按参与者保存表达偏好

### 这样拆的原因

- 当前轮要短
- 跨轮信息要保留
- 长期偏好不能丢

### 关键实现

- 普通工作窗口达到15条消息压缩，保留最近5条，窗口与摘要24小时TTL；不是15轮对话
- 压缩不是简单拼接，而是合并摘要；合并有800字符目标和失败兜底，不代表无损
- `to_prompt_text()` 只拼少量最近消息，避免上下文过长
- `update_profile()`在普通聊天后台执行；急症和报告上传不触发。模型只看最近用户原句，结果需通过原句子串校验

情景记忆先过滤参与者、患者和当前事项，不足时才回退同患者其他事项，不跨家属。VisitStore完整历史单独保存，窗口过期或确认后失效时从历史恢复最近最多20条，保留卡片和metadata，使用WATCH避免覆盖别人刚写出的窗口。

这里保留“当前轮、跨轮、长期”的时间尺度分离：只保留最近消息会忘长期偏好，只保留画像会丢当前任务，全部历史放prompt又会膨胀。完整历史解决产品展示和核查，不应每轮完整注入模型。

### 面试时怎么讲

> 我把记忆拆成工作记忆、情景记忆和用户画像三层，分别对应当前轮、跨轮线索和长期偏好。这样能控制上下文长度，也能保留跨会话连续性。

## 8. Monitor 在线观测

**文件**：[monitor/performance_monitor.py](../monitor/performance_monitor.py)

Monitor 的作用不是“看板”，而是把运行情况重新送回路由层。

### 它做什么

- 周期性读取 Agent 和工具统计
- 检测成功率和延迟异常
- 生成建议
- 写回 `monitor_penalty`

### 和路由的关系

`AgentStats.routing_score()` 会把 `monitor_penalty` 算进去。\
实际分数为 `(成功率×0.7 + 1/(1+平均毫秒/1000)×0.3) × max(0,1-monitor_penalty)`。在线表现差会降低同类实例分数，`_best_agent`取最大值，不是概率抽样。当前每类默认一个实例，不能因此宣称已有自动备用供应商。

### 这个闭环很重要

这说明同类实例选择有运行反馈，但不是根据医学回答质量自动训练或改提示词。运行成功率、延迟和回答事实准确性需要分别评估；工具管理器统计也不自动覆盖全部直连业务。

### 面试时怎么讲

> 我把监控结果接回了路由层，而不是只做展示。Agent 的成功率和延迟会影响 routing_score，在配置同角色多个实例时，可据运行表现选择得分更高的节点；当前默认单实例不夸大成自动扩容或模型切换。

## 9. 端到端评测

**文件**：[evaluation/evaluator.py](../evaluation/evaluator.py)

评测层解决的是“怎么知道系统有没有变好”。

### 两类评测

先理解两类基础评测，再看当前新增的业务状态断言：

1. **意图识别评测**
   - Accuracy
   - Macro-F1
   - 单类 Precision / Recall / F1

2. **对话质量评测**
   - 用 LLM-as-Judge 打分
   - 维度是 relevance、accuracy、completeness、helpfulness

Accuracy是正确预测/全部样本；Precision=TP/(TP+FP)，Recall=TP/(TP+FN)，F1=2PR/(P+R)，Macro-F1对各类F1等权平均，零分母按实现处理为0。举例：某类TP=3、FP=1、FN=2，则P=0.75、R=0.6、F1约0.667；不能只看总体准确率忽略少数类。

Judge每维0–1，四维平均达到0.75是质量通过条件。当前另加业务断言，检查库存、患者归属、卡片、回执和失败路径；高Judge分不能覆盖业务失败。

### 为什么不是 mock

评测会真实调用 `AgentOrchestrator.run()` 生成回复，再交给 judge 评分。\
这是直接编排器/服务链路，不等于HTTP与浏览器端到端全覆盖。测试套件还会用假模型做确定性机制验证，须和实际模型报告分开。

每个场景使用独立Redis前缀与Chroma记忆集合、固定业务时钟，退出精确清理；确认、切患者和推进时间由夹具执行，不交模型自由操作。Judge背景包含真实旧上下文、本轮卡片/工具成败/来源、绑定身份与时钟，存入metadata.judge_context，不泄漏预期断言或未来动作。调用失败、Judge失败、非法评分和跳过分开计数，judge=False也检查执行失败。

### 回归检测

评测结果可以和已人工接受的历史基线对比，用来判断有没有退化。普通run只保存`candidate`，`accept_baseline`要求明确复核人；前一次候选不会自动成为基线。

U001 历史记录：后端全量684 passed、21 skipped，前端35/35及build通过；Guidance最后提示修复后另跑119项相关检查，并非重跑全量。完整真实候选66/15/12输入，66/66意图、30/30质量、26/27业务，合计57/58。旧无障碍续问失败保留，新医疗通过；原样两轮定点修复3/3不能拼成全量58/58。两份候选均未人工接受，见[验收证据](../docs/internal/updates/U001-health-consultation/evidence/acceptance.md)。

U002 的意图专项入口是 [evaluation/semantic_intent.py](../evaluation/semantic_intent.py)：先保存实际向量排名和真实 LLM 响应，再复用生产分类器做三模式重放，不重复调用模型。它与 `/eval/run` 的 Agent、业务工具和 Judge 闭环不同。留出结果显示低重合向量单路改善、融合持平，故障接受准确率未过门槛，不能称 U002 已最终验收；数字和分母见[学习文档](MediPet学习文档.md)4.8及[指标模板](带数据指标的加强版简历模板.md)。

### 面试时怎么讲

> 我不只做了多 Agent 编排，还把意图识别和回复质量都接进了评测闭环。这样系统不是靠感觉调，而是能用 Accuracy、Macro-F1 和 LLM-as-Judge 持续回归。

1. `/chat` 主链路
2. 三路融合意图识别

5. 三层记忆
6. Monitor 闭环
7. 评测闭环

不要只记模块名字。可以按以下步骤检查理解；均使用既有确定性测试和隔离夹具，下面命令只用于学习者本地验证，本轮文档修订没有重新运行它们。

| 步骤 | 阅读或操作 | 预期与解释 |
|---|---|---|
| 1 | 跟第1节chat，标出身份、history、IntentResult、OrcReq、VisitMessage | 能说明每个字段来自用户、服务端还是模型；不从模型答案建立身份 |
| 2 | 手算三路0.79/0.07，再读校准与`_vote`提前返回 | 向量先过门槛；失败时冲突拒绝、hash需同类规则支持，不能自行归一化 |
| 3 | 阅读并运行三次工具请求上限测试 | 3次模型请求后停止，工具数可超过3 |
| 4 | 阅读并行测试的事件协调与Composer失败 | 两角色确实同时进入，失败后主辅原文保留 |
